# 睡眠養成 設計手冊

把「早睡、規律作息，你的夜間小世界就越安詳漂亮」這個方向整理成一份設計文件：概念、核心機制、就寢偵測方案、差異化賣點、避坑教訓、商業模式、技術平台、畫面框架、資料模型、待決事項。之後每次討論有新決定，這份文件會再更新。

> 沿用「許願池」同一套成功邏輯：**使用者的行為直接長出畫面上的東西，只給正回饋、不給罪惡感、一句話能講完。**

---

## 01 概念

- **核心體驗：** 使用者設定一個目標就寢時間，每晚在睡前按一下「睡了」，準時就寢的日子越多，畫面上的**夜間小世界／小鎮就越安詳漂亮**；晚睡的日子畫面也溫柔地反映出來（但不懲罰）。
- **一句話定位：** **「你把自己照顧好，夜晚的世界就越美。」**
- **明確不做什麼：** 不宣稱有醫療級睡眠分析、不做睡眠品質診斷。賣的是**作息規律的習慣養成 + 情感回報**，不是睡眠醫學。
- **差異化的核心：** 市面睡眠 App 兩種——精準追蹤型（要戴手環、比數據、有壓力）或純提醒鬧鐘型（冷冰冰、沒情感）。這個方向切的是「**不比數據，比你有沒有好好照顧自己，而且照顧得好世界就美**」。

---

## 02 核心機制

**1. 設定目標就寢時間**
- 使用者自己設一個目標（例如 23:00），這是後續所有達標判斷的基準。

**2. 睡前「就寢打卡」（主動作，也是儀式）**
- 睡前按一個「睡了」按鈕，觸發一段收心的儀式動畫（小鎮熄燈入夜、燈火漸暗、環境音轉為夜晚）。
- **這個動作本身就是設計的核心價值**——一個睡前放下手機的收心儀式，跟許願池投香油錢同一個邏輯。
- 早上按「起床」（或第一次解鎖 App 視為起床），結束當晚紀錄。

**3. 達標判斷與規律累積**
- 在目標時間前按「睡了」＝當天達標。
- 連續達標的日子累積 →「規律」→ 夜間小世界越來越美（多幾盞燈、多一戶人家、夜空更清澈）。
- **晚睡不扣分、不變醜**，只是那天沒有推進；漏按也不懲罰。

**4. 溫柔回顧**
- 「你這個月準時就寢 18 天」「連續一週都早睡」這類正向回顧，做為回訪動機。

## 03 就寢偵測方案（本方向的關鍵技術問題）

> **重要前提：手機 App 無法「真的」偵測你睡著沒——那是穿戴裝置（手環／手錶，貼身測心率與體動）才做得到。但這個 App 根本不需要精準偵測睡眠，只要抓「就寢規律」，用手機就能做，而且越簡單越好。**

三種方案，由最推薦到最複雜：

### 方案 A：手動就寢打卡（主機制，強烈建議）
- 睡前按「睡了」、早上按「起床」。以按鈕時間點判斷是否在目標時間前。
- **優點：**
  - 技術最簡單，不碰任何感測器權限，不會被 App 審核刁難。
  - **「按下睡了」本身就是儀式感**，正好是要的體驗。
  - 不需要知道有沒有真的睡著——賣的是作息規律，按了就代表「我準備睡了」，這就夠。
- **缺點：** 靠自律，忘按就沒紀錄。→ 設計成「按了有獎勵、忘了不懲罰」，呼應不給罪惡感原則。

### 方案 B：用手機使用行為推測（半自動，選配）
- 不直接測睡眠，用「手機有沒有在用」當代理指標：夜間某時間後持續沒解鎖、沒操作 → 推測就寢；早上第一次解鎖 → 起床。
- 可搭配系統的就寢模式（iOS Sleep Focus、Android Bedtime mode）。
- **缺點：** 睡前滑手機到很晚、或睡著手機還開著，誤差大；拿使用者活動記錄權限，審核與隱私說明較麻煩。

### 方案 C：接現成健康資料（最精準，加分項）
- 讀已戴穿戴裝置使用者的睡眠資料：Apple 讀 **HealthKit**、Android 讀 **Health Connect**（Google 統一健康資料層，取代舊 Google Fit）。
- **優點：** 有手環的人資料最準，可自動填入免手動。
- **缺點：**
  - 只有戴穿戴裝置的人才有資料（可能是少數），不能當主要機制。
  - 健康資料是敏感個資，權限與合規門檻高。
  - Godot 接原生 API 需額外橋接，工程量不小。

### 採用建議
**主機制用方案 A（手動打卡），方案 C 當給有手環使用者的自動加分（有就自動填，沒有就手動）。方案 B 除非有明確好處，否則先不做（誤差大又踩隱私）。** 力氣花在畫面與儀式上，判斷邏輯越簡單越好。**絕對不去碰「精準偵測睡著」這個坑**——那是穿戴裝置和醫療級 App 的戰場，手機做不好還會讓人覺得「不準」而棄用。

## 04 差異化與賣點

一句話：**「你把自己照顧好，夜晚的世界就越美。」**

- **主打賣點——會變美的夜間世界：** 規律作息累積成一個越來越安詳漂亮的夜景，用越久越有感情（跟許願池「會長大的樹」同一個護城河邏輯）。
- **不比數據，比照顧：** 不追蹤精密睡眠週期、不給你一堆焦慮的數字，只問「你今天有沒有好好準時休息」。
- **晚睡不懲罰：** 沒達標的日子畫面不變醜、不扣分，只是沒推進。這是留住人的關鍵（Habitica 扣血讓人棄坑，Finch 純鼓勵所以爆紅）。
- **睡前儀式感：** 「按下睡了 → 小鎮熄燈入夜」是一個幫人放下手機、收心入睡的溫柔動作，本身就有價值。

## 05 避坑：睡眠／習慣類 App 的墳場教訓

- **別做精準睡眠偵測：** 手機做不好，使用者一發現「不準」就棄用。這是穿戴裝置的戰場，不要進。
- **別用 streak 壓力：** 連續早睡可當正回饋，但斷了不懲罰、不扣分、不罵人。
- **別讓晚睡觸發難看畫面：** 使用者晚睡時若畫面變醜／變懲罰，等於在指責他，摧毀信任。晚睡的夜景也要美，只是「少一點光」而非「變醜」。
- **別把判斷邏輯做複雜：** 越想精準越容易出錯又難維護。目標時間 ± 打卡時間點，這麼簡單就夠驅動整套成長。

## 06 商業模式

- **核心免費：** 設定就寢時間、打卡、看夜間世界永遠免費。
- **訂閱制為主：** 去廣告＋更多世界主題／建築／夜景風格＋進階回顧。
- **低價外觀課金：** 夜景主題、建築造型、環境音包，真錢透明標價。
- **廣告（若用）：** 自願／激勵式，絕不打斷睡前儀式流程，類別排除博弈／酒類／借貸。
- **絕對不做：** 隨機／抽獎式付費獎勵。

## 09 資料模型（雛形）

**User**
- id
- target_bedtime（目標就寢時間，如 23:00）
- created_at
- deleted_at（軟刪除）

**SleepEntry（每晚就寢紀錄）**
- id / user_id
- date（以「入睡日」為準，一晚一筆）
- bedtime_at（按「睡了」的時間）
- wakeup_at（按「起床」或首次解鎖時間，選填）
- source：manual／health_data（手動或穿戴裝置）
- is_on_time（是否在目標時間前，達標判斷結果）
- created_at / updated_at
- deleted_at（軟刪除）

**Transaction（若有課金／訂閱）**
- id / user_id
- type：訂閱／課金／花費
- amount / reference_id
- created_at

**ShopItem**
- id / name
- type：夜景主題／建築／音效
- price

**WorldState（夜間世界目前狀態，可由紀錄推算或存快取）**
- user_id
- growth_level（世界繁榮程度，由累積達標推進）
- unlocked_items（已解鎖的建築／裝飾）
- updated_at

**關鍵設計：**
- 一晚一筆，跨午夜的就寢以「入睡日」歸屬，避免日期錯亂。
- 達標判斷（is_on_time）在記錄時就算好存起來，畫面不用每次重算。
- 全部軟刪除。

## 10 待決事項

- **達標判斷的寬容度：** 剛好卡目標時間、或晚幾分鐘算不算達標？要不要給緩衝區間（如目標 ±15 分）？
- **世界成長的門檻：** 累積幾天達標升一級？多久能看到世界明顯變化？（太慢沒動力、太快沒份量）
- **晚睡的畫面怎麼呈現：** 「少一點光」的溫柔版本具體長怎樣？確保不變成懲罰感。
- **要不要做起床偵測：** 只做就寢就夠，還是要連起床規律一起養成？（建議 MVP 先只做就寢，簡單優先）
- **通知策略：** 就寢提醒怎麼發才溫柔不惱人？發太多會被關通知。
- **帳號模型：** 純裝置 ID 匿名 vs 輕量帳號備份（就寢紀錄是長期資產，掉資料很傷）。
- **健康資料整合的優先級：** 方案 C 是否值得做，還是先純手動就好。
