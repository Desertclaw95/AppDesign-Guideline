# 小村落・統一世界觀設計手冊

把原本三個獨立方向（許願池／情緒天氣／睡眠養成）合併成**同一個世界**的整合草案：一個村落，家、樹、天空分別對應三套原本的核心機制，外加討論中新增的「每日運勢籤」。這份文件**整合自三份原始手冊**，作為後續要不要正式取代它們的討論底稿——內容仍有多處待拍板（見第 12 節），不是定案。

## 01 概念

- **核心體驗：** 使用者擁有一個自己的小村落。**家裡**好好睡覺，屋子會越住越溫馨（原睡眠養成）；**家門口的大樹**用來許願／告解，樹隨心願長大（原許願池）；**村落的天空**會變化，一部分反映真實天氣、一部分反映使用者自選的心情（原情緒天氣）；每天早上還可以抽一張**今日運勢籤**，開啟新的一天。
- **一句話定位（草案）：** **「照顧好你的小村落——家越住越暖，樹越長越大，天空跟著你的心情一起變。」**
- **為什麼合併：** 三個原方向的核心機制其實是同一套哲學的三種表現（行為直接長出畫面、只給正回饋、一句話能講完），而且畫面調性都是「夜晚、安靜、留白」。合併成一個世界後，使用者只需要對一個場景產生感情，而不是在三個 App 之間分散注意力，護城河（時間累積感）也更集中、更難被抄。
- **明確不做什麼：** 不宣稱醫療／心理治療效果、不做睡眠或情緒的醫療級診斷、不做評分量表、不做精準睡眠偵測、不做隨機抽獎式付費。這幾條是三份原手冊共同的紅線，合併後全部延續。
- **純文字、不上圖片：** 沿用原本決定，所有使用者輸入（許願、告解、心情備註）都只用文字，不開放上傳圖片，理由不變：貼合安靜留白的調性、繞開 Firebase Storage 免費方案的雷、大幅降低審核負擔。

## 02 世界結構與核心機制

村落是整個 App 的主畫面樞紐，打開 App 第一眼就是這個場景，而不是選單。

| 區域 | 對應原方向 | 主動作 | 累積的東西 |
|---|---|---|---|
| 家 | 睡眠養成 | 睡前按「睡了」 | 屋子越住越溫馨、燈火越多 |
| 家門口的樹 | 許願池 | 許願／告解 | 樹隨心願長大、掛滿願望籤 |
| 天空 | 情緒天氣 | 選今日心情天氣 | 累積成一張可回看的氣候圖 |
| （早晨入口） | 新增 | 抽今日運勢籤 | 每日一句話，不累積、當下用 |

### 一天的節奏（草案）

1. **早上打開 App** → 抽一張今日運勢籤（見第 03 節），順手選今天的心情天氣。
2. **白天任何時候** → 想許願或想告解，走到樹前面完成儀式。
3. **睡前** → 回到家，按「睡了」，屋子熄燈入夜，結束今天。

這個節奏把原本「一天一次」的單一觸點，變成「早、（白天彈性）、晚」的多次觸點，回訪頻率比三個分開的 App 各自一次還高，但**每個動作都維持原本的極簡儀式感，不強迫使用者三件事都做**——沒空的話，只做晚安打卡也完全成立。

### 天空：真實天氣 vs 心情天氣（需要拍板，見第 12 節）

這是合併後新出現、原本三份手冊都沒有的設計決定，兩種「天氣」意義不同，不能混為一談：

- **真實天氣（環境氛圍層）：** 串接手機定位或使用者設定城市的真實天氣 API，只決定村落的**大環境背景**（晴朗／陰雲／下雨的環境光與音效），純粹是氛圍裝飾，不代表使用者的任何行為。
- **心情天氣（使用者行為層）：** 使用者每天自選的心情天氣，這才是原「情緒天氣」的核心機制，決定**村落裡具體、跟你有關的細節**——例如家裡那盞燈的顏色、樹上光點的疏密、或是一個陪伴小角色的表情。累積起來變成情緒氣候圖。

**建議分工：** 真實天氣負責「大氣氛」，心情天氣負責「跟你有關的小細節」，兩者疊在同一個天空畫面上，不互相覆蓋、不互相打架。陰雨天氣（不管是真實還是心情）一樣要做得美、不能有懲罰感——這條原則三份手冊都反覆強調，合併後更要守住。

## 03 每日運勢籤（新增機制）

討論中新增的概念：早上抽一張「今日運勢卡」，滿足「每天早晨起來就想打開看看」的心理，同時填補「晚安動作是一天結束、沒辦法承載早晨儀式」這個空缺。

### 設計原則

- **不做成塔羅牌等級的正式占卜。** 塔羅需要成套插畫卡面，會直接撞上「純文字、不上圖片」的核心哲學，美術與牌義資料庫的工程量太大，而且塔羅本身的神秘學色彩會拉高法律與審核敏感度。
- **走「形式像抽籤、素材是純文字＋簡單幾何卡面」路線：** 用 CSS／SVG 畫簡單卡面（不是插畫），配抽卡動畫與音效，一樣有儀式感，不用養美術資產。
- **只給正回饋：** 不做「大吉大凶」二分法，不出現「犯小人」「諸事不宜」這類負面籤文。就算文案要提醒使用者留意什麼，也要包裝成正向建議，不能讓人抽到覺得倒楣——這是三份原手冊「只給正回饋、不給罪惡感」哲學的直接延伸。
- **可選擇跟天氣連動：** 下雨天抽到的籤文風格可以跟晴天不同（例如雨天籤偏向「沉澱」「安靜」的語氣），增加意境，但不是必要功能，可以排到後期。

### 卡片結構（草案）

- **一句話運勢**（像籤詩開頭，例如「今天適合把心裡的話說出口」）
- **一個正向關鍵字**（例如：好轉、沉澱、被看見——用關鍵字營造分類感，不用吉凶分級）
- **一句小提醒**（呼應村落裡的其他動作，例如「今天適合去樹下許一個新願望」「今晚早點回家看看」）

### 內容生成方式

不需要真的做命理演算法，本質是「文案模板庫 + 規則配對（可加入日期／天氣／使用者最近行為當種子）」，開發成本低，但需要準備足夠大的文案庫避免使用者很快看膩重複內容。

## 04 差異化與賣點

一句話定位（草案）：**「照顧好你的小村落——家越住越暖，樹越長越大，天空跟著你的心情一起變。」**

### 統一後的核心護城河：一個完整的、活的世界

三個原方向各自的賣點都是「會累積、看得見時間」的護城河（會長大的樹／會累積的氣候圖／會變美的夜間世界）。合併後這三個護城河**疊加在同一個場景裡**，使用者不是在管理三筆分散的紀錄，而是在照顧「一個地方」——這比任何單一機制都更難被抄，因為競品要抄就得整套世界觀一起抄。

### 承接自三份原手冊、合併後依然成立的賣點

- **回頭確認的戳心時刻**（原許願池）：三個月前許的願，App 溫柔問「這個願望實現了嗎？」。
- **一年前的今天**（原許願池／情緒天氣）：翻到舊願望或舊心情紀錄自動生成回顧卡，天然的分享點。
- **晚睡／陰雨天不懲罰**（原情緒天氣／睡眠養成）：畫面不因為「表現不好」變醜或變懲罰性，這是信任的基礎，合併後對整個村落畫面都適用，不只是單一區域。
- **純觀賞模式**（原許願池）：什麼都不做，只是看著村落——燈籠飄、天氣變化、風吹葉，讓 App 從工具變成「一個能待著的地方」。
- **聲音＋觸覺**（原許願池）：投香油錢的「鏘」、熄燈入夜的音效、抽籤的沙沙聲，配合震動，是成本低效果強的細節，MVP 就該有。

### 合併後新增的賣點

- **早中晚三個彈性觸點**，回訪頻率比單一動作的 App 高，但每個觸點都維持極簡不強迫。
- **每日運勢籤**本身是輕量、低成本、高頻率的內容鉤子，天生適合分享（「今天抽到這張」）。

## 05 內容與安全設計

沿用許願池手冊原則：**私密書寫完全自由，公開分享才需要安全機制**，這條原則對合併後的樹（許願／告解）與天空（心情備註）都適用。

- **許願：** 分類模板＋最多 20 字客製內容，預設會上公開心願牆，送出前跑基礎關鍵字過濾。
- **消災告解：** 私密自由書寫是預設狀態，不限字數、不審核；選擇公開分享時才進入安全層。
- **心情天氣的備註／標籤：** 同樣預設私密，若未來開放公開分享（如年度氣候圖分享），比照許願／告解的過濾原則處理。
- **公開分享安全層（適用所有可公開的內容）：** 不開放留言／回覆、不做排行榜或熱門榜、公開內容延遲＋打散顯示、每人每日分享次數上限、發布前跑關鍵字過濾。參考 Secret、Whisper、Yik Yak 死於「匿名＋自由留言＋排名」的教訓。
- **常態求助資源入口：** App 內（設定頁＋適當時機）要有**常態顯示**的求助資源（如自殺防治專線），不能只靠關鍵字觸發才出現。
- **危機內容處理原則：** 書寫過程中偵測到自殺／自傷等關鍵字，**不打斷、不即時攔截**；等使用者完成當次書寫後，才溫和地把求助資源浮出來。這條原則對樹（告解）與天空（心情備註）都適用。

## 06 法律風險備忘（合併版）

以台灣為主的初步整理，**不是正式法律意見**，正式上線前建議找律師看過條款與文案。

| 風險 | 相關規範 | 因應方向 |
|---|---|---|
| 宣稱消災解厄／今日運勢真的有效 | 消保法／公平交易法（不實廣告） | 文案定位為情緒抒發與娛樂體驗，不做效果宣稱；運勢籤文案避免使用「準確預測」等字眼 |
| 隨機付費獎勵（開運抽籤等） | 刑法賭博罪（射倖性要件） | 絕對不做，紅線項目——包含每日運勢籤本身也不能做成付費抽卡 |
| 告解／心情內容洩漏他人身分細節 | 個人資料保護法 | 使用條款明訂不得張貼他人個資 |
| 未成年人課金 | 民法交易效力 | 條款需載明，留意 Store 既有機制 |
| 危機內容未妥善轉介 | 企業社會責任／潛在究責 | 常態放置求助資源入口，偵測到危機內容於書寫完成後主動浮出 |
| 使用者無法刪除自己的資料 | 個人資料保護法（當事人刪除請求權） | 資料表支援軟刪除，使用者可隨時刪除自己的願望、告解、心情紀錄，公開分享版本連動撤下 |
| 讀取真實天氣所需的定位權限 | 個資／APP 審查（位置權限說明） | 定位僅用於天氣顯示，需在權限說明中清楚告知，並提供「手動選城市」取代定位的選項 |

## 07 商業模式

- **核心循環永遠免費：** 睡前打卡、許願、選心情天氣、抽今日運勢籤，一律不設付費門檻。
- **統一虛擬貨幣（沿用「香油錢」概念）：** 原本只在許願池出現的香油錢，合併後可以當作**整個村落共用的貨幣**——許願要花、也可以拿來買家的裝潢、樹的造型、天空／夜景主題。獲取管道：每日簽到＋自願看激勵廣告，不能直接用真錢購買（避免模糊使用者對花費的感知）。
- **課金走獨立通道：** 低價（約 NT$10–30）用真錢直接購買外觀與特效——房子的裝潢、樹的造型、天氣特效、運勢卡卡面風格，花費透明，不透過香油錢轉換。
- **訂閱制備案：** 去廣告＋無限額度＋專屬特效＋進階回顧分析，作為主要營收（書寫情境跟高頻廣告天生違和，參考 Day One、Reflectly）。
- **廣告（若用）：** 自願／激勵式，不打斷任何儀式流程，類別排除博弈／酒類／借貸。
- **絕對不做：** 隨機／抽獎式付費獎勵（含運勢籤付費抽卡），踩賭博法律紅線。

### 香油錢經濟・初版建議數值（沿用許願池原案，待實測調整）

| 項目 | 建議值 | 備註 |

| 許 1 次願 | 100 香油錢 | 基準單位 |
| 消災告解 | 免費或 30 香油錢 | 傾向免費 |

## 08 技術與平台

三份原手冊的技術評估完全一致，合併後不變，只是所有機制現在共用同一個 Godot 場景（村落），不需要分開三個專案。

| 項目 | 免費？ | 開源？ | 備註 |
|---|---|---|---|
| Godot（遊戲引擎） | 是 | 是 | 3D voxel 風格，同專案可輸出網頁＋原生 App，避開 Unity 授權費爭議 |
| Supabase（後台／資料庫） | 免費額度 | 核心開源 | 免費上限：資料庫 500 MB、儲存 1 GB、流量 5 GB／月、月活 5 萬、最多 2 專案，閒置 7 天自動暫停。純文字資料幾乎用不完額度 |
| MagicaVoxel（建模） | 是 | 否 | 房子、樹、燈籠、運勢卡等 voxel 資產 |
| Firebase | 免費額度 | 否 | **雷區：Spark 方案不能用 Cloud Storage**，若只當純資料庫可用，要存使用者上傳內容需升級付費 Blaze |
| 真實天氣 API | 通常有免費額度 | 視服務而定 | 需研究免費額度與請求頻率限制（如 OpenWeatherMap），只取天氣代碼即可，不需要完整氣象資料 |
| AdMob | 免費（分潤制） | 否 | 需設定廣告類別過濾＋兒童導向合規設定 |
| HealthKit（iOS）／Health Connect（Android） | 系統提供 | — | 選配，讀穿戴裝置睡眠資料；敏感個資，需授權與隱私說明，Godot 需原生橋接 |
| Apple／Google 開發者帳號 | 否 | — | US$99/年、US$25 一次性，上架必要成本 |

- id
- target_bedtime（目標就寢時間）

- location_or_city（真實天氣用，選填，可用手動城市取代定位）
- created_at
- deleted_at（軟刪除）

- id / user_id / private_content / share_publicly / shared_content / moderation_status / created_at / shared_at / unshared_at / deleted_at

- id / user_id

## 12 待決事項

這份合併草案還有幾個關鍵決定沒拍板，其中前兩項是**合併本身帶來的新風險**，建議優先討論：

- **MVP 範圍與上線策略（新增，最重要）：** 三個原方向分開規劃時，本來建議「先做最簡單的睡眠養成練手上架、驗證流程」。一旦合併成一個世界，等於一開始就要處理許願池的公開分享安全機制＋情緒天氣的天氣系統＋睡眠的打卡邏輯，開發量遠大於任何單一方向，也失去了「先出一個簡單版本練手」的路徑。**需要決定：是直接做完整村落再上線，還是先上線「只有家＋簡化版樹」的縮小版村落，天空與運勢籤留到 Phase 2？**
- **真實天氣與心情天氣的最終分工：** 第 02 節提出的「真實天氣管大環境、心情天氣管細節」是草案，實際要影響畫面上哪些具體元素，需要逐一列出來拍板。
- **是否要保留「三個獨立 App」的選項：** 這份文件預設走合併路線，但原本的比較文件也提過「當共用引擎的產品系列」分開上架的做法，兩條路線互斥，需要最終確認。
- **帳號模型：** 純裝置 ID 匿名（簡單但換機掉資料）vs 輕量帳號備份（保資料但多註冊摩擦）。合併後資料更豐富（願望史＋心情氣候圖＋就寢紀錄＋村落成長狀態全部綁在一起），掉資料的代價比任何單一方向都更高，傾向優先做帳號備份。
- **每日運勢籤的文案庫規模：** 需要準備多少組模板才不會讓使用者短期內看膩，以及要不要真的做「天氣影響籤文風格」這個加分機制。
- **村落各區域的成長門檻數字：** 家的溫馨等級、樹的生長階段，各自要累積多少天／多少願望才升級，需要具體數字（可先沿用許願池原案的門檻邏輯，再依實測調整）。
- **完整模板／詞庫文案清單：** 許願句、告解句型、運勢籤文案，三套內容庫的具體文字尚未撰寫。
- **App Store／Google Play 審查風險的具體條款比對**（類賭博、IAP 相關指引），尤其運勢籤功能上線前要再確認一次紅線。
