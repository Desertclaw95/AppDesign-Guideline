# 小村落設計手冊

把「許願池／情緒天氣／睡眠養成」三個原方向合併成一個世界的設計，整理成一份完整文件。這份文件**取代**《小村落・統一世界觀設計手冊》裡跟天空、心情天氣、每日運勢籤相關的設計（原文件保留作歷史紀錄），其餘沒提到的地方（內容安全、商業模式、技術平台）沿用原手冊。

## 01 概念

- **核心體驗：** 使用者擁有一個自己的小村落。打開 App 先停在**家**，這裡是每日運勢的入口，也看得到外面真實的天氣；想許願或想放下什麼，就**走出去門口的樹**，完成許願或告解的儀式；晚上回到家，按「睡了」，熄燈入夜，結束一天。
- **一句話定位：** **「照顧好你的小村落——家越住越暖，樹越長越大，外面的天氣，說著你此刻的心情。」**
- **為什麼是村落，不是三個分開的 App：** 三個原方向（許願、情緒抒發、睡眠）的核心機制其實是同一套哲學的三種表現——行為直接長出畫面、只給正回饋、一句話能講完、夜晚安靜留白的調性。合併成一個世界後，使用者對「一個地方」產生感情，而不是在三個 App 之間分散注意力，護城河（時間累積感）也更集中、更難被抄。
- **明確不做什麼：** 不宣稱醫療／心理治療效果、不做睡眠或情緒的醫療級診斷、不做評分量表、不做精準睡眠偵測、不做隨機抽獎式付費（塔羅抽牌也不例外）、不宣稱塔羅有真實占卜效果。這幾條紅線貫穿後面所有法律與文案決定。
- **純文字、不上圖片：** 所有使用者輸入（許願、告解、塔羅想問的問題）都只用文字，不開放上傳圖片。理由：貼合安靜留白的調性、繞開 Firebase Storage 免費方案的雷、大幅降低審核負擔。塔羅卡面也因此走幾何線條＋文字，不做插畫。

## 02 村落結構與場景動線

村落只有兩個實體區域，比原本三區域（家／樹／天空）更精簡：

| 區域 | 對應機制 | 主動作 | 累積的東西 |
|---|---|---|---|
| 家（主畫面 hub） | 睡眠養成＋塔羅式運勢 | 睡前按「睡了」／輸入今天想問的事再抽牌 | 屋子越住越溫馨、燈火越多 |
| 家門口的樹（子場景） | 許願池 | 許願／告解 | 樹隨心願長大、掛滿願望籤 |

天空不是獨立區域，而是家的背景層，靠真實天氣呈現（見第 03 節）。

**動線不是一鏡到底，而是以家為中樞：**

1. **打開 App → 停在家。** 這裡是每日運勢的入口，也是天氣看得到的地方。
2. **想許願／告解 → 走出去樹前。** 點擊後場景轉場到許願樹，完成儀式後可以選擇回家或留在原地看看。
3. **晚上 → 回到家。** 按「睡了」，熄燈入夜，一天結束。

家是 hub，樹是子場景，兩者不用擠在同一個畫面裡，轉場本身也可以是一個有儀式感的動畫（推門出去、走回家）。沒空的話，只做晚安打卡也完全成立——不強迫使用者三件事都做。

## 03 天氣：真實天氣＋語錄

天氣只有一個真相來源：**真實天氣**。不做使用者自選的「心情天氣」，避免兩層天氣互相打架、也少一套要拍板的規則。

- 串接手機定位或使用者設定城市的真實天氣 API，決定村落當下的光影與效果（晴朗／多雲／陣雨…）——這是唯一的視覺依據。
- 在家的畫面上，搭配一句**跟當下真實天氣呼應的語錄**（例如下雨天出現偏「沉澱」「安靜」語氣的句子），用文字傳達心情共鳴，而不是讓使用者自己選一個情緒圖示。使用者的「心情」不是自選出來的畫面，是天氣幫他說出來的一句話。
- 這句語錄跟第 04 節塔羅回應共用同一套「依天氣調語氣」的文案邏輯，不用另外做兩套系統。
- 陰雨天一樣要做得美、不能有懲罰感，這條原則延續原手冊。
- 定位僅用於天氣顯示，需在權限說明中清楚告知，並提供「手動選城市」取代定位的選項。

## 04 每日運勢：塔羅式，自由提問再抽牌

原手冊寫過「不做成塔羅牌等級的正式占卜」，理由是插畫成本高、跟「純文字不上圖」的調性衝突、神秘學色彩拉高審查風險。這版調整為：**保留塔羅的結構，卡面不做插畫，機制往「你可以主動問一件事」的方向做**，比單純每日固定一張牌更有目的性、更好玩。

### 機制

- **入口在家的畫面**：使用者輸入「今天想問的事」（自由文字），送出後抽一張牌，得到對應的回應。
- **卡面走幾何線條＋文字**，用 SVG 畫符號（太陽、星星、月亮…），延續「純文字、不上圖片」的精神，不用養插畫資產。
- **先做一組偏正向、不嚇人的牌**（例如：太陽／星星／月亮／力量／節制／世界），避開死神、高塔這類容易讓人覺得「抽到很衰」的牌——呼應「只給正回饋、不給罪惡感」的核心原則，就算問的事很沉重，抽到的牌本身也不該讓人覺得更糟。
- **卡片結構**：牌名／回應文字／一個正向關鍵字，回應會呼應使用者輸入的問題與當下的真實天氣。

### 安全與法律考量（比原本每日一牌更重，需要多想的地方）

自由輸入問題比固定每日一牌更像真的占卜，需要多幾條原本沒有的規則：

| 考量 | 做法 |
|---|---|
| 文案不能給出像「答案」的東西 | 回應走「反思提示」（例如「或許你其實已經有答案了」），不出現「會」「不會」「準」這類斷言字眼，避免踩到消保法／公平交易法的不實廣告紅線 |
| 使用者輸入的問題是自由文字 | 比照告解處理：預設完全私密、不公開、不審核；只有使用者主動選擇分享時才跑關鍵字過濾（判斷標準是「會不會被別人看到」，跟第 05 節原則一致） |
| 問題內容涉及自傷／自殺等關鍵字 | 不打斷書寫；等使用者完成、看到抽牌結果後，再溫和地把求助資源浮出來 |
| 使用者是「主動問問題」，更容易誤會這是真的在算命 | 開場或設定頁的「不宣稱真實占卜效果」聲明要比原本更顯眼 |
| 塔羅抽牌若走付費機制 | 絕對不能做成隨機付費抽卡，踩刑法賭博罪紅線——跟第 07 節「絕對不做」的原則一致 |

## 05 內容與安全設計（樹：許願／告解）

沿用原許願池手冊的原則：**私密書寫完全自由，公開分享才需要安全機制**。這條原則對樹的許願／告解、以及第 04 節塔羅的問題輸入都適用。

- **許願：** 分類模板（感情／事業／健康／財富／人際／其他）＋最多 20 字客製內容，預設會上公開心願牆，送出前跑基礎關鍵字過濾。
- **消災告解：** 私密自由書寫是預設狀態，不限字數、不審核；選擇公開分享時才進入安全層。
- **公開分享安全層（適用所有可公開的內容）：** 不開放留言／回覆、不做排行榜或熱門榜、公開內容延遲＋打散顯示、每人每日分享次數上限、發布前跑關鍵字過濾。參考 Secret、Whisper、Yik Yak 死於「匿名＋自由留言＋排名」的教訓。
- **常態求助資源入口：** App 內（設定頁＋適當時機）要有常態顯示的求助資源（如自殺防治專線），不能只靠關鍵字觸發才出現。
- **危機內容處理原則：** 書寫過程中偵測到自殺／自傷等關鍵字，不打斷、不即時攔截；等使用者完成當次書寫後，才溫和地把求助資源浮出來。這條原則對樹（告解）與塔羅（問題輸入）都適用。

## 06 法律風險備忘

以台灣為主的初步整理，**不是正式法律意見**，正式上線前建議找律師看過條款與文案。

| 風險 | 相關規範 | 因應方向 |
|---|---|---|
| 宣稱消災解厄／塔羅占卜真的有效 | 消保法／公平交易法（不實廣告） | 文案定位為情緒抒發與反思工具，不做效果宣稱；避免「準確」「會／不會」這類斷言字眼 |
| 隨機付費獎勵（塔羅抽卡、開運抽籤等） | 刑法賭博罪（射倖性要件） | 絕對不做，紅線項目 |
| 告解／塔羅問題內容洩漏他人身分細節 | 個人資料保護法 | 使用條款明訂不得張貼他人個資 |
| 未成年人課金 | 民法交易效力 | 條款需載明，留意 Store 既有機制 |
| 危機內容未妥善轉介 | 企業社會責任／潛在究責 | 常態放置求助資源入口，偵測到危機內容於書寫完成後主動浮出 |
| 使用者無法刪除自己的資料 | 個人資料保護法（當事人刪除請求權） | 資料表支援軟刪除，使用者可隨時刪除自己的願望、告解、塔羅提問紀錄 |
| 讀取真實天氣所需的定位權限 | 個資／APP 審查（位置權限說明） | 定位僅用於天氣顯示，需在權限說明中清楚告知，並提供「手動選城市」取代定位的選項 |

## 07 商業模式

沿用原手冊方案，塔羅化之後沒有改變：

- **核心循環永遠免費：** 睡前打卡、許願、塔羅提問抽牌，一律不設付費門檻。
- **香油錢＝村落共用貨幣：** 許願要花、也可以拿來買家的裝潢、樹的造型、塔羅卡面風格。獲取管道：每日簽到＋自願看激勵廣告，不能直接用真錢購買。
- **課金走獨立通道：** 低價（約 NT$10–30）用真錢直接購買外觀與特效——房子的裝潢、樹的造型、塔羅卡面風格，花費透明，不透過香油錢轉換。
- **訂閱制備案：** 去廣告＋無限額度（例如塔羅每日提問次數）＋專屬特效，作為主要營收。
- **廣告（若用）：** 自願／激勵式，不打斷任何儀式流程，類別排除博弈／酒類／借貸。
- **絕對不做：** 隨機／抽獎式付費獎勵（含塔羅付費抽卡），踩賭博法律紅線。

## 08 技術與平台

沿用原手冊評估，所有機制共用同一個 Godot 場景，不需要分開三個專案：

| 項目 | 免費？ | 開源？ | 備註 |
|---|---|---|---|
| Godot（遊戲引擎） | 是 | 是 | 3D voxel 風格，同專案可輸出網頁＋原生 App |
| Supabase（後台／資料庫） | 免費額度 | 核心開源 | 純文字資料幾乎用不完額度 |
| MagicaVoxel（建模） | 是 | 否 | 家、樹、塔羅卡面等 voxel／2D 資產 |
| 真實天氣 API | 通常有免費額度 | 視服務而定 | **現在是村落沉浸感的核心依賴，不是選配**——需要額外想好 API 故障或超額時的備援畫面（例如退回一個中性的預設天氣），避免天氣資料拿不到時主畫面壞掉 |
| Firebase | 免費額度 | 否 | 雷區：Spark 方案不能用 Cloud Storage，純文字資料不受影響 |
| AdMob | 免費（分潤制） | 否 | 需設定廣告類別過濾＋兒童導向合規設定 |
| Apple／Google 開發者帳號 | 否 | — | 上架必要成本 |

## 09 資料模型

**User**
- id / target_bedtime / currency_balance / location_or_city（真實天氣用，可用手動城市取代定位）/ created_at / deleted_at

**Wish**（樹）
- id / user_id / category / template_id / custom_text / is_public / status（許願中／已還願） / created_at / fulfilled_at / deleted_at

**Confession**（樹）
- id / user_id / private_content / share_publicly / shared_content / moderation_status / created_at / shared_at / unshared_at / deleted_at

**SleepEntry**（家）
- id / user_id / date / bedtime_at / wakeup_at / source（manual／health_data） / is_on_time / created_at / updated_at / deleted_at

**TarotDraw**（家，取代原「DailyFortune」）
- id / user_id / date
- question（使用者輸入的自由文字，預設私密）
- card（抽到的牌）
- response_text（反思提示回應，依 question＋當下天氣配對）
- keyword（正向關鍵字）
- weather_context（抽牌當下的真實天氣代碼，用於語氣配對）
- share_publicly / shared_content / moderation_status（僅分享時使用，比照 Confession）
- created_at / deleted_at

**Transaction**
- id / user_id / type（簽到／廣告／課金／花費） / amount / reference_id / created_at

**ShopItem**
- id / name / type（房屋裝潢／樹的造型／塔羅卡面風格／音效） / price / currency_type

**WorldState（村落整體狀態）**
- user_id / house_level（家的溫馨程度，由就寢達標累積推進） / tree_level（樹的茂密程度，由累積願望數推進） / unlocked_items / updated_at

**關鍵安全設計：**
- Confession、TarotDraw 的私密原文與公開分享版本分開存放。
- 刪除與撤回一律用軟刪除（`deleted_at`），不做實體刪除；使用者端呈現上完全不顯示。
- 公開內容要能連動下架：撤回分享或刪除時，公開版本必須同步從探索頁移除。

## 10 美術與場景設計

延續許願池原本的視覺語言（許願樹＋天燈夜景，避開真實廟宇聯想），家與塔羅卡面也統一進同一套調性。

### 色彩與字體

| 色票 | 色碼 |
|---|---|
| 靛夜 | #101A2E |
| 燈金 | #E8A94A |
| 翠玉 | #74AE8D |
| 火硃 | #C2653F |
| 紙白 | #F3EFE4 |

- **標題／場景標題：** Noto Serif TC（600/700）
- **內文／介面文字：** Noto Sans TC
- **數字（香油錢、字數）：** tabular-nums 對齊

### 場景

- **家：** 沿用睡眠養成的「越住越溫馨」邏輯——達標天數越多，窗戶燈光越暖、屋子裝飾越多、周圍多幾戶鄰居的燈。同一畫面上顯示真實天氣效果與塔羅提問入口。
- **樹：** 完整沿用許願池的生長系統——階段式樹體切換（4～5 階）＋願望籤動態掛載＋環境氛圍隨進度變化。獨立場景，從家轉場過去。
- **塔羅卡面：** 幾何線條＋文字，不做插畫，SVG 畫符號（太陽、星星、月亮等），配合抽卡動畫與音效營造儀式感。
- **家↔樹轉場：** 推門走出去、走回家的動畫，本身也是儀式感的一部分，不是單純的畫面切換。

## 11 待決事項

- 抽牌回應是純文案模板配對問題關鍵字，還是需要更聰明的比對邏輯？模板庫要多大才不會很快看膩或答非所問？
- 塔羅提問用量要不要限制（例如每日可以問幾次），避免變成使用者一直重複問同一件事，也避免內容審核負擔無限增加。
- 天氣語錄庫的規模，跟塔羅回應文案庫是否共用同一套內容系統。
- 家↔樹的轉場動畫規格，以及樹場景做完儀式後是自動回家還是使用者手動返回。
- 塔羅要做多少張牌（先 6 張正向牌驗證，還是直接做 22 張大阿爾克那）。
- 真實天氣 API 掛掉或超過免費額度時的備援畫面設計。
- 家與樹各自的成長門檻數字，沿用原案再依實測調整。
- 帳號模型：純裝置 ID 匿名 vs 輕量帳號備份，村落資料（願望史＋塔羅提問史＋就寢紀錄＋村落成長狀態）全部綁在一起，掉資料代價高，傾向優先做帳號備份。
- App Store／Google Play 審查風險的具體條款比對（類賭博、IAP 相關指引），塔羅提問功能上線前要再確認一次紅線。
