## 00 一分鐘看懂：我到底在做什麼

（給任何第一次接觸這個專案的人——包括未來的自己——的白話版）

**你在做一個手機 App，叫「小村落」。每個使用者都有一座自己的小村莊，好好過生活，村莊就會越來越美。**

具體來說，使用者打開 App 會看到一座小小的村落，裡面有兩樣東西：

- **一間家。** 晚上想睡了，就按一下「睡了」，家會熄燈入夜。越常準時睡，家的燈光越暖、裝飾越多、旁邊鄰居的燈也越亮。等於「你把自己照顧好，家就越住越溫馨」。
- **家門口一棵樹。** 想許願或想把煩惱說出來，就走到樹前面寫下來。每許一個願，樹就長大一點，掛上一盞願望籤。等於「你的心願，變成一棵慢慢長大的樹」。

天空不用另外做，直接抓**你所在城市的真實天氣**當背景——下雨天村落就在下雨，還會配一句呼應天氣的溫柔句子，像是天氣幫你把心情說出來。

**這個 App 的靈魂只有一句話：只給溫暖，不給壓力。** 漏睡一天不會被罵、不會扣分、畫面不會變醜。它不是要管你、逼你，而是一個你每天願意回來看一眼、待一下的地方。

**之後會長出兩個進階功能（不是一開始就做）：**
- **漂流瓶：** 你的願望可以飄給陌生人，別人讀到會回你一份祝福；你也會收到別人的願望，回他一份善意。一種安靜的、互相打氣的感覺。
- **塔羅提問：** 心裡有事，可以問一句話、抽一張牌，得到一段溫柔的反思提示（不是算命、不說「準不準」）。

**它不做什麼：** 不宣稱能治療或占卜、不做付費抽卡、不做留言區和排行榜。這些都是為了讓它一直是個安全、乾淨、沒有壓力的地方。

**技術上：** 用 Godot 這個免費遊戲引擎做，美術用 MagicaVoxel 做成方塊積木風（voxel），後台資料用 Supabase 存。整個 App 都是純文字，不讓使用者上傳圖片——這樣審核輕鬆、也貼合安靜的調性。

## 01 概念

- **核心體驗：** 使用者擁有一個自己的小村落。打開 App 先停在**家**，這裡是每日運勢的入口，也看得到外面真實的天氣；想許願或想放下什麼，就**走出去門口的樹**，完成許願或告解的儀式；晚上回到家，按「睡了」，熄燈入夜，結束一天。
- **一句話定位：** **「照顧好你的小村落——家越住越暖，樹越長越大，外面的天氣，說著你此刻的心情。」**
- **為什麼是村落，不是三個分開的 App：** 三個原方向（許願、情緒抒發、睡眠）的核心機制其實是同一套哲學的三種表現——行為直接長出畫面、只給正回饋、一句話能講完、夜晚安靜留白的調性。合併成一個世界後，使用者對「一個地方」產生感情，而不是在三個 App 之間分散注意力，護城河（時間累積感）也更集中、更難被抄。
- **明確不做什麼：** 不宣稱醫療／心理治療效果、不做睡眠或情緒的醫療級診斷、不做評分量表、不做精準睡眠偵測、不做隨機抽獎式付費（塔羅抽牌也不例外）、不宣稱塔羅有真實占卜效果。這幾條紅線貫穿後面所有法律與文案決定。
- **純文字、不上圖片：** 所有使用者輸入（許願、告解、塔羅想問的問題）都只用文字，不開放上傳圖片。理由：貼合安靜留白的調性、繞開 Firebase Storage 免費方案的雷、大幅降低審核負擔。塔羅卡面也因此走幾何線條＋文字，不做插畫。

## 01.5 MVP 與分階段規劃

合併成一個世界之後，最大的風險是「一開工就要同時做完所有東西」——公開分享的審核、塔羅文案系統、睡眠打卡、天氣串接全部壓在一起，會拖很久才上得了架。所以刻意分三階段，**先讓一個能上架的東西存在，再逐步長出社交與進階功能**。

### 分階段內容

| 階段 | 做什麼 | 為什麼放這裡 |
|---|---|---|
| **MVP** | 自己的村落：**家（睡前打卡）＋真實天氣背景＋樹（許願／告解，只有自己看得到）** | 單機體驗就成立、能上架、能驗證留存，幾乎沒有 UGC 審核負擔。天氣是家的背景層，技術成本低，一併做。 |
| **Phase 2** | **漂流瓶願望交換**（見第 05 節，A 版預設祝福）＋**塔羅提問**（見第 04 節，先 6 張正向牌） | 社交要有夠多人在用才好玩，先靠 MVP 累積使用者，Phase 2 開漂流瓶才有滿滿的願望在飄。塔羅的文案系統也留到這裡再養。 |
| **Phase 3** | 漂流瓶 B 版（祝福可加一句自由回話）＋塔羅擴充到 22 張大阿爾克那 | 自由文字＝騷擾／廣告風險，等社群穩定、營運機制成熟再開。 |

### 為什麼漂流瓶不放 MVP

漂流瓶要好玩的前提是「有夠多人在許願」。第一天上線只有零星使用者，系統飄不出足夠的別人的願望，體驗反而最差，會讓人以為功能壞掉。而且一旦開社交，配對分發、祝福統計、關鍵字過濾、檢舉機制、負面內容處理全都要一起做。先做穩單機村落，累積使用者，再開漂流瓶，一上線體驗就是好的。

### MVP 的紅線

MVP 階段樹的許願／告解**只有自己看得到，完全不做任何公開或分享**。這樣 MVP 完全沒有 UGC 對外曝光，審核負擔趨近於零，能最快跑完「從想法到上架」全流程。公開相關的過濾、檢舉機制全部留到 Phase 2 隨漂流瓶一起做。

## 02 村落結構與場景動線

村落只有兩個實體區域，比原本三區域（家／樹／天空）更精簡：

| 區域 | 對應機制 | 主動作 | 累積的東西 |
|---|---|---|---|
| 家（主畫面 hub） | 睡前打卡（MVP）＋塔羅提問（Phase 2） | 睡前按「睡了」／（Phase 2）輸入想問的事再抽牌 | 屋子越住越溫馨、燈火越多 |
| 家門口的樹（子場景） | 許願池 | 許願／告解 | 樹隨心願長大、掛滿願望籤 |

天空不是獨立區域，而是家的背景層，靠真實天氣呈現（見第 03 節）。

**動線不是一鏡到底，而是以家為中樞：**

1. **打開 App → 停在家。** 這裡是每日運勢的入口，也是天氣看得到的地方。
2. **想許願／告解 → 走出去樹前。** 點擊後場景轉場到許願樹，完成儀式後可以選擇回家或留在原地看看。
3. **晚上 → 回到家。** 按「睡了」，熄燈入夜，一天結束。

家是 hub，樹是子場景，兩者不用擠在同一個畫面裡，轉場本身也可以是一個有儀式感的動畫（推門出去、走回家）。沒空的話，只做晚安打卡也完全成立——不強迫使用者三件事都做。

## 02.5 陪伴體驗（讓村落不只是工具）

這幾個都是低成本、高情感的細節，是這類 App（Forest、Finch）留得住人的關鍵，不是可有可無的加分項。

### 冷啟動：新使用者的第一天（MVP 必做）

「一天的節奏」是寫給老使用者的。新使用者第一次打開 App，看到一個空蕩蕩、還沒長起來的村落，很容易覺得「這什麼都沒有」就走了——留存最脆弱的就是第一天。所以第一次打開要有一個**開場儀式**：

- 引導使用者做一個立即有回應的小動作，例如「種下第一棵樹」或「點亮家的第一盞燈」，讓他第一天就體驗到「我做了一件事、世界回應了我」。
- 開場同時完成：體驗定位說明＋免責聲明（不宣稱醫療／占卜效果）＋設定目標就寢時間。
- 第一天的村落不該是全空的——給一個有基礎溫度的起點（家已經有微光、樹已經是幼苗），讓人有東西可以「養大」，而不是從零的荒地開始。

### 純觀賞模式

什麼都不用做，只是看著自己的村落——燈籠飄、天氣變化、風吹葉、鄰居的燈火。這讓 App 從「工具」變成「一個能待著的地方」，是留存的隱形功臣。MVP 就該有。

### 回顧卡：「一年前的今天」

翻到很久以前的願望或就寢紀錄，自動生成一張回顧卡：「三個月前你許的這個願，實現了嗎？」「一年前的今天，你在這裡許下……」。這是這類 App 最天然、最戳心的**分享來源**——使用者會主動截圖分享「我一年前的願望實現了」。屬於 Phase 2（需要累積夠久的資料才有東西可回顧）。

### 聲音＋觸覺

投香油錢的「鏘」、熄燈入夜的音效、抽塔羅的沙沙聲，配合輕微震動。成本低、效果強的儀式感細節，MVP 就該有。

## 03 天氣：真實天氣＋語錄

天氣只有一個真相來源：**真實天氣**。不做使用者自選的「心情天氣」，避免兩層天氣互相打架、也少一套要拍板的規則。

- 串接手機定位或使用者設定城市的真實天氣 API，決定村落當下的光影與效果（晴朗／多雲／陣雨…）——這是唯一的視覺依據。
- 在家的畫面上，搭配一句**跟當下真實天氣呼應的語錄**（例如下雨天出現偏「沉澱」「安靜」語氣的句子），用文字傳達心情共鳴，而不是讓使用者自己選一個情緒圖示。使用者的「心情」不是自選出來的畫面，是天氣幫他說出來的一句話。
- 這句語錄跟第 04 節塔羅回應共用同一套「依天氣調語氣」的文案邏輯（不用另外做兩套系統）；但天氣語錄是 MVP 就要有的，塔羅是 Phase 2，所以 MVP 階段就得先獨立備好一套天氣語錄庫，不能等塔羅一起做。
- 陰雨天一樣要做得美、不能有懲罰感，這條原則延續原手冊。
- 定位僅用於天氣顯示，需在權限說明中清楚告知，並提供「手動選城市」取代定位的選項。

### 天氣拿不到時的備援（MVP 就要有）

天氣是打開 App 第一眼看到的東西，所以 API 掛掉或超過免費額度時，主畫面**絕對不能壞掉或空白**。備援規則：

- **API 失敗或無資料時**，村落自動退回一個**中性預設畫面**——柔和的黃昏／星空，不強調任何特定天氣。
- 這個備援畫面配一句**不提天氣的通用語錄**（例如偏「陪伴」「安靜待著」語氣的句子），使用者不會察覺是降級狀態。
- 只有天氣正常回來時，才切換到對應的天氣光影與語錄。
- 這條是 MVP 必做，不是選配——因為天氣是每個人每天必經的第一個畫面。

## 04 每日運勢：塔羅式，自由提問再抽牌

原手冊寫過「不做成塔羅牌等級的正式占卜」，理由是插畫成本高、跟「純文字不上圖」的調性衝突、神秘學色彩拉高審查風險。這版調整為：**保留塔羅的結構，卡面不做插畫，機制往「你可以主動問一件事」的方向做**，比單純每日固定一張牌更有目的性、更好玩。

### 機制

- **入口在家的畫面**：使用者輸入「今天想問的事」（自由文字），送出後抽一張牌，得到對應的回應。
- **卡面走幾何線條＋文字**，用 SVG 畫符號（太陽、星星、月亮…），延續「純文字、不上圖片」的精神，不用養插畫資產。
- **先做一組偏正向、不嚇人的牌**（例如：太陽／星星／月亮／力量／節制／世界），避開死神、高塔這類容易讓人覺得「抽到很衰」的牌——呼應「只給正回饋、不給罪惡感」的核心原則，就算問的事很沉重，抽到的牌本身也不該讓人覺得更糟。
- **卡片結構**：牌名／回應文字／一個正向關鍵字，回應會呼應使用者輸入的問題與當下的真實天氣。
- **提問次數：免費每天 1 次，訂閱無限。** 這個限制同時解決三件事——避免使用者一直重複問同一件事、控制內容審核負擔、也成為訂閱的誘因。跟第 07 節商業模式契合，不用等實測。

### 安全與法律考量（比原本每日一牌更重，需要多想的地方）

自由輸入問題比固定每日一牌更像真的占卜，需要多幾條原本沒有的規則：

| 考量 | 做法 |
|---|---|
| 文案不能給出像「答案」的東西 | 回應走「反思提示」（例如「或許你其實已經有答案了」），不出現「會」「不會」「準」這類斷言字眼，避免踩到消保法／公平交易法的不實廣告紅線 |
| 使用者輸入的問題是自由文字 | 塔羅提問**一律純私密、永遠不飄出去、不公開**——它是自己問自己的事，不進漂流瓶。因為永遠只有自己看得到，所以完全不需要審核／過濾 |
| 問題內容涉及自傷／自殺等關鍵字 | 不打斷書寫；等使用者完成、看到抽牌結果後，再溫和地把求助資源浮出來 |
| 使用者是「主動問問題」，更容易誤會這是真的在算命 | 開場或設定頁的「不宣稱真實占卜效果」聲明要比原本更顯眼 |
| 塔羅抽牌若走付費機制 | 絕對不能做成隨機付費抽卡，踩刑法賭博罪紅線——跟第 07 節「絕對不做」的原則一致 |

## 05 內容與安全設計（樹：許願／告解＋漂流瓶）

沿用原許願池手冊的原則：**私密書寫完全自由，公開才需要安全機制**。這條原則對樹的許願／告解、以及第 04 節塔羅的問題輸入都適用。

### 基本規則

- **許願：** 分類模板（感情／事業／健康／財富／人際／其他）＋最多 20 字客製內容。MVP 只給自己看；Phase 2 起可選擇「讓願望飄出去」進入漂流瓶（見下），送出前跑基礎關鍵字過濾。
- **消災告解：** 私密自由書寫是預設狀態，不限字數、不審核；選擇讓它飄出去時才進入安全層。
- **常態求助資源入口：** App 內（設定頁＋適當時機）要有常態顯示的求助資源（如自殺防治專線），不能只靠關鍵字觸發才出現。
- **危機內容處理原則：** 書寫過程中偵測到自殺／自傷等關鍵字，不打斷、不即時攔截；等使用者完成當次書寫後，才溫和地把求助資源浮出來。這條原則對樹（告解）與塔羅（問題輸入）都適用。

### 漂流瓶願望交換（Phase 2，取代傳統公開心願牆）

不做一整面攤開來滑的「公開心願牆」，改成**一對一、雙向的善意交換**——像收到一封漂流瓶：

- **收：** 每天最多收到少數幾個（例如 1～3 個）陌生人飄來的願望，一次只看一個，讀完可以送出一份祝福。
- **送：** 使用者自己選擇要不要讓某個願望飄出去；飄出去的願望會隨機、延遲地分發給其他人，自己也會收到別人回的祝福數（例如「今天有 3 個人為你的願望加油」）。
- **為什麼這樣設計更安全：** 沒有一整面牆可以滑，就沒有比較、沒有排行榜、沒有炎上、沒有酸民聚集的地方。一次只給你看一個願望，你只能給善意、給不了惡意。這正好避開了 Secret、Whisper、Yik Yak 死於「匿名＋自由留言＋排名」的教訓。

**祝福的形式，分階段開放：**

- **Phase 2（A 版）：只能送預設祝福。** 讀完別人的願望，從幾個固定選項點一個送出，例如「為你加油」「會實現的」「抱抱」。**完全沒有自由文字，就完全沒有審核問題、沒有任何人能傳惡意訊息給你。**
- **Phase 3（B 版）：預設祝福＋一句自由回話。** 等社群穩定、營運機制成熟後再開。一旦開放自由文字傳給特定的人，就有騷擾／廣告／惡意訊息風險，屆時必須配套：關鍵字過濾＋檢舉機制＋封鎖。

### 漂流瓶安全層（Phase 2 起，隨漂流瓶一起上）

- **願望文字本身要過濾：** 就算祝福只能點預設選項，別人的願望文字還是會被你看到，所以願望「飄出去」時就要跑一次關鍵字過濾。
- 不開放留言／回覆串、不做排行榜或熱門榜。
- 願望分發**延遲＋打散**，不即時、不可回溯到特定人。
- 每人每日「飄出願望」與「收到願望」都設上限。
- 提供**檢舉／不想再收到這類**的入口，收到讓人不舒服的願望時能一鍵略過並回報。

## 06 法律風險備忘

以台灣為主的初步整理，**不是正式法律意見**，正式上線前建議找律師看過條款與文案。

| 風險 | 相關規範 | 因應方向 |
|---|---|---|
| 宣稱消災解厄／塔羅占卜真的有效 | 消保法／公平交易法（不實廣告） | 文案定位為情緒抒發與反思工具，不做效果宣稱；避免「準確」「會／不會」這類斷言字眼 |
| 隨機付費獎勵（塔羅抽卡、開運抽籤等） | 刑法賭博罪（射倖性要件） | 絕對不做，紅線項目 |
| 告解／塔羅問題內容洩漏他人身分細節 | 個人資料保護法 | 使用條款明訂不得張貼他人個資 |
| 未成年人課金 | 民法交易效力 | 條款需載明，留意 Store 既有機制 |
| 危機內容未妥善轉介 | 企業社會責任／潛在究責 | 常態放置求助資源入口，偵測到危機內容於書寫完成後主動浮出 |
| 使用者無法刪除自己的資料 | 個人資料保護法（當事人刪除請求權） | 資料表支援軟刪除，使用者可隨時刪除自己的願望、告解、塔羅提問紀錄 |
| 讀取真實天氣所需的定位權限 | 個資／APP 審查（位置權限說明） | 定位僅用於天氣顯示，需在權限說明中清楚告知，並提供「手動選城市」取代定位的選項 |

## 07 商業模式

沿用原手冊方案，另補上塔羅提問與漂流瓶祝福的收費原則（見本節末）：

- **核心循環永遠免費：** 睡前打卡、許願、塔羅提問抽牌，一律不設付費門檻。
- **香油錢＝村落共用貨幣：** 許願要花、也可以拿來買家的裝潢、樹的造型、塔羅卡面風格。獲取管道：每日簽到＋自願看激勵廣告，不能直接用真錢購買。
- **課金走獨立通道：** 低價（約 NT$10–30）用真錢直接購買外觀與特效——房子的裝潢、樹的造型、塔羅卡面風格，花費透明，不透過香油錢轉換。
- **訂閱制備案：** 去廣告＋無限額度（例如塔羅每日提問次數）＋專屬特效，作為主要營收。
- **廣告（若用）：** 自願／激勵式，不打斷任何儀式流程，類別排除博弈／酒類／借貸。
- **絕對不做：** 隨機／抽獎式付費獎勵（含塔羅付費抽卡），踩賭博法律紅線。

### 香油錢經濟・初版建議數值（沿用許願池原案，待實測調整）

| 項目 | 建議值 | 備註 |
|---|---|---|
| 許 1 次願 | 100 香油錢 | 基準單位 |
| 消災告解 | 免費或 30 香油錢 | 傾向免費 |
| 每日簽到 | 100 香油錢 | 確保純免費玩家每天至少能許 1 次願 |
| 看 1 支激勵廣告 | 50 香油錢 | 看 2 支≈多許 1 次願 |
| 每日看廣告上限 | 4～6 支 | 防止刷廣告換願望 |

### 塔羅提問與漂流瓶祝福要不要花錢

- **塔羅提問：不花香油錢，用「每日次數」控管。** 免費每天 1 次，訂閱無限（見第 04 節）。理由：塔羅提問不做付費抽卡（賭博紅線），也不適合用香油錢當門檻（會讓人覺得「算命要收費」，拉高效果宣稱的法律風險），所以走純次數限制最乾淨。
- **漂流瓶送祝福：完全免費、不花香油錢、不設高門檻。** 送善意這件事不該有付費或消耗感，只用第 05 節的每日次數上限防濫用即可。

**DriftInbox**（漂流瓶，Phase 2）— 記錄「今天飄到我這裡、待我讀與祝福的別人的願望」
- id / user_id（收件人）/ source_wish_id / delivered_date / is_read / blessed_at / reported_at（檢舉時間）

**SleepEntry**（家）
- id / user_id / date / bedtime_at / wakeup_at / source（manual／health_data） / is_on_time / created_at / updated_at / deleted_at

**TarotDraw**（家，取代原「DailyFortune」）
- id / user_id / date
- question（使用者輸入的自由文字，預設私密）
- card（抽到的牌）
- response_text（反思提示回應，依 question＋當下天氣配對）
- keyword（正向關鍵字）
- weather_context（抽牌當下的真實天氣代碼，用於語氣配對）
- created_at / deleted_at
- （註：塔羅提問一律純私密，永遠不飄出去、不公開，所以沒有 is_drifting／分享相關欄位）

**Transaction**
- id / user_id / type（簽到／廣告／課金／花費） / amount / reference_id / created_at

**ShopItem**
- id / name / type（房屋裝潢／樹的造型／塔羅卡面風格／音效） / price / currency_type

**WorldState（村落整體狀態）**
- user_id / house_level（家的溫馨程度，由就寢達標累積推進） / tree_level（樹的茂密程度，由累積願望數推進） / unlocked_items / updated_at

**關鍵安全設計：**
- Confession 的私密原文與飄出去的版本分開存放（TarotDraw 永遠私密，無此問題）。
- 刪除與撤回一律用軟刪除（`deleted_at`），不做實體刪除；使用者端呈現上完全不顯示。
- 飄出去的內容要能連動下架：使用者收回或刪除願望／告解時，已分發到別人 DriftInbox 的版本必須同步移除（別人下次打開就看不到了）。
- 漂流瓶的分發是延遲＋隨機、不可回溯到特定人，避免任何人反查「這個願望是誰的」。

## 12 塔羅設計參考資料（外部研究整理）

整理自四篇塔羅教學文章，作為第 04 節「每日運勢」機制的設計參考，主要回應待決事項裡「牌卡要做多少張」與「回應文案怎麼寫」這兩個問題。這節是**參考資料**，不是已拍板的設計決定。

### 12.1 一副牌的完整結構（78 張）

- **大阿爾克那 22 張：** 代表大方向、關鍵性事件或人生課題（愚者、魔術師、女祭司…到世界）。
- **小阿爾克那 56 張，4 花色×14 張：**
  - 權杖（對應火元素）：熱情、行動、意志力
  - 聖杯（對應水元素）：情感、直覺、關係
  - 寶劍（對應風元素）：智力、邏輯、衝突、溝通（雙面刃，能幫人也能傷人）
  - 星幣（對應土元素）：金錢、安全感、穩定、長期未來
- 每張牌都有一組正位關鍵字＋一組逆位關鍵字。

**對照現行方案：** 第 04 節先做的 6 張正向牌（太陽／星星／月亮／力量／節制／世界）全部屬於大阿爾克那裡評價偏正面的牌，跳過死神、高塔、惡魔這類容易讓人覺得「抽到很衰」的牌，方向上跟「只給正回饋」的核心原則一致。

**若日後要擴充，建議順序：** 先擴到大阿爾克那全 22 張，再考慮小阿爾克那。理由是大阿爾克那本來就偏向大方向的人生課題，比較貼合「每日一問」的調性；小阿爾克那較細瑣、也多達 56 張，比較適合留給多張牌陣或訂閱限定的進階功能（見 12.3）。

### 12.2 牌義寫法參考

每張牌用「正位」「逆位」兩組關鍵字表達，例如：太陽 正位＝幸福、成功、樂觀、活力；逆位＝幸福受阻、過度熱情、悲觀、不切實際。

現行機制只做正向牌，等於是**只用正位語意、不判斷逆位**，可以刻意維持這個簡化——之後真的要擴充到 22 張大阿爾克那時，再決定要不要引入逆位（引入逆位代表要多寫一倍的文案，也代表要處理「抽到死神逆位」這類負面牌義怎麼包裝成不嚇人的回應）。

### 12.3 若未來做多張牌陣：可直接參考的結構與整合邏輯

現行機制是「問一句話→抽一張牌→給一段反思回應」，屬於單張牌形式。若之後想做進階的「多張牌」版本（例如訂閱限定功能），這裡有現成的設計語言可以參考：

**常見三張牌陣結構：**

| 牌陣 | 第1張 | 第2張 | 第3張 | 適合問題 |
|---|---|---|---|---|
| 時間軸型 | 過去影響 | 現在狀態 | 未來傾向 | 事情怎麼發展 |
| 行動型 | 目前情境 | 主要阻礙 | 可行建議 | 我該怎麼做 |
| 選擇型 | 選項A | 選項B | 評估重點 | 比較兩條路 |
| 內外型 | 表層想法 | 內在驅動 | 外在表現 | 理解情緒/關係互動 |

**多張牌之間的四種關係**（用來把多張牌串成一段回應，而不是各自獨立的三段文字）：
- **支持／延續：** 方向相近，後一張延續或放大前一張
- **拉扯／對立：** 方向衝突，代表內外需求還不一致
- **因果／回應：** 後一張像是回應前一張帶出的課題
- **轉折／修正：** 方向明顯改變，帶出新的選擇或方法

**整合公式（可以直接當成多牌回應的文案骨架）：**
> 目前＿＿＿（第一張），真正需要處理的是＿＿＿（第二張）；如果願意＿＿＿（第三張），事情較可能朝＿＿＿發展。

這個「先給結論、不出現斷言字眼」的寫法，跟第 04 節現行「回應走反思提示，不說會／不會／準」的原則相容，之後做多牌版本可以直接沿用同一套文案邏輯，不用另外設計一套。

## 13 製作流程：從現在做到上架

給第一次要動手的人的路線圖。原則跟三份原始手冊一致——**先讓一個能上架的東西存在，再逐步長功能**，不要一次全做。每個階段結束都該是「能給人用、能截圖、能上架」的狀態。

### 階段 0：開工前先拍板（不寫程式，1～2 天）

先把「開工前必須拍板」那幾件事定下來（見第 11 節 A 組），免得做到一半打掉重練：

1. 帳號要用什麼登入方式（建議 Supabase Auth，先支援匿名試用，之後可綁 Email／第三方登入升級）。
2. 註冊一個真實天氣 API（例如 OpenWeatherMap 免費方案），確認免費額度與請求頻率限制，只取天氣代碼即可。
3. 申請 Apple／Google 開發者帳號（要錢、要審核時間，越早辦越好，別卡在最後一步）。

### 階段 1：做出 MVP（自己的村落）

目標：一個人能養一座只有自己看得到的村落，能上架。順序建議由內而外：

1. **搭骨架先跑起來** — 用 Godot 開一個空場景，放一個最陽春的「家」和「樹」（先用灰盒佔位，美術後面再換），確認 App 能開、能點。
2. **接後台** — 接 Supabase，做好 User／Wish／Confession／SleepEntry／WorldState 這幾張表，確認資料存得進、讀得出。
3. **做睡前打卡** — 按「睡了」→ 記一筆 SleepEntry → 家熄燈入夜的動畫 → 隔天家的溫暖度依累積達標天數推進。這是最核心、最單純的循環，先讓它完整。
4. **做許願／告解** — 走到樹前 → 選分類或自由書寫 → 儀式動畫 → 樹長大、掛願望籤。此階段**只存自己看**，完全不做任何對外分享。
5. **接真實天氣＋語錄＋備援** — 抓天氣代碼決定村落光影，配語錄；同時做好第 03 節的備援畫面（天氣拿不到就退回中性黃昏／星空）。
6. **補冷啟動＋陪伴細節** — 新使用者第一天的開場儀式（種第一棵樹／點第一盞燈）、純觀賞模式、聲音＋觸覺（見第 02.5 節）。
7. **補必要的合規頁** — 免責聲明、隱私與定位權限說明、常態求助資源入口、設定頁、資料刪除功能。
8. **換上正式美術** — 把灰盒佔位換成 MagicaVoxel 做好的家、樹、燈籠等資產（見第 14 節）。
9. **上架** — 打包送審 App Store／Google Play，跑完整個審查流程。**這一步的經驗最寶貴，越早跑越好。**

### 階段 2：加漂流瓶 + 塔羅

MVP 上線、累積了一批天天在許願的使用者之後再做：

1. **漂流瓶（A 版）** — 加 BlessingReceived／DriftInbox 兩張表，做「願望飄出去→延遲隨機分發→別人讀到回預設祝福→我收到祝福數」的循環，配上關鍵字過濾與檢舉入口（見第 05 節）。
2. **塔羅提問** — 先做 6 張正向牌，做「輸入問題→抽牌→依問題＋天氣配對出反思提示回應」，每天免費 1 次。
3. **回顧卡** — 這時資料累積夠久了，做「一年前的今天／三個月前的願望實現了嗎」的回顧卡，當自然分享點。

### 階段 3：進階與變現深化

1. 漂流瓶 B 版（祝福可加一句自由回話）＋配套的審核／檢舉／封鎖。
2. 塔羅擴充到 22 張大阿爾克那，考慮訂閱限定的多張牌陣。
3. 訂閱制、商店外觀課金上線。

### 一句話總結流程

先做「一個人的村落」做到能上架 → 累積使用者 → 再開「人與人之間的漂流瓶」和「塔羅」→ 最後才做進階與深度變現。

## 14 美術與場景製作建議（MagicaVoxel 導向）

你打算用 MagicaVoxel 做 voxel（方塊積木風）資產，這跟整個 App「安靜、溫暖、不擬真」的調性很搭。這節是給實際動手做美術的具體建議。

### 為什麼 voxel 風格很適合這個專案

- **做得快、好統一。** 方塊積木風不需要精細的貼圖和高模，一個人也能在合理時間內把家、樹、燈籠全做完，而且天生就風格一致。
- **溫暖不擬真，剛好避開恐怖谷。** 這個 App 要的是「療癒」，voxel 的圓潤方塊感比寫實風更容易做出可愛、安心的感覺。
- **檔案小、跑得動。** voxel 模型面數低，手機上跑起來輕鬆，載入也快。

### 統一規範（動手前先定，之後省很多事）

- **色票鎖死。** 全部資產只用第 10 節那五個色（靛夜 #101A2E／燈金 #E8A94A／翠玉 #74AE8D／火硃 #C2653F／紙白 #F3EFE4）＋少數過渡色。MagicaVoxel 建議把這套色票存成 palette 檔，每個模型都套同一份，畫面才會像出自同一個世界。
- **統一體素密度。** 先定好「1 公尺＝幾個方塊」，家、樹、鄰居房子都照同一個密度做，不然擺在一起會有的粗有的細。
- **光靠氛圍，不靠寫實。** 這個 App 的重點是燈火、黃昏、星空這種「光的溫度」。voxel 本身不用做很細，靠 Godot 裡的燈光、發光材質、粒子（螢火、燈籠光點）去營造氣氛，比把模型做很精細更有效。

### 各場景的美術重點

- **家：** 做**一個基礎屋子 + 多層可疊加的裝飾件**（暖光窗戶、掛飾、煙囪的煙、門口小燈…）。溫暖度升級不是換一整棟新房子，而是逐件點亮／加上裝飾，這樣升級感是連續的、成本也低。鄰居的房子可以用同一棟屋子改色重複擺，遠處點幾盞燈就有村落感。
- **樹：** 這是情感核心，值得多花力氣。做 **4～5 個生長階段的樹體**（幼苗→小樹→成樹→茂盛→開花／掛滿籤），階段之間切換要有一個「長大」的過渡動畫或粒子效果，不要硬切。願望籤做成小掛牌／天燈，能一盞盞掛上去。
- **天空／天氣：** 天空不做成 voxel 模型，用 Godot 的背景漸層 + 光照 + 粒子（雨、雪、星點、飄雲）呈現。做**一套天氣狀態**（晴／多雲／雨／夜／備援用的中性黃昏），每種都調到「就算是陰雨也很美、沒有懲罰感」。
- **塔羅卡面（Phase 2）：** 不做 voxel、不做插畫。用 SVG／幾何線條畫符號（太陽、星星、月亮），純文字排版，配抽卡動畫與沙沙音效。這是刻意跟 voxel 世界做出區隔的「儀式物件」。

### 給一個人做美術的務實建議

- **先做灰盒佔位、程式先跑通，最後才換正式模型。** 別一開始就雕美術，先確認機制對了。
- **資產分「基礎件＋裝飾件」，不要做「完成品」。** 這樣升級系統才能一件件疊加，而不是每個等級都重做一整套。
- **氣氛的錢花在燈光和粒子上，不是花在模型精度上。** 這是這類療癒 App 投報率最高的地方。

## 15 成長門檻與美術資產清單（初版方案，待實測調整）

這節把「家要幾個溫暖等級、樹要幾個生長階段」的具體數字定出來（回應第 11 節 B 組的待決事項），再依這些等級列出 MVP 要做的 MagicaVoxel 資產。**數字是初版、可調**，重點是先有個能開工的基準，實測後再依真實留存曲線調整。

### 設計原則：前期快、後期慢

升級節奏要「**一開始很快就有回饋，越到後面越慢**」。理由：新使用者最脆弱是頭幾天，前面幾級門檻要低（第一次打卡、第二天就升級），讓人馬上感覺「我的村落有在變」；後面拉長，才有長期養成的空間。**漏做一天絕不倒退、不扣等級**——這是全 App 的紅線，成長只會前進或停住，永遠不退。

### 家的溫暖度（house_level）— 靠「累積準時就寢天數」推進

| 等級 | 累積準時天數 | 畫面變化 |
|---|---|---|
| Lv.0 | 0（新使用者） | 家有微光，冷清但不荒涼（冷啟動起點） |
| Lv.1 | 1 天 | 窗戶亮起暖光（第一次打卡就升級，立刻有回饋） |
| Lv.2 | 3 天 | 門口點一盞小燈、加一件掛飾 |
| Lv.3 | 7 天 | 煙囪冒煙、屋內更暖、多一件裝飾 |
| Lv.4 | 14 天 | 旁邊出現第一戶鄰居的燈 |
| Lv.5 | 30 天 | 鄰居變多，村落夜景成形 |
| Lv.6+ | 之後每 30 天 | 持續增加鄰居燈火／季節性小裝飾，無上限、越來越慢 |

- 「準時」的判定沿用 SleepEntry 的 `is_on_time`（打卡時間 vs 目標就寢時間）。
- 累積的是**總達標天數**，不是連續天數——不做「斷 streak」那套，漏一天只是那天沒 +1，不倒退。

### 樹的生長階段（tree_level）— 靠「累積許願數」推進

| 階段 | 累積願望數 | 樹的樣子 |
|---|---|---|
| 幼苗 | 0～1 | 剛冒出的小芽（冷啟動時「種下第一棵樹」就在這） |
| 小樹 | 2 | 有主幹和幾片葉（許第 2 個願就升，快速回饋） |
| 成樹 | 5 | 樹冠成形，開始能掛願望籤 |
| 茂盛 | 12 | 枝葉繁密，掛滿多盞願望籤 |
| 開花 | 25 | 開花／掛天燈，最華麗的完成態 |
| 開花+ | 之後每 15 個願 | 花況／光點持續豐富，無上限、越來越慢 |

- 願望籤（掛牌／天燈）是**每許一個願就掛一盞**，跟階段分開算——就算樹到頂了，籤還是會一盞盞增加，讓「我許過很多願」看得見。
- 告解不推進樹的等級（告解是「放下」，不是「許願」），但可以有自己的小視覺回饋（例如樹下飄走一點光）。

### MVP 要做的 MagicaVoxel 資產清單

依上面的等級，MVP（階段 1）需要這些。**全部遵守第 14 節的統一色票與體素密度。**

**家（基礎件 + 可疊加裝飾件，不做整棟替換）**
- 基礎屋子 ×1（Lv.0 的樣子，之後靠疊裝飾升級）
- 暖光窗戶件 ×1（Lv.1 疊上去）
- 門口小燈 ×1、掛飾 ×2～3 種（Lv.2～3 陸續疊）
- 煙囪煙效（用粒子做，非模型）
- 鄰居房子 ×1（用基礎屋改色重複擺，Lv.4 起放遠處）

**樹（5 個生長階段 + 願望籤）**
- 樹體 ×5（幼苗／小樹／成樹／茂盛／開花，各一個 voxel 模型）
- 願望籤掛牌／天燈 ×1～2 種（能重複掛載）
- 階段切換的過渡粒子（發光／葉子飄動，用 Godot 做）

**天氣（不做 voxel，Godot 的光照＋粒子＋背景漸層）**
- 天氣狀態 ×5：晴／多雲／雨／夜／備援中性黃昏
- 粒子：雨滴、星點、飄雲（雪可留到後面）

**共用氛圍件**
- 燈籠／螢火光點（點綴用，成本低效果強）
- 香油錢投入的「鏘」音效 + 熄燈入夜音效 + 輕微震動（見第 02.5 節）

**MVP 不用做的**（留到 Phase 2）：塔羅卡面 SVG、漂流瓶相關 UI、商店外觀件、回顧卡版型。

### 一句話總結

家看「準時睡了幾天」、樹看「許了幾個願」，兩者都是前期升得快、後期升得慢、漏做不倒退。美術照這些等級做，家用「基礎屋＋疊裝飾」、樹做 5 個階段，天氣全部交給 Godot 的光和粒子，別花時間雕模型細節。

## 16 這份做得到嗎？給不會寫程式的人的可行性與學習路線

老實話先講：**做得到，但這不是一個週末能搞定的東西，要有「幾個月、邊做邊學」的心理準備。** 好消息是——我們刻意把 MVP 切得很小，所以你的第一個可上架版本，用到的全是「有標準教學、有明確答案」的入門題，不是需要天才才能解的難題。

### 各部分的真實難度

| 部分 | 難度 | 說明 |
|---|---|---|
| 睡前打卡 | ★ 很簡單 | 本質是「記一個時間、跟目標時間比一下、存起來」，全 App 最簡單的功能 |
| 許願／告解（存自己看） | ★ 很簡單 | 寫一段文字→存資料庫→列出來給自己看，標準的增刪查改 |
| 接 Supabase 存資料 | ★★ 不難 | Supabase 對新手友善，官方教學多，等於填好設定、呼叫現成函式 |
| 接真實天氣 API | ★★ 需學但資源多 | 「跟一個網址要資料、拿天氣代碼來用」，卡點在第一次串 API 的觀念 |
| Godot 場景與動畫 | ★★ 需學但資源多 | 熄燈、樹長大、轉場，Godot 有完整中文教學，voxel 也是熱門題材 |
| 上架 App Store／Google Play | ★★★ 繁瑣不難 | 技術含量不高但雜事多（憑證、打包、審查表單、退件重改），第一次最容易卡在這 |
| 漂流瓶（Phase 2） | ★★★★ 最難 | 願望隨機分發／延遲／防濫用——**但這是 Phase 2，MVP 完全不用碰** |

**重點：MVP 只用到上面前五項（都是 ★～★★），最難的漂流瓶排在後面。這就是把 MVP 切小的價值。**

### 不會寫程式，怎麼開始？

你現在的處境比想像中好：

1. **你已經有一份完整設計文件。** 大部分人卡在「不知道要做什麼」，你跨過這關了。你不是要「學會寫程式」，你是要「學會做出第 13 節那九個步驟」，範圍小很多。
2. **可以先做網頁版驗證，不用一開始就碰上架。** Godot 能直接輸出成網頁。先做一個「瀏覽器打開就能玩的村落」，自己玩、給朋友玩，確認點子有人喜歡，之後再處理上架那些繁瑣的事。這樣最快看到成果、最不容易半途放棄。
3. **一步一步來，不要看「整份」。** 你不會一次做完整份，你會先做第 13 節階段 1 的第一步：開一個 Godot 場景、放一個方塊小房子、能點一下就熄燈。做出這一個，你就會知道「我做得到」，後面自然接得上。

### 新手學習路線（對應第 13 節階段 1，由易到難）

| 步驟 | 要學什麼 | 難度 | 建議 |
|---|---|---|---|
| 1 | 裝 Godot、開一個場景、放物件、能點擊互動 | ★ | 從官方或中文入門教學開始，先做出「點一下有反應」 |
| 2 | Godot 基礎腳本（GDScript），做「按睡了→畫面變暗」 | ★★ | GDScript 很好上手，語法接近 Python |
| 3 | 接 Supabase，把打卡紀錄存上去、讀回來 | ★★ | 跟著 Supabase 官方教學做一次就懂 |
| 4 | 做許願／告解的寫入與列表 | ★★ | 跟步驟 3 同一套邏輯，練熟就好 |
| 5 | 接天氣 API，用回傳的天氣代碼切換畫面 | ★★ | 學會「呼叫 API、解析回傳」這個通用技能 |
| 6 | 做動畫與粒子（熄燈、樹長大、螢火） | ★★ | Godot 的動畫系統，靠教學＋多試 |
| 7 | 用 MagicaVoxel 做美術、匯入 Godot | ★★ | 美術與程式分開學，不衝突 |
| 8 | 輸出網頁版自己玩 → 之後再學上架 | ★★★ | 網頁版先驗證，上架留到最後 |

### 我能幫你的

你不用自己從零讀教學、獨自除錯。我們可以**一步一步配合**：

- 你要做哪一步，我就教那一塊怎麼寫、帶著你寫。
- 你貼錯誤訊息給我，我幫你找問題、解釋為什麼錯。
- 你負責理解和做決定，我負責寫碼、解釋、除錯。

**下一步建議：** 從學習路線的步驟 1 開始——裝好 Godot、開第一個場景、放一個方塊房子、點一下讓它有反應。做出這一個小東西，就正式開始了。
