# 小村落設計手冊

把「許願池／情緒天氣／睡眠養成」三個原方向合併成一個世界的設計，整理成一份完整文件。

## 00 一分鐘看懂：我到底在做什麼

（給任何第一次接觸這個專案的人——包括未來的自己——的白話版）

**你在做一個手機 App，叫「小村落」。每個使用者都有一座自己的小村莊，好好過生活，村莊就會越來越美。**

具體來說，使用者打開 App 會看到一座小小的村落，裡面有兩樣東西：

- **一間家。** 晚上想睡了，就按一下「睡了」，家會熄燈入夜。越常準時睡，家的燈光越暖、裝飾越多、旁邊鄰居的燈也越亮。等於「你把自己照顧好，家就越住越溫馨」。
- **家門口一棵樹。** 想許願或想把煩惱說出來，就走到樹前面寫下來。每許一個願，樹就長大一點，掛上一塊願望牌（voxel 做的小木牌，掛在枝上），牌掛滿幾天後會被風吹走，像心願被送出去。等於「你的心願，變成一棵慢慢長大的樹」。
- **抬頭望向星空，問塔羅。** 心裡有事，可以問一句話、從一片 voxel 牌海抽一張牌，得到一段溫柔的反思提示（不是算命、不說「準不準」）。**這是吸引使用者的核心功能之一，第一版上線就有**，不是後面才加的東西。

天空不用另外做，直接抓**你所在城市的真實天氣**當背景——下雨天村落就在下雨，還會配一句呼應天氣的溫柔句子，像是天氣幫你把心情說出來。

**每次打開，還有一個安靜的開場**：村落上方浮現今天的日期，下方一句話像流星一樣劃過、寫出來、停幾秒、再化成光點飄散消失。這句話會依當下的天氣和節日不同（情人節有情人節的話），而且**看過就沒了、下次開又是新的一句**——刻意的，要那種「珍惜當下這一眼」的感覺。

**這個 App 的靈魂只有一句話：只給溫暖，不給壓力。** 漏睡一天不會被罵、不會扣分、畫面不會變醜。它不是要管你、逼你，而是一個你每天願意回來看一眼、待一下的地方。

**之後（累積使用者穩定後）會再長出一個進階功能：**
- **漂流瓶：** 你的願望可以飄給陌生人，別人讀到會回你一份祝福；你也會收到別人的願望，回他一份善意。一種安靜的、互相打氣的感覺。

**它不做什麼：** 不宣稱能治療或占卜、不做付費抽卡、不做留言區和排行榜。這些都是為了讓它一直是個安全、乾淨、沒有壓力的地方。

**技術上：** 用 Godot 這個免費遊戲引擎做，美術用 MagicaVoxel 做成方塊積木風（voxel），後台資料用 Supabase 存。整個 App 都是純文字，不讓使用者上傳圖片——這樣審核輕鬆、也貼合安靜的調性。

## 01 概念

- **核心體驗：** 使用者擁有一個自己的小村落。打開 App 先停在**家**，看得到外面真實的天氣；想許願或想放下什麼，就**走出去門口的樹**，完成許願或告解的儀式；心裡有事，**抬頭望向星空**抽塔羅、問一件心裡的事（第一版就有，是主要拉新賣點）；晚上回到家，按「睡了」，熄燈入夜，結束一天。
- **一句話定位：** **「照顧好你的小村落——家越住越暖，樹越長越大，抬頭的夜空，陪你問一件心裡的事。」**
- **為什麼是村落，不是三個分開的 App：** 三個原方向（許願、情緒抒發、睡眠）的核心機制其實是同一套哲學的三種表現——行為直接長出畫面、只給正回饋、一句話能講完、夜晚安靜留白的調性。合併成一個世界後，使用者對「一個地方」產生感情，而不是在三個 App 之間分散注意力，護城河（時間累積感）也更集中、更難被抄。
- **明確不做什麼：** 不宣稱醫療／心理治療效果、不做睡眠或情緒的醫療級診斷、不做評分量表、不做精準睡眠偵測、不做隨機抽獎式付費（塔羅抽牌也不例外）、不宣稱塔羅有真實占卜效果、**不做留言／回覆、不做排行榜或熱門榜**（這是漂流瓶避免變炎上戰場的核心紅線）。這幾條貫穿後面所有法律與文案決定。
- **純文字、不上圖片：** 所有使用者輸入（許願、告解、塔羅想問的問題）都只用文字，不開放上傳圖片。理由：貼合安靜留白的調性、繞開 Firebase Storage 免費方案的雷、大幅降低審核負擔。塔羅牌面走 voxel 拼出的簡單符號，不做插畫。

## 01.5 MVP 與分階段規劃

合併成一個世界之後，最大的風險是「一開工就要同時做完所有東西」——公開分享的審核、塔羅文案系統、睡眠打卡、天氣串接全部壓在一起，會拖很久才上得了架。所以刻意分三階段，**先讓一個能上架的東西存在，再逐步長出社交與進階功能**。

> 📌 **塔羅提早進 MVP：** 塔羅提問是主要拉新賣點，第一批下載的人就該看到它，所以塔羅不等 Phase 2，直接排進 MVP。這樣調整不影響「MVP 零 UGC 審核負擔」的原則——塔羅問題一律純私密、永遠不飄出去（見第 04 節），本來就沒有社交曝光風險，跟漂流瓶完全不是同一種東西，可以放心提早做。真正需要「先累積使用者」才好玩的只有漂流瓶。

### 分階段內容

| 階段 | 做什麼 | 為什麼放這裡 |
|---|---|---|
| **MVP** | 自己的村落：**家（睡前打卡）＋真實天氣背景＋樹（許願／告解，只有自己看得到）＋塔羅提問**（見第 04 節，先 6 張正向牌） | 單機體驗就成立、能上架、能驗證留存，幾乎沒有 UGC 審核負擔。天氣是家的背景層、塔羅問題永遠私密，技術與審核成本都低，一併做；塔羅同時是主要拉新賣點，不宜延後。 |
| **Phase 2** | **漂流瓶願望交換**（見第 05 節，A 版預設祝福）＋**回顧卡**（見第 02.5 節） | 社交要有夠多人在用才好玩，先靠 MVP 累積使用者，Phase 2 開漂流瓶才有滿滿的願望在飄；回顧卡也要累積夠久的資料才有東西可回顧。 |
| **Phase 3** | 漂流瓶 B 版（祝福可加一句自由回話）＋塔羅擴充到 22 張大阿爾克那與真正的多張牌陣 | 自由文字＝騷擾／廣告風險，等社群穩定、營運機制成熟再開；塔羅牌數與牌陣擴充則是內容量與互動複雜度都較高，留到穩定後再加。 |

### 為什麼漂流瓶不放 MVP

漂流瓶要好玩的前提是「有夠多人在許願」。第一天上線只有零星使用者，系統飄不出足夠的別人的願望，體驗反而最差，會讓人以為功能壞掉。而且一旦開社交，配對分發、祝福統計、關鍵字過濾、檢舉機制、負面內容處理全都要一起做。先做穩單機村落，累積使用者，再開漂流瓶，一上線體驗就是好的。

### MVP 的紅線

MVP 階段樹的許願／告解**只有自己看得到，完全不做任何公開或分享**；塔羅問題也是永遠私密、不飄出去。這樣 MVP 完全沒有 UGC 對外曝光，審核負擔趨近於零，能最快跑完「從想法到上架」全流程。公開相關的過濾、檢舉機制全部留到 Phase 2 隨漂流瓶一起做。

## 02 村落結構與場景動線

**地面層是同一個連續的平面場景，不是切換讀取的獨立場景。** 家跟門口的樹放在同一片地面上（像一個小庭院的兩端），點樹就是鏡頭平移過去，不是「離開家的場景、進入樹的場景」。這是刻意的技術決定：比起做一顆能滑動旋轉的圓形小星球（地形彎曲、鏡頭繞著轉、物件要貼合弧面），同一片平面＋鏡頭平移對 AI 來說是同一套場景與攝影機邏輯，難度不會拉高，跟第 17 節可行性表的評級一致；圓形星球那個方向做起來會漂亮，但複雜很多，先不做。

| 區域 | 對應機制 | 主動作 | 累積的東西 |
|---|---|---|---|
| 家（地面世界的一端） | 睡前打卡＋塔羅提問（皆 MVP） | 睡前按「睡了」／抬頭望向星空抽牌 | 屋子越住越溫馨、燈火越多 |
| 門口的樹（同一片地面，鏡頭平移過去） | 許願／告解 | 許願／告解 | 樹隨心願長大、掛滿願望牌 |

天空不是獨立區域，而是家的背景層，靠真實天氣呈現（見第 03 節）。

**動線不是一鏡到底，而是以家為中樞：**

1. **打開 App → 停在家前。** 看得到當下的真實天氣與呼應的語錄，還有每次打開才有的日期＋流星語錄開場。
2. **想許願／告解 → 點樹，鏡頭平移過去。** 同一片地面、同一場天氣，沒有讀取轉場；走到樹下完成儀式後，點回家、鏡頭再平移回去。
3. **想問塔羅 → 抬頭望向星空。** 這是唯一真正的「轉場」——抽牌夜空是脫離地面的專屬星空，固定不跟著真實天氣變，用「抬頭、畫面上抬淡出」帶過去，跟平面上的鏡頭平移是兩種不同的心理切換（見第 04 節）。
4. **晚上 → 回到家前。** 按「睡了」，熄燈入夜，一天結束。

家跟樹共用同一片地面、同一套光影，鏡頭平移本身就有走過去的儀式感，不需要額外做場景轉場動畫；抽牌夜空則保留單獨的「抬頭」轉場，因為那是刻意做出「離開地面、進入星空」的感覺。沒空的話，只做晚安打卡也完全成立——不強迫使用者三件事都做。

## 02.5 陪伴體驗（讓村落不只是工具）

這幾個都是低成本、高情感的細節，是這類 App（Forest、Finch）留得住人的關鍵，不是可有可無的加分項。

### 冷啟動：新使用者的第一天（MVP 必做）

「一天的節奏」是寫給老使用者的。新使用者第一次打開 App，看到一個空蕩蕩、還沒長起來的村落，很容易覺得「這什麼都沒有」就走了——留存最脆弱的就是第一天。所以第一次打開要有一個**開場儀式**：

- 引導使用者做一個立即有回應的小動作，例如「種下第一棵樹」或「點亮家的第一盞燈」，讓他第一天就體驗到「我做了一件事、世界回應了我」。
- 開場同時完成：體驗定位說明＋免責聲明（不宣稱醫療／占卜效果）＋設定目標就寢時間。
- 第一天的村落不該是全空的——給一個有基礎溫度的起點（家已經有微光、樹已經是幼苗），讓人有東西可以「養大」，而不是從零的荒地開始。

### 每日開場：日期 ＋ 流星語錄（MVP 必做）

每次打開 App，先有一個安靜的開場——**上方是穩定的日期，下方是一句如流星般短暫的語錄**。一穩一動，對比之下更有「珍惜這一刻」的感覺。

**畫面呈現（介面設計）：**

- **場景**：打開 App，鏡頭停在你的村落（家＋樹），天色是清晨微光。開場的一切都疊在你自己的村落上，不是另開一張卡——日期與語錄是「長在村落裡」的。
- **日期（穩定、發光的 voxel 立體大字）**：村落上方的晨空浮現當天日期。主角是大大的「幾號」數字（voxel 立體、燈金色微微發光，像貼圖那張的大數字「3」），上方小字是月份英文（November）＋年份，另一側是星期（星期五）。日期是「今天」的錨，天天都在、給人安定感。
- **語錄（流星般浮現→飄散）**：日期下方，一道微光從夜空斜劃過（流星），語錄文字**隨著光逐字寫出來**。停留幾秒讓人讀完，接著文字**化成一小撮光點往上飄散、淡出消失**。
- **消失後**：畫面剩下乾淨的村落，語錄不再出現。**這一句只屬於這一次打開，看過就沒了（A 版：完全不留、不可回看）**——這是刻意的，要的就是「錯過就抓不回」的珍惜感。
- **排版參考**（呼應你給的日曆感樣稿）：月份英文走手寫感弧線、幾號用最大的發光數字、星期在側、語錄在下方置中，四角可有淡淡的框線點綴。字體沿用第 10 節（標題 Noto Serif TC、內文 Noto Sans TC）。

**語錄怎麼挑（每次都不同、依情境）：**

- **依當下條件選語錄池**：看天氣（晴／雨／陰）、時段（清晨／夜晚）、以及**今天是不是節日**，決定從哪個池子抽。例如雨天早上抽「雨天＋晨間」的句子；情人節就抽情人節專屬語錄，村落還可加一點節日小裝飾（情人節飄愛心光點、過年掛小燈籠）。
- **抽完短期不重複**：從符合的池子隨機抽一句，但記住最近出現過的幾句，短期內不再抽到，維持「每次都新鮮」的流星感。
- **池子要夠大**：這是唯一要持續投入的地方——語錄庫越多句，流星感越持久。屬於內容量的功課，可慢慢累積。

**跟天氣語錄的關係**：這套語錄跟第 03 節「天氣語錄」是**同一套內容系統**，只是每日開場多了「日期顯示＋節日判斷＋流星動畫＋看過消失」。不用做兩套。

**語氣紅線**：語錄與主題詞維持「陪伴、反思」的語氣，**不寫成運勢預測**（不出現「今天諸事不宜」「財運差」這類）。這跟塔羅的紅線一致——不做吉凶、不做預測，只做溫柔的一句話。

### 純觀賞模式

什麼都不用做，只是看著自己的村落——燈籠飄、天氣變化、風吹葉、鄰居的燈火。這讓 App 從「工具」變成「一個能待著的地方」，是留存的隱形功臣。MVP 就該有。

### 回顧卡：「一年前的今天」

翻到很久以前的願望或就寢紀錄，自動生成一張回顧卡：「三個月前你許的這個願，實現了嗎？」「一年前的今天，你在這裡許下……」。這是這類 App 最天然、最戳心的**分享來源**——使用者會主動截圖分享「我一年前的願望實現了」。屬於 Phase 2（需要累積夠久的資料才有東西可回顧）。

### 聲音＋觸覺

許願時星光匯聚的「叮」、熄燈入夜的音效、抽塔羅的沙沙聲，配合輕微震動。成本低、效果強的儀式感細節，MVP 就該有。

## 03 天氣：真實天氣＋語錄

天氣只有一個真相來源：**真實天氣**。不做使用者自選的「心情天氣」，避免兩層天氣互相打架、也少一套要拍板的規則。

- 串接手機定位或使用者設定城市的真實天氣 API，決定村落當下的光影與效果（晴朗／多雲／陣雨…）——這是唯一的視覺依據。
- 在家的畫面上，搭配一句**跟當下真實天氣呼應的語錄**（例如下雨天出現偏「沉澱」「安靜」語氣的句子），用文字傳達心情共鳴，而不是讓使用者自己選一個情緒圖示。使用者的「心情」不是自選出來的畫面，是天氣幫他說出來的一句話。
- 這句語錄跟**第 02.5 節「每日開場」共用同一套語錄系統**（依天氣/時段/節日選句），也跟第 04 節塔羅回應共用「依天氣調語氣」的文案邏輯，不用做三套。天氣語錄、每日開場、塔羅回應現在都是 MVP 就要有的功能，這套語錄庫要在 MVP 階段就備好，一次寫、三個地方共用。
- 陰雨天一樣要做得美、不能有懲罰感，這條原則延續原手冊。
- 定位僅用於天氣顯示，需在權限說明中清楚告知，並提供「手動選城市」取代定位的選項。

### 天氣拿不到時的備援（MVP 就要有）

天氣是打開 App 第一眼看到的東西，所以 API 掛掉或超過免費額度時，主畫面**絕對不能壞掉或空白**。備援規則：

- **API 失敗或無資料時**，村落自動退回一個**中性預設畫面**——柔和的黃昏／星空，不強調任何特定天氣。
- 這個備援畫面配一句**不提天氣的通用語錄**（例如偏「陪伴」「安靜待著」語氣的句子），使用者不會察覺是降級狀態。
- 只有天氣正常回來時，才切換到對應的天氣光影與語錄。
- 這條是 MVP 必做，不是選配——因為天氣是每個人每天必經的第一個畫面。

## 04 塔羅：望向星空，問一件心裡的事（MVP・主要拉新賣點）

原手冊寫過「不做成塔羅牌等級的正式占卜」，理由是插畫成本高、神秘學色彩拉高審查風險。這版調整為：**保留塔羅的結構，牌做成 voxel 立體牌（不做插畫），機制往「你可以主動問一件事」的方向做**，比單純每日固定一張牌更有目的性、更好玩。

### 呈現：望向星空抽牌（核心儀式）

塔羅入口不在桌上、也不在選單，而是**抬頭望向夜空**——呼應「向星空提問、從宇宙接收訊息」的意象，跟貨幣「星光」、跟整個夜晚安靜的調性完全連起來。完整流程：

1. **抬頭 → 出現寫字的牌**：在家的畫面往上看（或點一顆微亮的星），畫面上抬、家淡出，轉場到一片專屬的抽牌夜空（靛夜打底、星點燈金）。夜空中浮現一塊 voxel 牌，牌面就是輸入區，寫下今天想問的事。
2. **寫完 → 射上天空**：送出後，牌化成一道星光射向夜空深處（一段有儀式感的動畫）。
3. **牌海浮現 → 挑牌**：星光散開，一整群 voxel 塔羅牌浮現。呈現方式：
   - **靜態時「星群漂浮」**：牌背朝上、發著微光，像一片會緩緩流動的星群散在夜空。
   - **一滑動就聚成「環形星盤」**：牌群聚攏成一個緩緩旋轉的圓環（像星座盤），滑動轉動它，點一張把它抽出來。這樣既有星群的夢幻、又解決「牌太多塞不下小螢幕」的問題（轉動時只看到一段弧）。
4. **翻牌 → 解讀**：抽出的牌飛到眼前、旋轉翻正，voxel 牌面拼出符號（太陽／星星／月亮），下方顯示反思提示回應＋正向關鍵字。
5. **收尾**：看完點一下，牌化成星光散回夜空，畫面落回家。

> **抽牌夜空是「固定的專屬星空」，不跟著真實天氣變**——就算現實在下雨，抽牌時一樣是滿天星。儀式時刻要純粹、不被天氣干擾，所以它跟第 03 節那個會變天氣的背景層是兩回事，互不影響。

### 牌的內容與數量（分階段，見 01.5）

- **牌是 voxel 立體牌**：有厚度、能翻面、能發光，牌面用 voxel 拼出簡單符號（太陽、星星、月亮…），跟整個世界統一成方塊風。不做平面 SVG、也不做插畫。
- **MVP：牌海很多張，但實際只抽 1 張正向牌。** 視覺上是滿天牌海（爽感有了），但實際只做並抽出一組偏正向、不嚇人的牌（例如：太陽／星星／月亮／力量／節制／世界），避開死神、高塔這類讓人覺得「抽到很衰」的牌。這樣工作量還是 6 張的等級，符合「只給正回饋」；牌海的滑動互動先做簡單版（牌排成一段弧、點一張抽出），環形星盤那種華麗滑動可以之後再優化，不擋 MVP 上線（見第 17 節）。
- **Phase 3：升級成真正的多張牌陣。** 能選 3 張（過去／現在／未來這類牌陣，見 12.3），牌擴到 22 張大阿爾克那甚至 78 張全套。這是進階／訂閱功能，等前面穩了再做。
- **卡片結構**：牌名／回應文字／一個正向關鍵字，回應會呼應使用者輸入的問題與當下的真實天氣。
- **提問次數：免費每天 1 次，訂閱無限。** 這個限制同時解決三件事——避免使用者一直重複問同一件事、控制內容審核負擔、也成為訂閱的誘因。跟第 07 節商業模式契合，不用等實測。

### 安全與法律考量（比原本每日一牌更重，需要多想的地方）

自由輸入問題比固定每日一牌更像真的占卜，需要多幾條原本沒有的規則：

| 考量 | 做法 |
|---|---|
| 文案不能給出像「答案」的東西 | 回應走「反思提示」（例如「或許你其實已經有答案了」），不出現「會」「不會」「準」這類斷言字眼，避免踩到消保法／公平交易法的不實廣告紅線 |
| 使用者輸入的問題是自由文字 | 塔羅提問**一律純私密、永遠不飄出去、不公開**——它是自己問自己的事，不進漂流瓶。因為永遠只有自己看得到，所以完全不需要審核／過濾 |
| 問題內容涉及自傷／自殺等關鍵字 | 不打斷書寫；等使用者完成、看到抽牌結果後，再溫和地把求助資源浮出來 |
| 使用者是「主動問問題」，更容易誤會這是真的在算命 | 開場或設定頁的「不宣稱真實占卜效果」聲明要比原本更顯眼 |
| 塔羅抽牌若走付費機制 | 絕對不能做成隨機付費抽卡，踩刑法賭博罪紅線——跟第 07 節「絕對不做」的原則一致 |

## 05 內容與安全設計（樹：許願／告解＋漂流瓶）

沿用原許願池手冊的原則：**私密書寫完全自由，公開才需要安全機制**。這條原則對樹的許願／告解、以及第 04 節塔羅的問題輸入都適用。

### 基本規則

- **許願：** 分類模板（感情／事業／健康／財富／人際／其他）＋最多 20 字客製內容。**免費每天 1 次，看 1 支廣告可以再許 1 次（一天最多 2 次）**，不花星光——跟塔羅同一套「次數」邏輯，星光專心當裝飾貨幣（見第 07 節）。MVP 只給自己看；Phase 2 起可選擇「讓願望飄出去」進入漂流瓶（見下），送出前跑基礎關鍵字過濾。
- **消災告解：** 私密自由書寫是預設狀態，不限字數、不審核；選擇讓它飄出去時才進入安全層。
- **常態求助資源入口：** App 內（設定頁＋適當時機）要有常態顯示的求助資源（如自殺防治專線），不能只靠關鍵字觸發才出現。
- **危機內容處理原則：** 書寫過程中偵測到自殺／自傷等關鍵字，不打斷、不即時攔截；等使用者完成當次書寫後，才溫和地把求助資源浮出來。這條原則對樹（告解）與塔羅（問題輸入）都適用。

### 願望牌的去留（固定天數後被風吹走）

每塊願望牌掛上樹枝滿一段時間（初版建議 **5～7 天**）後，會被風吹走——**不是消失，是「心願被送出去」的正面收尾**，配一句類似「這個心願已經飄了七天，風要帶它去遠方了」的提示，不要讓人覺得心願被拒絕或遺忘。

- **樹的成長不受影響：** tree_level 靠的是**累積總願望數**（永久紀錄、只會往上不會倒退），不是「牌還掛著幾塊」；牌被吹走不會讓樹變小或降級。
- **想回顧舊願望：** 靠第 02.5 節的回顧卡，不是靠樹上還掛著那塊牌。
- **天然解決掛牌過多的問題：** 配合上面「一天最多許 2 次願」的頻率限制，樹上同時存在的牌數量本來就有上限，不需要額外做「牌太多要疊放/群組」的邏輯。
- **Phase 2 加分項（先預留欄位，不用現在做）：** 如果願望被送進漂流瓶、收到別人的祝福，可以讓它提早被吹走，通知裡把兩件事一起講，例如「這個心願已經被 3 個人聽見了，風要把它帶走了」，串起收到祝福＋提早飄走這兩個回饋。

### 漂流瓶願望交換（Phase 2，取代傳統公開心願牆）

不做一整面攤開來滑的「公開心願牆」，改成**一對一、雙向的善意交換**——像收到一封漂流瓶：

- **收：** 每天最多收到少數幾個（例如 1～3 個）陌生人飄來的願望，一次只看一個，讀完可以送出一份祝福。
- **送：** 使用者自己選擇要不要讓某個願望飄出去；飄出去的願望會隨機、延遲地分發給其他人，自己也會收到別人回的祝福數（例如「今天有 3 個人為你的願望加油」）。
- **為什麼這樣設計更安全：** 沒有一整面牆可以滑，就沒有比較、沒有排行榜、沒有炎上、沒有酸民聚集的地方。一次只給你看一個願望，你只能給善意、給不了惡意。這正好避開了 Secret、Whisper、Yik Yak 死於「匿名＋自由留言＋排名」的教訓。

**祝福的形式，分階段開放：**

- **Phase 2（A 版）：只能送預設祝福。** 讀完別人的願望，從幾個固定選項點一個送出，例如「為你加油」「會實現的」「抱抱」。**完全沒有自由文字，就完全沒有審核問題、沒有任何人能傳惡意訊息給你。**
- **Phase 3（B 版）：預設祝福＋一句自由回話。** 等社群穩定、營運機制成熟後再開。一旦開放自由文字傳給特定的人，就有騷擾／廣告／惡意訊息風險，屆時必須配套：關鍵字過濾＋檢舉機制＋封鎖。

### 漂流瓶安全層（Phase 2 起，隨漂流瓶一起上）

- **願望文字本身要過濾：** 就算祝福只能點預設選項，別人的願望文字還是會被你看到，所以願望「飄出去」時就要跑一次關鍵字過濾。
- 不開放留言／回覆串、不做排行榜或熱門榜。
- 願望分發**延遲＋打散**，不即時、不可回溯到特定人。
- 每人每日「飄出願望」與「收到願望」都設上限。
- 提供**檢舉／不想再收到這類**的入口，收到讓人不舒服的願望時能一鍵略過並回報。

## 06 法律風險備忘

以台灣為主的初步整理，**不是正式法律意見**，正式上線前建議找律師看過條款與文案。用白話說明每條「怕的是什麼、我們怎麼避開」。

### 一直都要守的（MVP 就適用）

| 怕什麼 | 白話說明 | 我們怎麼做 |
|---|---|---|
| 說塔羅／消災「真的有效」 | 若講得像真能算命、真能消災，會被當成不實廣告 | 文案定位成「情緒抒發與反思工具」，不做效果宣稱；不出現「準」「會／不會」這種斷言 |
| 付費抽卡 | 花錢隨機抽東西＝賭博性質，是刑事紅線 | 絕對不做付費抽卡，塔羅也不例外 |
| 使用者刪不掉自己的資料 | 法律規定人有權要求刪除自己的個資 | 全部用軟刪除，使用者能隨時刪掉自己的願望／告解／塔羅紀錄，畫面上完全不再出現 |
| 定位權限 | 為了抓天氣要用定位，若沒講清楚會被質疑亂拿位置 | 講明「定位只用來顯示天氣」，並提供「手動選城市」取代定位 |
| 未成年人課金 | 未成年亂刷錢，交易效力有爭議 | 條款寫明，並用 App Store／Google Play 既有的家長／年齡機制 |
| 危機內容沒好好處理 | 有人寫下想不開的話，平台放著不管會有道德與究責風險 | 設定頁常態放求助資源；偵測到危機字眼，等對方寫完再溫和浮出專線 |

### Phase 2 開漂流瓶後，額外要守的（社交才有的風險）

漂流瓶＝把 A 寫的東西送到 B 眼前，等於平台在「散布使用者產生的內容」，多了幾條原本單機時沒有的風險：

| 怕什麼 | 白話說明 | 我們怎麼做 |
|---|---|---|
| 你收到別人的不當內容 | 飄來的願望可能有色情、辱罵、廣告、仇恨言論，平台推給你就有責任 | 願望「飄出去」前先跑關鍵字過濾；每則都能一鍵略過並檢舉；累積被檢舉的內容自動下架 |
| 別人的內容洩漏第三人個資 | 有人在願望裡寫別人的真名、電話、住址 | 條款明訂不得張貼他人個資；過濾＋檢舉一起擋 |
| 未成年接觸到陌生人內容 | 有陌生人互動的 App，各國對保護未成年要求特別高 | 明確標示年齡分級；漂流瓶內容經過過濾；提供檢舉與封鎖 |
| App 商店審查卡關 | 「使用者產生內容＋陌生人互動」是商店審查的重點，沒做防護會被退件 | 上線前備好三件套：內容過濾、檢舉、封鎖／略過；審查表單據實說明 |
| Phase 3 自由回話的騷擾風險 | 一旦能寫字給特定的人，就等於陌生人私訊，騷擾／性騷擾風險大增 | 這是 Phase 3 才開；開之前必須先有成熟的過濾＋檢舉＋封鎖機制 |

**一句話：MVP 因為只有自己看得到，法律風險很低；風險主要集中在 Phase 2 開漂流瓶之後，核心就是「過濾＋檢舉＋封鎖」這三件套，缺一不可。**

## 07 商業模式

- **核心循環永遠免費：** 睡前打卡、許願、塔羅提問抽牌，一律不設付費門檻。
- **星光＝純裝飾貨幣。** 只拿來買 voxel 外觀（家的裝潢、樹周圍的擺件、音效…），**不再是許願或塔羅的門檻**。獲取管道：每日簽到＋自願看激勵廣告，不能直接用真錢購買。
- **課金走獨立通道：** 低價（約 NT$10–30）用真錢直接購買外觀與特效，花費透明，不透過星光轉換。可賣的東西：
  - MVP 就有的 voxel 外觀：房子的裝潢、樹周圍的擺件。
  - Phase 3 才有的：塔羅牌風格／牌背樣式（塔羅功能本身 MVP 就上線了，但額外的牌皮膚屬於錦上添花，留到後面深化變現階段再賣）。
- **MVP 商店賣什麼：** MVP 階段星光與課金只賣「家與樹周圍的 voxel 外觀」——塔羅本身雖然 MVP 就有，但先不賣牌皮膚，因為漂流瓶還沒上、還不需要那麼多外觀選項。外觀項目越到後面階段越多。
- **訂閱制備案：** 去廣告＋無限額度（塔羅、許願的每日次數都變無限）＋專屬特效，作為主要營收。
- **廣告（若用）：** 自願／激勵式，不打斷任何儀式流程，類別排除博弈／酒類／借貸；廣告有**兩種用途**，彼此不換算——(a) 在樹前或抽塔羅時看 1 支，直接換「今天再 1 次」的機會；(b) 在商店頁看廣告，換的是星光（存起來買裝飾）。
- **絕對不做：** 隨機／抽獎式付費獎勵（含塔羅付費抽卡），踩賭博法律紅線。

### 塔羅提問、許願與漂流瓶祝福要不要花錢

- **塔羅提問：不花星光，用「每日次數」控管。** 免費每天 1 次，看 1 支廣告可再 1 次，訂閱無限（見第 04 節）。
- **許願：跟塔羅同一套邏輯，不花星光。** 免費每天 1 次，看 1 支廣告可再許 1 次（**一天最多 2 次**——2 次已經算奢侈，避免無限灌水養樹），訂閱無限（見第 05 節）。

**關鍵安全設計：**
- Confession 的私密原文與飄出去的版本分開存放（TarotDraw 永遠私密，無此問題）。

## 10 美術與場景設計

延續許願池原本的視覺語言（許願樹＋溫暖夜景，避開真實廟宇聯想），家、樹、願望牌也統一進同一套調性。

> 🧊 **視覺總則：整個世界都是 MagicaVoxel 的 3D 方塊風，無例外。** 家、樹、願望牌、燈籠、鄰居屋、**塔羅牌**等所有物件都是 voxel 立體模型。塔羅牌做成有厚度、能翻面發光的 voxel 牌，牌面用 voxel 拼出符號（太陽、星星、月亮），抽牌在專屬的夜空場景進行（見第 04 節）。全 voxel 統一，畫面才像出自同一個世界。
>
> 原許願池的「天燈」意象已移除（天燈輕飄半透明，不適合 voxel 方塊風）。許願的累積物改成 **voxel 願望牌**——一塊小木牌／石牌，掛在樹枝上，像日本繪馬那種，好用方塊做、能一塊塊累積、也無宗教包袱。

### 場景

- **家：** 沿用睡眠養成的「越住越溫馨」邏輯——達標天數越多，窗戶燈光越暖、屋子裝飾越多、周圍多幾戶鄰居的燈。家的畫面上顯示真實天氣效果；抬頭望向星空則進入塔羅抽牌。
- **樹：** 完整沿用許願池的生長系統——階段式樹體切換（4～5 階）＋願望牌（voxel 小木牌）動態掛載＋環境氛圍隨進度變化。跟家在同一片地面，不是獨立場景，點樹鏡頭平移過去（見第 02 節）。
- **塔羅牌：** voxel 立體牌（有厚度、能翻面發光），牌面用 voxel 拼出符號（太陽、星星、月亮）。抽牌在專屬夜空場景進行：望向星空 → 寫問題 → 射上天空 → 牌海（星群漂浮／環形星盤）→ 抽牌翻正解讀（見第 04 節）。
- **家↔樹鏡頭平移、家↔抽牌夜空轉場：** 家跟樹是同一片地面的鏡頭平移，不用做場景轉場動畫；抬頭望向星空才是真正離開地面的轉場，這段轉場動畫才需要儀式感（見第 02 節）。

### 氛圍加強方向（靠光與粒子，不是靠建模精細度）

參考了幾張《原神》截圖後確認方向：想要的是那種戲劇性暖光、巨樹存在感的**情緒**，不是要追那個等級的建模精細度，而且仍然全部用 voxel 製作。

- **樹冠比例誇張化：** 樹幹細、樹冠大、層數多做到 3～4 層，巨樹感靠比例堆出來，不用雕細節葉片。
- **光柱效果：** 用 Godot 的方向光＋體積霧，做出樹冠縫隙透光的丁達爾光柱，voxel 模型本身不用變複雜。
- **螢火／光點粒子取代花瓣特效：** 飄在樹冠周圍跟地面附近的發光小光點，量少但夠亮，是花瓣氛圍的 voxel 版替代方案。
- **地面發光小花點綴：** 樹根周圍點幾顆會發光的小 voxel 花草，呼應地面光效，不用做整片草地建模。
- **暖色不用全天開：** 可以只在特定天氣（黃昏／晴天）或節日時加強樹的暖光效果，平常維持安靜的靛夜基調，美術工作量仍然可控。

🚫 **紅線提醒：** 避免神社／鳥居／石獅狐狸像這類明確的宗教／廟宇符號，跟本節開頭「避開真實廟宇聯想」的原則一致——只抓光影與粒子的情緒，不抓建築符號。

### 12.1 一副牌的完整結構（78 張）

  - 星幣（對應土元素）：金錢、安全感、穩定、長期未來
- 每張牌都有一組正位關鍵字＋一組逆位關鍵字。

**對照現行方案：** 第 04 節先做的 6 張正向牌（太陽／星星／月亮／力量／節制／世界）全部屬於大阿爾克那裡評價偏正面的牌，跳過死神、高塔、惡魔這類容易讓人覺得「抽到很衰」的牌，方向上跟「只給正回饋」的核心原則一致。

**若日後要擴充，建議順序：** 先擴到大阿爾克那全 22 張，再考慮小阿爾克那。理由是大阿爾克那本來就偏向大方向的人生課題，比較貼合「每日一問」的調性；小阿爾克那較細瑣、也多達 56 張，比較適合留給多張牌陣或訂閱限定的進階功能（見 12.3）。

### 12.2 牌義寫法參考

每張牌用「正位」「逆位」兩組關鍵字表達，例如：太陽 正位＝幸福、成功、樂觀、活力；逆位＝幸福受阻、過度熱情、悲觀、不切實際。

現行機制只做正向牌，等於是**只用正位語意、不判斷逆位**，可以刻意維持這個簡化——之後真的要擴充到 22 張大阿爾克那時，再決定要不要引入逆位。

> ✏️ **文案原則：盡可能還原塔羅牌本來的感覺，不刻意避諱字眼。** 唯一的硬邊界是第 06 節的法律紅線——不能宣稱真的能預測、占卜，這是廣告不實的問題，跟牌名、牌義道不道地無關。除此之外：
> - **牌名照傳統用，不用改名或迴避。** 死神、惡魔、高塔都用原本的名字，塔羅的吸引力本來就來自這些原型意象，刻意繞開反而顯得矯情。
> - **牌義先誠實講傳統解釋，不用急著加緩衝詞。** 例如死神就直接講「代表某個階段要結束、需要放手」，逆位就直接講「抗拒改變」，不用先想辦法包裝成別的說法。
> - **「只給溫暖」管的是讀完整段話之後的感受，不是每個字都要正面。** 文案公式是「先誠實講牌義是什麼→收尾補一句往前走的具體方向」，重點放在後段給出方向，而不是迴避前段的本義。
> - 這套原則對 MVP 現行 6 張牌、以及未來擴充的大阿爾克那、逆位都適用。

### 12.3 若未來做多張牌陣：可直接參考的結構與整合邏輯

現行機制是「問一句話→抽一張牌→給一段反思回應」，屬於單張牌形式。若之後想做進階的「多張牌」版本（例如訂閱限定功能），這裡有現成的設計語言可以參考：

**常見三張牌陣結構：**

| 牌陣 | 第1張 | 第2張 | 第3張 | 適合問題 |
|---|---|---|---|---|
| 時間軸型 | 過去影響 | 現在狀態 | 未來傾向 | 事情怎麼發展 |
| 行動型 | 目前情境 | 主要阻礙 | 可行建議 | 我該怎麼做 |
| 選擇型 | 選項A | 選項B | 評估重點 | 比較兩條路 |
| 內外型 | 表層想法 | 內在驅動 | 外在表現 | 理解情緒/關係互動 |

> 📌 **牌陣結構定案：用「行動型」，不用「時間軸型」。** 「未來傾向」這個位置名稱本身就有風險——等於在畫面上明講「這張牌在講你的未來」，太接近占卜預測的定位，跟第 04、06 節「不出現會/不會/準、不代表真實預測」的紅線衝突。行動型（目前情境／主要阻礙／可行建議）三個位置都是反思＋行動導向，沒有任何一格在講「未來會怎樣」，法律風險低很多，也跟現行單張牌的反思提示語氣一致。**牌陣結構固定、內容客製化**：三個位置模板不變，實際配出來的反思文字才依使用者輸入的問題＋抽到的牌＋當下天氣變化。

**多張牌之間的四種關係**（用來把多張牌串成一段回應，而不是各自獨立的三段文字）：
- **支持／延續：** 方向相近，後一張延續或放大前一張
- **拉扯／對立：** 方向衝突，代表內外需求還不一致
- **因果／回應：** 後一張像是回應前一張帶出的課題
- **轉折／修正：** 方向明顯改變，帶出新的選擇或方法

**整合公式（可以直接當成多牌回應的文案骨架）：**
> 目前＿＿＿（第一張），真正需要處理的是＿＿＿（第二張）；如果願意＿＿＿（第三張），事情較可能朝＿＿＿發展。

這個「先給結論、不出現斷言字眼」的寫法，跟第 04 節現行「回應走反思提示，不說會／不會／準」的原則相容，之後做多牌版本可以直接沿用同一套文案邏輯，不用另外設計一套。

## 13 製作流程：從現在做到上架

給第一次要動手的人的路線圖。原則跟三份原始手冊一致——**先讓一個能上架的東西存在，再逐步長功能**，不要一次全做。每個階段結束都該是「能給人用、能截圖、能上架」的狀態。

### 👤 分工定位（重要）

**你（專案主）負責美術與決策，程式的部分交給 AI 協作完成。** 這份製作流程的每一步都會標上負責人：

- **🎨 你：** 用 MagicaVoxel 做 voxel 資產、定調視覺、拍板設計決定、測試玩起來的感覺、提供素材。
- **🤖 AI：** 寫程式、接後台與 API、除錯、解釋每段程式在做什麼。你不用學會自己寫程式，你要學會的是「看得懂 AI 做出來的結果、能測、能給回饋」。
- **🤝 一起：** 需要你決定方向、AI 執行的事（例如成長門檻數字、動線手感）。

新手怎麼一步步跟 AI 配合，詳見第 16 節。下面每步的標記對應這個分工。

### 階段 0：開工前先拍板（不寫程式，1～2 天）

先把「開工前必須拍板」那幾件事定下來（見第 11 節 A 組），免得做到一半打掉重練：

1. 🤝 帳號要用什麼登入方式（建議 Supabase Auth，先支援匿名試用，之後可綁 Email／第三方登入升級）。**AI 給建議、你拍板。**
2. 🤝 註冊一個真實天氣 API（例如 OpenWeatherMap 免費方案）。**AI 幫你查怎麼註冊、你去申請拿金鑰。**
3. 🎨 申請 Apple／Google 開發者帳號（要錢、要審核時間，越早辦越好，別卡在最後一步）。**這是帳號與付費的事，要你本人辦。**

### 階段 1：做出 MVP（自己的村落）

目標：一個人能養一座只有自己看得到的村落，能上架。順序建議由內而外：

1. 🤖 **搭骨架先跑起來** — 用 Godot 開一個空場景，放一個最陽春的「家」和「樹」（先用灰盒佔位，美術後面再換），確認 App 能開、能點。**AI 帶你裝 Godot、建場景、寫第一段腳本。**
2. 🤖 **接後台** — 接 Supabase，做好 User／Wish／Confession／SleepEntry／WorldState 這幾張表，確認資料存得進、讀得出。**AI 寫接後台的程式，你去 Supabase 網站建帳號。**
3. 🤖 **做睡前打卡** — 按「睡了」→ 記一筆 SleepEntry → 家熄燈入夜的動畫 → 隔天家的溫暖度依累積達標天數推進。這是最核心、最單純的循環，先讓它完整。**AI 寫邏輯，你測手感、確認熄燈動畫好不好看。**
4. 🤖 **做許願／告解** — 走到樹前 → 選分類或自由書寫 → 儀式動畫 → 樹長大、掛願望牌。此階段**只存自己看**，完全不做任何對外分享。**AI 寫，你測、給回饋。**
5. 🤖 **接真實天氣＋語錄＋備援** — 抓天氣代碼決定村落光影，配語錄；同時做好第 03 節的備援畫面（天氣拿不到就退回中性黃昏／星空）。**AI 寫串接，語錄文案可你我一起寫。**
6. 🤖 **做塔羅提問** — 望向星空的抽牌儀式：寫問題→射上天空→牌海（先做簡單版，牌排成一段弧、點一張抽出）→翻牌顯示反思回應。6 張正向牌，每天免費 1 次。**這是主要拉新賣點，MVP 一定要做完整。AI 寫抽牌邏輯與轉場，你做 6 張 voxel 塔羅牌＋牌背、文案可一起寫。**
7. 🤝 **補冷啟動＋陪伴細節** — 新使用者第一天的開場儀式（種第一棵樹／點第一盞燈）、純觀賞模式、聲音＋觸覺（見第 02.5 節）。**AI 寫程式，你做美術與音效素材、定手感。**
8. 🤖 **補必要的合規頁** — 免責聲明、隱私與定位權限說明、常態求助資源入口、設定頁、資料刪除功能；塔羅「不宣稱真實占卜效果」的聲明要比其他頁面更顯眼。**AI 寫，法律文字上線前建議找人確認。**
9. 🎨 **換上正式美術** — 把灰盒佔位換成 MagicaVoxel 做好的家、樹、塔羅牌、燈籠等資產（見第 14、15 節）。**這是你的主場，AI 幫你把素材接進 Godot。**
10. 🤝 **上架** — 打包送審 App Store／Google Play，跑完整個審查流程。**AI 幫你打包、寫送審資料，帳號與付款要你本人操作。這一步的經驗最寶貴，越早跑越好。**

### 階段 2：加漂流瓶 + 回顧卡

MVP 上線、累積了一批天天在許願／抽塔羅的使用者之後再做：

1. **漂流瓶（A 版）** — 加 BlessingReceived／DriftInbox 兩張表，做「願望飄出去→延遲隨機分發→別人讀到回預設祝福→我收到祝福數」的循環，配上關鍵字過濾與檢舉入口（見第 05 節）。
2. **回顧卡** — 這時資料累積夠久了，做「一年前的今天／三個月前的願望實現了嗎」的回顧卡，當自然分享點。

### 階段 3：進階與變現深化

1. 漂流瓶 B 版（祝福可加一句自由回話）＋配套的審核／檢舉／封鎖。
2. 塔羅擴充到 22 張大阿爾克那，考慮訂閱限定的多張牌陣。
3. 訂閱制、商店外觀課金上線。

### 一句話總結流程

先做「一個人的村落」做到能上架 → 累積使用者 → 再開「人與人之間的漂流瓶」和「塔羅」→ 最後才做進階與深度變現。

## 14 美術與場景製作建議（MagicaVoxel 導向）

你打算用 MagicaVoxel 做 voxel（方塊積木風）資產，這跟整個 App「安靜、溫暖、不擬真」的調性很搭。這節是給實際動手做美術的具體建議。

### 為什麼 voxel 風格很適合這個專案

- **做得快、好統一。** 方塊積木風不需要精細的貼圖和高模，一個人也能在合理時間內把家、樹、燈籠全做完，而且天生就風格一致。
- **溫暖不擬真，剛好避開恐怖谷。** 這個 App 要的是「療癒」，voxel 的圓潤方塊感比寫實風更容易做出可愛、安心的感覺。
- **檔案小、跑得動。** voxel 模型面數低，手機上跑起來輕鬆，載入也快。

### 統一規範（動手前先定，之後省很多事）

- **色票鎖死。** 全部資產只用第 10 節那五個色（靛夜 #101A2E／燈金 #E8A94A／翠玉 #74AE8D／火硃 #C2653F／紙白 #F3EFE4）＋少數過渡色。MagicaVoxel 建議把這套色票存成 palette 檔，每個模型都套同一份，畫面才會像出自同一個世界。
- **統一體素密度。** 先定好「1 公尺＝幾個方塊」，家、樹、鄰居房子都照同一個密度做，不然擺在一起會有的粗有的細。
- **光靠氛圍，不靠寫實。** 這個 App 的重點是燈火、黃昏、星空這種「光的溫度」。voxel 本身不用做很細，靠 Godot 裡的燈光、發光材質、粒子（螢火、燈籠光點）去營造氣氛，比把模型做很精細更有效。

### 各場景的美術重點

- **家：** 做**一個基礎屋子 + 多層可疊加的裝飾件**（暖光窗戶、掛飾、煙囪的煙、門口小燈…）。溫暖度升級不是換一整棟新房子，而是逐件點亮／加上裝飾，這樣升級感是連續的、成本也低。鄰居的房子可以用同一棟屋子改色重複擺，遠處點幾盞燈就有村落感。
- **樹：** 這是情感核心，值得多花力氣。做 **4～5 個生長階段的樹體**（幼苗→小樹→成樹→茂盛→開花＋掛滿願望牌），階段之間切換要有一個「長大」的過渡動畫或粒子效果，不要硬切。願望牌做成 voxel 小木牌／石牌，能一塊塊掛到樹枝上。
- **天空／天氣：** 天空不做成 voxel 模型，用 Godot 的背景漸層 + 光照 + 粒子（雨、雪、星點、飄雲）呈現。做**一套天氣狀態**（晴／多雲／雨／夜／備援用的中性黃昏），每種都調到「就算是陰雨也很美、沒有懲罰感」。
- **塔羅牌（MVP）：** voxel 立體牌，有厚度、能翻面、能發光，牌面用 voxel 拼出符號（太陽、星星、月亮）。牌背朝上時發微光，MVP 先排成一段弧、點一張抽出即可，環形星盤那種滑動聚合效果可以之後再做。搭配「射上天空→牌海浮現→翻牌」的動畫與音效。**抽牌夜空**是一個獨立場景（靛夜打底＋燈金星點），不是家/樹那兩個場景，也不受真實天氣影響。
- **牌面美術定案：固定舞台＋角色本身翻轉。** 為了盡可能還原塔羅的感覺（見 12.2），牌面走完整立體小場景（例如太陽牌拼一個「人物剪影＋太陽＋地面」的縮小舞台），不是抽象符號。舞台（地板、背景元素、光源）永遠固定方向、正常打光，只有場景裡的**角色模型本身**在逆位時旋轉 180 度（頭朝下），不是整張卡一起翻轉。這樣光影永遠正確、不會出現「翻過來後光從下面打上來」的違和感；一張牌只需要做一份角色模型，正逆位共用，不用多建模或多畫一次場景。旋轉軸心抓在角色中心點，避免頭朝下時插入地板或懸空不自然。

### 給一個人做美術的務實建議

- **先做灰盒佔位、程式先跑通，最後才換正式模型。** 別一開始就雕美術，先確認機制對了。
- **資產分「基礎件＋裝飾件」，不要做「完成品」。** 這樣升級系統才能一件件疊加，而不是每個等級都重做一整套。
- **氣氛的錢花在燈光和粒子上，不是花在模型精度上。** 這是這類療癒 App 投報率最高的地方。

## 15 成長門檻與美術資產清單（初版方案，待實測調整）

> 📎 **開工前實作三節連讀：** 第 15 節（要做哪些美術資產、成長門檻數字）→ 第 16 節（你和 AI 怎麼分工協作）→ 第 17 節（每個功能做不做得出來、難度與雷）。這三節是把設計轉成實作的依據。

這節把「家要幾個溫暖等級、樹要幾個生長階段」的具體數字定出來（回應第 11 節 B 組的待決事項），再依這些等級列出 MVP 要做的 MagicaVoxel 資產。**數字是初版、可調**，重點是先有個能開工的基準，實測後再依真實留存曲線調整。

### 設計原則：前期快、後期慢

升級節奏要「**一開始很快就有回饋，越到後面越慢**」。理由：新使用者最脆弱是頭幾天，前面幾級門檻要低（第一次打卡、第二天就升級），讓人馬上感覺「我的村落有在變」；後面拉長，才有長期養成的空間。**漏做一天絕不倒退、不扣等級**——這是全 App 的紅線，成長只會前進或停住，永遠不退。

### 家的溫暖度（house_level）— 靠「累積準時就寢天數」推進

| 等級 | 累積準時天數 | 畫面變化 |
|---|---|---|
| Lv.0 | 0（新使用者） | 家有微光，冷清但不荒涼（冷啟動起點） |
| Lv.1 | 1 天 | 窗戶亮起暖光（第一次打卡就升級，立刻有回饋） |
| Lv.2 | 3 天 | 門口點一盞小燈、加一件掛飾 |
| Lv.3 | 7 天 | 煙囪冒煙、屋內更暖、多一件裝飾 |
| Lv.4 | 14 天 | 旁邊出現第一戶鄰居的燈 |
| Lv.5 | 30 天 | 鄰居變多，村落夜景成形 |
| Lv.6+ | 之後每 30 天 | 持續增加鄰居燈火／季節性小裝飾，無上限、越來越慢 |

- 「準時」的判定沿用 SleepEntry 的 `is_on_time`（打卡時間 vs 目標就寢時間）。
- 累積的是**總達標天數**，不是連續天數——不做「斷 streak」那套，漏一天只是那天沒 +1，不倒退。

### 樹的生長階段（tree_level）— 靠「累積許願數」推進

| 階段 | 累積願望數 | 樹的樣子 |
|---|---|---|
| 幼苗 | 0～1 | 剛冒出的小芽（冷啟動時「種下第一棵樹」就在這） |
| 小樹 | 2 | 有主幹和幾片葉（許第 2 個願就升，快速回饋） |
| 成樹 | 5 | 樹冠成形，開始能掛願望牌 |
| 茂盛 | 12 | 枝葉繁密，掛滿多塊願望牌 |
| 開花 | 25 | 開花＋掛滿願望牌，最華麗的完成態 |
| 開花+ | 之後每 15 個願 | 花況／光點持續豐富，無上限、越來越慢 |

- 願望牌（voxel 小木牌）是**每許一個願就掛一塊**，掛滿 5～7 天後被風吹走（見第 05 節），跟樹的階段分開算——牌會流動更新，不會無限堆積；「我許過很多願」看得見的是樹的成長等級本身（永久累積、只會往上），不是掛著的牌數。
- 告解不推進樹的等級（告解是「放下」，不是「許願」），但可以有自己的小視覺回饋（例如樹下飄走一點光）。

### MVP 要做的 MagicaVoxel 資產清單

依上面的等級，MVP（階段 1）需要這些。**全部遵守第 14 節的統一色票與體素密度。**

**家（基礎件 + 可疊加裝飾件，不做整棟替換）**
- 基礎屋子 ×1（Lv.0 的樣子，之後靠疊裝飾升級）
- 暖光窗戶件 ×1（Lv.1 疊上去）
- 門口小燈 ×1、掛飾 ×2～3 種（Lv.2～3 陸續疊）
- 煙囪煙效（用粒子做，非模型）
- 鄰居房子 ×1（用基礎屋改色重複擺，Lv.4 起放遠處）

**樹（5 個生長階段 + 願望牌）**
- 樹體 ×5（幼苗／小樹／成樹／茂盛／開花，各一個 voxel 模型）
- 願望牌 ×1～2 種（voxel 小木牌／石牌，能一塊塊重複掛到樹枝上）
- 階段切換的過渡粒子（發光／葉子飄動，用 Godot 做）

**天氣（不做 voxel，Godot 的光照＋粒子＋背景漸層）**
- 天氣狀態 ×5：晴／多雲／雨／夜／備援中性黃昏
- 粒子：雨滴、星點、飄雲（雪可留到後面）

**每日開場（見第 02.5 節）**
- voxel 數字 0～9（各一個，能拼出任何日期）＋ 12 個月份字（英文或中文，能拼出任何月份）＋星期字。一次做好永久用。
- 流星劃過與語錄飄散的粒子（用 Godot 做，非 voxel 建模）
- 節日小裝飾（情人節愛心光點、過年小燈籠…）：想做幾個做幾個，不做也不影響核心

**塔羅（主要拉新賣點，MVP 就要做）**
- voxel 塔羅牌 ×6（先做正向牌：太陽／星星／月亮／力量／節制／世界），牌背 ×1（能發微光、排星群用）
- 抽牌夜空場景（靛夜背景＋燈金星點，獨立於天氣層）
- 動畫：牌射上天空、牌海先排成一段弧（點一張抽出，先不做環形星盤那種滑動聚合）、抽牌翻正、化星光散回（多半用 Godot 做，非 voxel 建模）

**共用氛圍件**
- 燈籠／螢火光點（點綴用，成本低效果強）
- 許願時星光匯聚的「叮」音效 + 熄燈入夜音效 + 抽塔羅的沙沙聲 + 輕微震動（見第 02.5 節）

**MVP 不用做的**（留到 Phase 2）：漂流瓶相關 UI、回顧卡版型。**Phase 3 才做**：塔羅牌皮膚／牌背商店樣式、環形星盤那種華麗牌海滑動、22 張大阿爾克那擴充。

### 一句話總結

家看「準時睡了幾天」、樹看「許了幾個願」，兩者都是前期升得快、後期升得慢、漏做不倒退。美術照這些等級做，家用「基礎屋＋疊裝飾」、樹做 5 個階段，天氣全部交給 Godot 的光和粒子，別花時間雕模型細節。

## 16 這份做得到嗎？AI 寫程式、你做美術的協作分工

> 📎 開工前實作三節：第 15 節（資產與門檻）→ **第 16 節（分工協作）** → 第 17 節（逐功能可行性）。

老實話先講：**做得到。** 這個專案的分工很明確——**你負責美術與決策，程式全部交給 AI 協作完成，你不需要學會自己寫程式。** 我們也刻意把 MVP 切得很小，用到的都是「有標準做法、AI 能穩定產出」的入門功能，不是什麼高難度的東西。

### 分工總表：誰做什麼

| 你（🎨 專案主） | AI（🤖 協作） |
|---|---|
| 用 MagicaVoxel 做 voxel 資產（家、樹、燈籠…） | 寫全部程式（Godot 腳本、接後台、接 API） |
| 定調視覺風格、色票、體素密度 | 除錯，解釋每段程式在做什麼 |
| 拍板設計決定（成長門檻、動線手感） | 把你的美術素材接進 Godot |
| 測試「玩起來的感覺」，給回饋 | 打包、寫上架送審資料 |
| 申請帳號、付款、按送審鈕（要本人） | 教你每一步該點哪裡、貼什麼 |

**一句話：你像導演＋美術，AI 是工程師。你說要什麼、看成果、給回饋；AI 把它變成能跑的程式。**

### 各部分難度（對 AI 來說）

| 部分 | 對 AI 難度 | 你要做的 |
|---|---|---|
| 睡前打卡 | ★ 很簡單 | 測手感、確認熄燈動畫好看 |
| 許願／告解（存自己看） | ★ 很簡單 | 測、給回饋 |
| 接 Supabase 存資料 | ★★ 不難 | 去 Supabase 網站建帳號（AI 教你點） |
| 接真實天氣 API | ★★ 不難 | 去申請一組免費金鑰 |
| Godot 場景與動畫 | ★★ 不難 | 提供 voxel 素材、定手感 |
| 塔羅：望向星空抽牌（MVP，主要拉新賣點） | ★★ 不難 | 做 6 張 voxel 牌＋牌背、文案一起想 |
| 上架 App Store／Google Play | ★★★ 繁瑣 | 帳號、付款、按送審鈕（AI 幫你備好一切） |
| 漂流瓶（Phase 2） | ★★★★ 最難 | 這是 Phase 2，MVP 完全不用碰 |

**重點：MVP 包含塔羅在內都是 ★～★★，AI 都能穩定做出來；最難的漂流瓶排在後面，你 MVP 階段一次都不會碰到它。**

### 你只需要記住三件事

1. **不用學寫程式，但要學會「看成果、給回饋」。** AI 做出一版，你打開來玩，告訴我「熄燈太快了」「樹長大的動畫要更明顯」——這種回饋比你會不會寫程式重要得多。
2. **可以先做網頁版驗證，不用一開始就碰上架。** Godot 能直接輸出成網頁。先做一個「瀏覽器打開就能玩的村落」，自己玩、給朋友玩，確認點子有人喜歡，之後再處理上架那些繁瑣的事。最快看到成果、最不容易半途放棄。
3. **一步一步來，不要看「整份」。** 我們會照第 13 節階段 1 的順序，一步一步做。你不會一次面對整個專案。

### 我們的協作節奏（對應第 13 節階段 1）

| 步驟 | 誰主導 | 你要出手的地方 |
|---|---|---|
| 1 骨架跑起來（Godot 開場景、灰盒佔位） | 🤖 AI | 跟著裝 Godot（AI 帶你點） |

從步驟 1 開始——**裝好 Godot、開第一個場景、放一個方塊房子、點一下讓它有反應。** 你哪天想動手，跟我說「開始做步驟 1」，我就一步步帶你，包括在哪下載、按哪個鈕、程式我來寫。做出這第一個能點的小房子，專案就正式啟動了。

## 17 可行性總表：每個功能你要做多少、AI 做不做得出來

> 📎 開工前實作三節：第 15 節（資產與門檻）→ 第 16 節（分工協作）→ **第 17 節（逐功能可行性）**。

分工是「你做美術、AI 寫程式」，所以每個功能都用同一把尺量：**你的美術負擔（在 MagicaVoxel 做幾個 voxel）／ AI 程式難度 ／ 要注意的雷**。難度標記：🟢 好做、🟡 要花時間調手感、🔴 難點或效能雷。

### 圖例

- 🟢＝標準功能，AI 寫起來很穩、一次就能到位。
- 🟡＝做得到，但要來回調整（動畫手感、互動細節），不是寫一次就完美。
- 🔴＝真正的難點或效能雷，通常已排到後面階段，MVP 不碰。

### 逐功能評估

| 功能 | 階段 | 🎨 你的美術負擔 | 🤖 AI 程式難度 | 要注意的雷 |
|---|---|---|---|---|
| **家：基礎屋＋裝飾件** | MVP | 基礎屋 ×1＋裝飾件約 5～6 件 | 🟢 疊裝飾＝依等級開關顯示，簡單 | 無 |
| **家：鄰居屋** | MVP | 0（基礎屋改色重複用） | 🟢 複製擺放 | 別擺太多，遠處點燈即可 |
| **家↔樹：同平面鏡頭平移** | MVP | 0（用現有模型） | 🟢 攝影機在同一場景內移動，不是切場景讀取 | 比做圓形星球（地形彎曲、鏡頭繞轉）簡單很多，是刻意選的低風險做法 |
| **樹：5 個生長階段** | MVP | 樹體 ×5 | 🟢 依等級換模型 | 階段切換想「長大過渡」而非硬切＝🟡，可先硬切上線再優化 |
| **樹：願望牌掛載＋定時吹走** | MVP | 願望牌 ×1～2 種 | 🟢 每許一願掛一塊，排程檢查掛滿天數就吹走 | 每天最多許 2 次願＋掛滿即吹走，天然不會掛爆，不用做疊放/群組邏輯 |
| **睡前打卡＋熄燈動畫** | MVP | 0（用燈光，非模型） | 🟢 記時間＋比對＋燈光變化 | 無，這是全 App 最單純的功能 |
| **天氣：背景＋光影** | MVP | 0（Godot 光照＋粒子） | 🟢 抓天氣代碼→切換光影 | 無 |
| **天氣：語錄** | MVP | 0（純文字） | 🟢 依天氣代碼配一句 | 要你我一起備文案庫（內容量，非技術難度） |
| **天氣：備援畫面** | MVP | 0 | 🟢 API 失敗→切中性畫面 | 一定要做，否則天氣掛了主畫面壞掉 |
| **每日開場：日期＋流星語錄** | MVP | voxel 數字 0～9＋月份字（一次做好） | 🟢 選句＋短期不重複＋浮現/飄散動畫 | 語錄庫要夠大才有流星感（內容量，非技術難度） |
| **節日語錄＋裝飾** | MVP | 節日小裝飾（想做才做） | 🟢 對照節日表換語錄/裝飾 | 農曆節日的日期換算要留意 |
| **冷啟動開場儀式** | MVP | 0（用現有素材） | 🟢 第一次打開的引導流程 | 無 |
| **純觀賞模式** | MVP | 0 | 🟢 就是不做事、讓場景動 | 無 |
| **聲音＋觸覺** | MVP | 音效素材（你找或做） | 🟢 觸發播放＋震動 | 無 |
| **塔羅：voxel 牌** | MVP | 6 張牌＋1 牌背 | 🟢 隨機抽 1 張 | 量小，比做房子簡單；是主要拉新賣點，優先做 |
| **塔羅：望向星空→寫字→射上天空→翻牌** | MVP | 0（Godot 動畫） | 🟢 轉場＋輸入框＋動畫 | 無 |
| **塔羅：牌海（先做簡單弧形排列）** | MVP | 0 | 🟢 排成一段弧、點一張抽出 | 環形星盤那種滑動聚合效果留到 Phase 3 再做，不擋 MVP |
| **回顧卡** | Phase 2 | 卡片版型（簡單） | 🟢 撈舊資料生成一張卡 | 需累積夠久資料才有東西可回顧 |
| **漂流瓶：願望飄出/收到/回祝福** | Phase 2 | 0（用現有 UI） | 🟡 隨機延遲分發＋祝福統計＋過濾檢舉 | 這是社交，要一整套防濫用機制，比單機功能重 |
| **塔羅：牌海升級成環形星盤滑動** | Phase 3 | 0 | 🟡 飄浮＋滑動轉動＋點選，要調手感 | MVP 已有簡單弧形版可用，這是體驗優化，不急 |
| **塔羅：78 張多選牌陣** | Phase 3 | 牌擴到 22～78 張 | 🔴 效能（多張 3D 同時浮動）＋多牌解讀邏輯 | 排到 Phase 3，MVP 完全不碰 |
| **漂流瓶 B 版自由回話** | Phase 3 | 0 | 🔴 自由文字＝騷擾風險，要審核/檢舉/封鎖全套 | 排到 Phase 3，社群穩了再開 |

### 白話總結

- **MVP 你要做的美術，量還是不大**：家（1 屋＋約 6 裝飾件）＋樹（5 階段＋1～2 願望牌）＋塔羅（6 張牌＋1 牌背）＋一些音效，大概 **二十來個 voxel 小物件**，天氣和動畫幾乎都是程式做、不用你雕。
- **MVP 的程式對 AI 幾乎全是 🟢**，塔羅也不例外（牌少、邏輯單純）。唯一的 🟡 是「樹長大的過渡動畫」，可以先硬切上線、之後再優化，不擋進度。
- **真正的難點集中在 Phase 2、Phase 3**：漂流瓶社交、環形星盤那種華麗牌海互動、78 張牌陣、自由回話。這些都排在後面，**你的第一個可上架版本一個都不會碰到**，但塔羅的核心體驗第一版就有。
- **結論：MVP 涵蓋主要拉新賣點（塔羅），美術量你扛得住、程式 AI 有把握。** 真正難的東西還是被分階段推到後面了，這樣既能第一時間吸引使用者，也沒有失去「先做出一個做得完、上得了架的東西」的原則。
