> 「照顧好你的小村落——家越住越暖，樹越長越大，抬頭的夜空，陪你問一件心裡的事。」

**一分鐘看懂：** 這是一個手機 App，叫「小村落」。每個使用者有一座自己的小村莊，好好過生活，村莊就會越來越美——一間家（睡前打卡，越住越溫馨）、一棵門口的樹（許願／告解，掛上 voxel 願望牌，越長越大），主畫面以中性天氣備援開始，Store MVP 再接入真實天氣作為增強效果。心裡有事，還能**抬頭望向星空抽塔羅**，問一句話、從星空牌海抽一張牌，得到溫柔的反思提示（不算命）——這是核心體驗假設，V0 就驗證，但不以付費或廣告驗證。每日開場只在 Store MVP 可選加入：每個本地日首次播放日期與一句語錄，同日再次打開直接進村落。靈魂只有一句話：**只給溫暖，不給壓力**，漏做一天不會被罵、不會扣分。

累積使用者穩定後，會再長出**漂流瓶**（願望飄給陌生人，換一份祝福）這個進階功能。技術上用 Godot＋MagicaVoxel（全世界都是 voxel 方塊風，塔羅牌也不例外）＋Supabase，全 App 純文字、不上傳圖片。

**三個階段圖例：**
- **V0 體驗驗證** — 先驗證村落、睡前打卡、許願與塔羅反思是否有人願意持續使用；以本機資料為主，不做商業化
- **MVP／Store MVP** — 補上帳號、雲端同步、刪除與必要合規頁，通過封閉測試後再送商店
- **Phase 2／3** — 累積使用者後再加漂流瓶、回顧卡、進階塔羅與商業化

> **範圍總原則：** 本手冊的世界觀可以完整保留，但開發順序以「先驗證核心體驗，再補上架必要能力」為準。V0、Store MVP 和 Phase 2／3 的資料、安全與商業規則不能混用。

## 00.5 一頁全貌：整個 App 有哪些東西、什麼時候做

白話版的全專案地圖。想知道細節再往下翻對應章節。

| 功能 | 白話說它是什麼 | 什麼時候做 | 細節看哪節 |
|---|---|---|---|
| **每日開場** | 每個本地日第一次打開時顯示日期與短語錄，可跳過；當天再次打開直接進村落 | Store MVP，可選 | 02.5 |
| **家 + 睡前打卡** | 按「睡了」熄燈入夜，準時累積讓家逐步變暖 | V0 | 02、15 |
| **樹 + 許願/告解** | 寫下私密願望或煩惱，樹和願望牌逐步成長 | V0 | 05、15 |

| **塔羅反思牌** | 抬頭望向星空，抽一張 voxel 牌，閱讀反思提示；不提供占卜答案 | V0 | 04 |
| **漂流瓶** | 你的願望飄給陌生人、收到別人的願望回一份祝福（先只能點預設祝福，只收願望、不含告解） | Phase 2 | 05 |
| **回顧卡** | 「一年前的今天你許下…」自動生成回顧，適合分享 | Phase 2 | 02.5 |
| **多張牌陣、漂流瓶自由回話、告解加入漂流瓶、塔羅牌主題套組** | 塔羅升級成選 3 張；漂流瓶祝福能寫一句話；告解也能飄出去；塔羅牌整套換主題造型 | Phase 3 | 04、05、07 |

**三個階段一句話**

- **V0 體驗驗證（先做、先測）：** 一座只有自己的村落——家、樹、睡前打卡、私密許願、每日反思牌。以本機資料為主，不做廣告、訂閱、星光商店、漂流瓶或複雜雲端同步。目標是驗證核心體驗與留存，不是直接送商店。
- **MVP／Store MVP（通過封閉測試後上架）：** 在 V0 核心體驗穩定後，補上帳號、雲端同步、資料刪除、手動城市天氣、必要隱私與合規頁，再決定是否送 App Store／Google Play。MVP 不開放公開內容或陌生人互動。
- **Phase 2（累積使用者後）：** 加入漂流瓶願望交換與回顧卡。漂流瓶上線前，必須先完成內容過濾、略過、檢舉、封鎖和人工處理流程。
- **Phase 3（穩定後）：** 再評估漂流瓶自由回話、22 張大阿爾克那、多張牌陣、塔羅牌主題套組與商業化；任何自由文字互動都不能只靠關鍵字過濾就上線。

### 你（美術）要做的東西，一句話

**V0** 先做：浮空島基座、基礎家、樹的 3 個階段、1 種願望牌、簡化瀑布、6 張 voxel 塔羅牌與牌背、基本燈光粒子和音效。**Store MVP** 再補：樹的完整 5 個階段、家裝飾、鄰居島、日期字體、天氣粒子和可跳過的每日開場。複雜牌海、漂流瓶、商店和付費素材不屬於首發資產。

## 01 概念

- **核心體驗：** 使用者擁有一個自己的小村落。打開 App 先停在家；V0 使用中性天氣備援，Store MVP 可選接入真實天氣作為增強效果。想許願或想放下什麼，就走出去門口的樹；心裡有事，抬頭望向星空抽塔羅、問一件心裡的事（V0 就驗證這個核心體驗，但不做預測或付費抽牌）；晚上回到家，按「睡了」，熄燈入夜。
- **一句話定位：** 「照顧好你的小村落——家越住越暖，樹越長越大，抬頭的夜空，陪你問一件心裡的事。」
- **為什麼是村落，不是三個分開的 App：** 三個原方向（許願、情緒抒發、睡眠）的核心機制其實是同一套哲學的三種表現——行為直接長出畫面、只給正回饋、一句話能講完、夜晚安靜留白的調性。合併成一個世界後，護城河也更集中、更難被抄。
- **明確不做什麼：** 不宣稱醫療／心理治療效果、不做睡眠或情緒的醫療級診斷、不做評分量表、不做精準睡眠偵測、不做隨機抽獎式付費（塔羅抽牌也不例外）、不宣稱塔羅有真實占卜效果、**不做留言／回覆、不做排行榜或熱門榜**（這是漂流瓶避免變炎上戰場的核心紅線）。這幾條貫穿後面所有法律與文案決定。
- **純文字、不上圖片：** 所有使用者輸入（許願、告解、塔羅想問的問題）都只用文字。理由：貼合安靜留白的調性、繞開 Firebase Storage 免費方案的雷、大幅降低審核負擔。塔羅牌面走 voxel 拼出的簡單符號，不做插畫。

## 01.5 MVP 與分階段規劃

合併成一個世界之後，最大的風險是「一開工就要同時做完所有東西」。所以分成 V0 體驗驗證、MVP／Store MVP、Phase 2 和 Phase 3：先驗證核心體驗，再補齊能上架的必要能力，最後才逐步長出社交與進階功能。

> 📌 **塔羅提早進 V0：** 塔羅反思是主要拉新假設，但不應直接用「付費抽牌」驗證。V0 先做每日一張反思牌：問題欄位可選填、只在本機暫存，回應不解析問題內容，也不提供預測或答案。等核心體驗通過測試後，Store MVP 再評估是否加入雲端紀錄與更完整的提問流程。

| 階段 | 做什麼 | 為什麼放這裡 |
|---|---|---|
| **V0 體驗驗證** | 本機村落：家（睡前打卡）＋樹（私密許願／告解）＋每日一張反思牌＋中性天氣備援 | 先驗證使用者是否願意回來，不把後台、廣告、訂閱和社交風險帶進原型 |
| **MVP／Store MVP** | 在 V0 基礎上加入帳號、雲端同步、資料刪除、手動城市天氣、必要隱私／合規頁與正式測試 | 這才是可考慮送商店的版本；沒有公開內容，但私密文字仍是敏感資料 |
| **Phase 2** | 漂流瓶願望交換（A 版預設祝福）＋回顧卡 | 社交要有足夠使用者才好玩；上線前先完成內容治理和處理流程 |
| **Phase 3** | 自由回話、告解外流、22 張牌、多張牌陣、塔羅主題套組與商業化 | 自由文字互動、進階塔羅和付費權益的風險與工程量較高，不能提前塞進首發 |

### 為什麼漂流瓶不放 MVP

漂流瓶要好玩的前提是「有夠多人在許願」。第一天上線只有零星使用者，系統飄不出足夠的別人的願望，體驗反而最差。先做穩單機村落，累積使用者，再開漂流瓶，一上線體驗就是好的。

### V0／Store MVP 的紅線

V0 與 Store MVP 階段，樹的許願／告解**只有自己看得到，完全不做任何公開或分享**；塔羅問題即使在 Store MVP 保存，也永遠只屬於本人，不飄出去、不進公開內容。這代表沒有公開社交內容治理，但不代表沒有隱私與敏感資料責任：私密文字仍必須有明確的存取權限、刪除流程、備份清除規則與不進普通日誌的限制。

## 02 村落結構與場景動線

> 📐 **架構定案（美術方向定案後更新：從平面地面改為浮空島）：** 家與門口的樹站在同一座浮空島上，島的邊緣垂著瀑布，島懸在天空／夜空中。這不是重新踩到當初被否決的「圓形星球」那個坑——島頂仍然是一片平面，鏡頭一樣在平面上左右平移，攝影機邏輯跟最初「同一片地面＋鏡頭平移」的判斷完全相容，難度沒有拉高；改變的只是這片地面的邊界，從「模糊消失在地平線」換成「看得見的懸崖＋瀑布」。**鄰居的房子不放在同一座島上**，改成遠方另外漂浮的小島，隨 house_level 解鎖陸續點亮、用景深模糊處理成朦朧的背景光點（見下方「鄰居島」）。

村落結構：

| 區域 | 對應機制 | 主動作 | 累積的東西 |
|---|---|---|---|
| 家（浮空島上） | 睡前打卡＋塔羅反思 | 睡前按「睡了」／抬頭望向星空抽牌 | 屋子越住越溫馨、燈火越多 |
| 門口的樹（同一座島，鏡頭平移過去） | 許願／告解 | 許願／告解 | 樹隨心願長大、掛滿願望牌 |
| 鄰居島（遠景背景，依 house_level 解鎖） | 純視覺回饋，不可互動、不可前往 | 無主動作，僅背景點綴 | house_level 越高，遠方陸續亮起越多座小島 |

### 鄰居島（遠景背景）

鄰居的房子改成放在主島以外、遠方另外漂浮的小島上，永遠去不了、也不需要去——本來手冊裡鄰居就只是「證明村落越來越熱鬧」的視覺回饋，不是可互動的空間，換成浮空島架構後這個定位完全沒變。因為永遠隔著一段距離看，鄰居島可以**刻意做得很簡化、再用 Godot 的景深後製模糊掉**：越遠越朦朧本來就是真實的光學現象，不用花力氣雕細節，省下來的工時留給主島雕琢。House_level 每解鎖一戶新鄰居，遠方就多亮起一座小島（見第 15 節），跟原本「鄰居燈越來越多」的成長邏輯一致，只是從「同一片地面上的房子」換成「另一座漂浮的島」。**MVP／Phase 2 都不用架橋連接鄰居島**——如果以後想做「拜訪朋友」這類社交功能，架橋是很自然的視覺語言，先記在待決事項的未來擴充裡。

動線不是一鏡到底，而是以家為中樞：

1. **打開 App → 停在家前。** 若 Store MVP 已啟用每日開場，先播放當天首次開場；完成或跳過後，看得到當下天氣備援或天氣效果，遠方鄰居島只在 Store MVP 資產完成後顯示。
2. **想許願／告解 → 點樹，鏡頭平移過去。** 同一座島、同一場天氣，沒有讀取轉場；完成儀式後點回家，鏡頭再平移回去。
3. **想問塔羅 → 抬頭望向星空。** 這是唯一真正的「轉場」——抽牌夜空是脫離島面的專屬星空，固定不跟著真實天氣變，用「抬頭、畫面上抬淡出」帶過去，跟平面上的鏡頭平移是兩種不同的心理切換（見第 04 節）。
4. **晚上 → 回到家前。** 按「睡了」，熄燈入夜，一天結束。

家跟樹共用同一座島、同一套光影，鏡頭平移本身就有走過去的儀式感，不需要額外做場景轉場動畫；抽牌夜空則保留單獨的「抬頭」轉場。沒空的話，只做晚安打卡也完全成立——不強迫使用者每件事都做。天氣效果是 Store MVP 的可選增強，V0 使用中性備援；日夜燈火規則在任何版本都可以獨立運作。

## 02.5 陪伴體驗（讓村落不只是工具）

這幾個都是低成本、高情感的細節，是這類 App（Forest、Finch）留得住人的關鍵，不是可有可無的加分項。

### 冷啟動（V0／Store MVP 必做）

新使用者第一次打開要有開場儀式——引導做一個立即有回應的小動作（種下第一棵樹／點亮家的第一盞燈），同時完成體驗定位說明、免責聲明、設定目標就寢時間。第一天的村落不該全空，給一個有基礎溫度的起點。

### 每日開場：日期＋流星語錄（Store MVP 可選）

每日開場是氣氛功能，不得阻塞核心操作。V0 不要求製作完整每日開場；若要在 V0 測試氛圍，可用可跳過的短版，不保存狀態。Store MVP 定案為：**每個本地日第一次打開 App 播放完整開場，同一天再次打開直接進村落**，使用者可以從設定或角落入口手動重播。動畫中途關閉或回到背景時沿用原語錄，不重新抽取。

### 每日開場細節

**上方是穩定的日期，下方是一句如流星般短暫的語錄**。片頭使用跟真實時段無關的中性柔光；動畫結束後才淡入當下時段與天氣。這個開場最多播放一次，不得阻擋使用者直接進入家、樹、塔羅或設定。
- **語錄（流星般浮現→飄散）：** 日期下方，一道微光從夜空斜劃過（流星），語錄文字隨著光逐字寫出來，停留幾秒讓人讀完，接著化成一小撮光點往上飄散、淡出消失。
- **看過就沒了：** 這一句只屬於這一次打開，A 版完全不留、不可回看——刻意的，要的就是「錯過就抓不回」的珍惜感。
- **語錄怎麼挑：** 依當下天氣（晴／雨／陰）、時段（清晨／夜晚）、以及今天是不是節日，決定從哪個池子抽；抽完短期內記住、不重複，維持每次都新鮮的流星感。情人節、過年這類節日可配專屬語錄與小裝飾（愛心光點、小燈籠）。
- **跟天氣語錄共用系統：** 這套語錄跟第 03 節「天氣語錄」是同一套內容系統，只是每日開場多了日期顯示、節日判斷、流星動畫、看過消失，不用做兩套。
- **語氣紅線：** 維持「陪伴、反思」的語氣，不寫成運勢預測（不出現「今天諸事不宜」「財運差」），跟塔羅的紅線一致——不做吉凶、不做預測，只做溫柔的一句話。

### 早晨燈火：晨光接手，不是把家的溫度消除（V0／Store MVP 必做）

清晨的燈火規則要和「家的成長等級」分開計算——**house_level 只代表永久累積的成長成果，不代表目前燈是否亮著**，目前燈火亮度依時段、天氣即時計算（詳見第 09、15 節）。

- **家已經變暖的部分會保留：** 窗戶、門口小燈、鄰居房屋、掛飾等已解鎖的模型不會因為天亮而消失，使用者早上仍然看得出自己的家變好了。
- **夜間照明會退到背景：** 窗戶和門口燈在清晨逐漸降低亮度，門口燈、燈籠大多熄滅；窗戶保留一點很淡的暖色余光，讓畫面仍有家的溫度，但不再像夜晚一樣明亮。
- **鄰居島燈火也逐漸熄滅：** 鄰居島保留，只有發光效果降低或關閉，不會讓村落看起來像整個消失。
- **晨光成為主要光源：** 天空、地面和樹木逐步轉為清晨的柔和光線；雨天、陰天仍以真實天氣決定色調，不強行顯示晴天。

**時段燈火基準（第一版可直接採用）：**

| 時段 | 場景主光源 | 家與鄰居島的燈火 |
|---|---|---|
| 清晨 05:00～08:00 | 深藍逐步轉為柔和晨光 | 窗戶淡亮，門口燈與燈籠逐步熄滅 |
| 白天 08:00～17:00 | 當下真實天氣的日間光線 | 基本關閉，只保留模型與極淡余光 |
| 黃昏 17:00～20:00 | 暖色夕光逐步轉入靛夜 | 窗戶、門口燈和鄰居島燈逐步亮起 |
| 夜晚 20:00～05:00 | 靛夜、月光與星點 | 家與鄰居島燈火成為主要視覺焦點 |

這些時間只是第一版的畫面分段，不用模擬精確日出日落，之後可依使用者所在城市或實際體驗調整。**真實天氣決定當下的天色與粒子，時段決定燈火亮度，兩者不互相覆蓋。**

**「家變暖」與「今晚有沒有熄燈」是兩件事：** `house_level` 由累積準時就寢天數推進、只會前進；`is_sleeping` 只在按「睡了」後的熄燈動畫期間使用，動畫結束即清除，不用來判斷隔天是否完成打卡。使用者漏睡一天時，家不降級、鄰居不消失、已解鎖裝飾不隱藏，只是不增加當天的準時累積。

### 純觀賞模式（V0／Store MVP）

什麼都不用做，只是看著自己的村落——燈籠飄、天氣變化、風吹葉、瀑布流動、鄰居島的燈火。讓 App 從「工具」變成「一個能待著的地方」。

### 回顧卡（Phase 2）

「一年前的今天」「三個月前你許的這個願，實現了嗎？」——這類 App 最天然的分享來源，需要累積夠久的資料才有東西可回顧。

### 聲音＋觸覺（V0／Store MVP）

許願時星光匯聚的「叮」、熄燈入夜的音效、抽塔羅的沙沙聲，配合輕微震動。成本低、效果強。

## 03 天氣：真實天氣作為增強效果＋通用備援

Store MVP 的天氣效果以手動城市或使用者選擇的定位結果為來源；V0 不依賴網路，使用中性備援。

- 串接手機定位或使用者設定城市的真實天氣 API，決定村落當下的光影與效果（晴朗／多雲／陣雨…）——這是唯一的視覺依據。
- **時段只控制燈火與日夜過渡，不取代真實天氣：** 清晨、白天、黃昏、夜晚決定家與鄰居燈火的亮度和開關；真實天氣決定天空色調、雲雨粒子與日間光線。兩層一起作用，例如「清晨下雨」仍然是雨天的清晨，不會被固定的晴天晨光覆蓋（詳見下方「時段與燈火的分工」）。
- 在家的畫面上，搭配一句**跟當下真實天氣呼應的語錄**，用文字傳達心情共鳴，而不是讓使用者自己選一個情緒圖示。
- 這句語錄跟每日開場共用內容格式，但不要求 V0 一次完成大量內容。V0 先提供少量通用語錄；Store MVP 再補天氣標籤、時段標籤與節日內容。
- 陰雨天一樣要做得美、不能有懲罰感。
- **天氣是增強效果，不是核心依賴：** 沒有網路、拒絕定位或 API 失敗時，使用者仍能完成村落、睡前打卡、許願與塔羅反思。
- 定位僅用於天氣顯示，需在權限說明中清楚告知；預設優先提供手動選城市，不能把定位當成進入 App 的必要條件。天氣 API 金鑰只能放在服務端或受保護的代理層。

### 時段與燈火的分工（V0／Store MVP 必做）

家裡的燈火不是全天候固定亮度，而是依當下時段自然過渡。早上不是把家的成長成果清除，而是讓晨光接手夜間照明（時段表見第 02.5 節「早晨燈火」）。第一版先用固定時段即可，不需要計算精確日出日落；時段只調整燈火亮度和日夜過渡，天氣 API 仍然負責晴、陰、雨等當下天氣效果。若 API 暫時失敗，只替代天氣造成的天空與粒子效果，時段燈火規則仍照常運作——例如白天備援時仍是白天，不會強行變成黃昏。

### 天氣拿不到時的備援（V0／Store MVP 必做）

天氣 API 掛掉、超過免費額度、使用者拒絕定位或沒有網路時，主畫面**不能壞掉或空白**。先使用尚未過期的 `WeatherSnapshot`；沒有可用快照時，依當下時段顯示中性預設畫面：白天用柔和中性日光，黃昏／夜晚用柔和夕光／星空，不強調特定天氣。配一句不提天氣的通用語錄。天氣恢復後再更新視覺，不影響睡眠紀錄、樹的成長或塔羅反思。

## 04 塔羅：望向星空，做一張今日反思牌（V0／Store MVP）

塔羅在本產品中是**自我反思與文字陪伴工具，不是占卜、預測、診斷或治療**。V0 先驗證「望向星空→抽一張牌→讀一段反思提示」是否有人願意使用；Store MVP 再決定是否保存完整抽牌紀錄。不要用付費、廣告或無限次數來驗證塔羅價值。

### 呈現：望向星空抽牌（核心儀式）

塔羅入口不在桌上、也不在選單，而是**抬頭望向夜空**——呼應「向星空提問、從宇宙接收訊息」的意象，跟貨幣「星光」、跟整個夜晚安靜的調性完全連起來。

1. **抬頭 → 出現寫字的牌：** 在家的畫面往上看（或點一顆微亮的星），畫面上抬、家淡出，轉場到一片專屬的抽牌夜空（靛夜打底、星點燈金）。夜空中浮現一塊 voxel 牌，牌面就是輸入區，寫下今天想問的事。
2. **寫完 → 射上天空：** 送出後，牌化成一道星光射向夜空深處。
3. **牌海浮現 → 挑牌：** V0 與 Store MVP 只做一段簡單弧形牌海，牌背朝上、發著微光，點選一張抽出；環形星盤和滑動聚合留到 Phase 3。
4. **翻牌 → 解讀：** 抽出的牌飛到眼前、旋轉翻正，voxel 牌面拼出符號（太陽／星星／月亮），下方顯示反思提示回應＋正向關鍵字。
5. **收尾：** 看完點一下，牌化成星光散回夜空，畫面落回家。

> **抽牌夜空是固定的專屬星空，不跟著真實天氣變**——就算現實在下雨，抽牌時一樣是滿天星。儀式時刻要純粹、不被天氣干擾，所以它跟第 03 節那個會變天氣的背景層是兩回事，互不影響。

### 牌的內容與數量（分階段）

- **牌是 voxel 立體牌：** 有厚度、能翻面、能發光，牌面用 voxel 拼出簡單符號（太陽、星星、月亮…），跟整個世界統一成方塊風。不做平面 SVG、也不做插畫。
- **V0 的牌與提問：** 先做 6 張正向牌（太陽／星星／月亮／力量／節制／世界），每天預設一張反思牌。問題欄位可選填；若使用者填寫，V0 只在本機暫存，**不解析、不作為答案依據、不把問題與牌說成因果關係**。Store MVP 若要雲端保存，必須先完成隱私說明、刪除流程與敏感資料處理規格。
- **回應文字：** 只提供反思提示與行動方向，不提供預測、保證、診斷、治療或健康／投資／法律建議。牌名可以保留傳統名稱，但不要用「抽到這張就會……」的句式。
- **提問次數與廣告：** V0 先不做廣告換抽牌、訂閱無限或付費抽牌，避免還沒驗證核心體驗就把塔羅變成變現機制。每日次數只在玩家完成抽牌並進入最終結果畫面時才消耗；只寫問題、進入牌海、選牌前返回、或動畫中途離開都不算使用一次。Store MVP 之後可以評估「每日 1 次免費反思 + 看 1 次自願廣告增加 1 次」，但文案必須寫成「多一次反思」而不是「更準、更好、更有用的結果」；每日可加次數要設上限，且不能用廣告或付費改變牌義、結果池或危機提示。若未來增加額度，必須重新檢查商店規則與地方法律，且核心反思功能不可被付費結果化。
- **呈現方式：** V0 與 Store MVP 只做固定星空、簡單弧形牌海、點選一張、翻牌和返回；環形星盤、多張牌陣、逆位和 22 張以上牌組留到 Phase 3。

### ⭐ 重點定案：真實時間層 vs 塔羅回響層

> **定案原則：真實時間控制世界底色，塔羅只做局部回響。** 早晨抽到星星，不把世界變成夜晚；夜晚抽到太陽，也不把天空變成白天。真實早晚、天氣與燈火規則仍由第 03 節和第 02.5 節控制；塔羅結果只疊加在村落裡的局部光、粒子、物件狀態、語錄和短暫異象上。

設計分層：

| 層級 | 負責什麼 | 不做什麼 |
|---|---|---|
| 真實時間層 | 清晨／白天／黃昏／夜晚的大環境、主光源、天空明暗、家與鄰居島燈火基準 | 不因塔羅結果被整體覆蓋 |
| 真實天氣層 | 晴、陰、雨、雲、霧等天空色調、粒子和環境氛圍 | 不代表使用者狀態，也不改變抽牌結果 |
| 塔羅回響層 | 抽牌後留下的局部細節：光點、微粒、語錄、小物件、局部燈光與短暫動畫 | 不把白天改成夜晚，不把夜晚改成白天，不破壞真實時間 |

也就是：

```text
apply_time_of_day(time_phase)
apply_weather(weather_snapshot)
apply_tarot_echo(last_tarot_card, time_phase)
```

塔羅牌的意義不是「改天象」，而是「村子記得你抽到了什麼」。

| 塔羅牌 | 核心情緒 | 早晨／白天呈現 | 黃昏／夜晚呈現 | 未來 3D 美術方向 |
|---|---|---|---|---|
| 太陽 | 被照亮、變暖 | 屋頂、窗邊或樹梢有一點金色邊光；白天材質略暖 | 夜晚不出太陽，改成窗戶與門口像小太陽一樣更暖 | 局部暖光、窗燈增強、金色邊緣光 |
| 星星 | 希望、遠方微光 | 白天只留很淡的星塵或樹上微光，不做滿天星 | 夜晚可以明顯多一顆星、星光閃爍或短暫星軌 | 小粒子、遠處亮點、樹枝上的星光 |
| 月亮 | 安靜、沉澱 | 清晨或白天用柔霧、低飽和、較軟陰影表現 | 夜晚加強銀藍月光與地面柔光 | 薄霧、銀藍補光、柔化陰影 |
| 力量 | 穩定、守住 | 家門口或屋旁出現穩定、不閃爍的守護光 | 夜晚窗燈更穩，像替使用者守著家 | 固定暖光、門口護符、小型守護燈 |
| 節制 | 調和、節奏回來 | 風、水、樹葉動畫更平順，畫面節奏放慢 | 夜晚燈光呼吸更慢，冷暖過渡更柔 | 水流／瀑布／風動動畫速度調整 |
| 世界 | 完成、連結、告一段落 | 遠方島嶼輪廓更清楚，村落邊界感變開闊 | 遠方鄰居島亮一下，像完成一段路後得到回應 | 遠方島光、路徑光、範圍擴張感 |

範例判斷：

- **早上 + 月亮：** 不是變晚上，而是晨光中多一點薄霧，陰影更柔，村子更安靜。
- **晚上 + 太陽：** 不是天亮，而是家裡像有小太陽，窗燈與門口光更暖。
- **白天 + 星星：** 不是滿天星，而是樹枝或空氣裡殘留一點很淡的星光。

這條規則的目的，是避免塔羅特效跟真實時段、真實天氣打架。美術與程式都應把塔羅效果做成「局部回響」，不是整體換天。

### V0 實作備忘：塔羅場景交互與狀態同步

這段記錄 V0 原型已踩過、後續維護要保留的實作規則；不是美術規格，而是避免場景互動再次失效的工程備忘。

#### 場景與腳本掛載

- `scenes/TarotSky.tscn` 的根節點 `TarotSky` 必須掛上 `res://scripts/tarot_sky.gd`。若根節點腳本掛載遺失，畫面仍會顯示，但 `SendButton`、`BackButton`、抽牌流程全部不會生效，且不一定會有明顯錯誤日誌。
- `scenes/Main.tscn` 的 `Main` 根節點必須掛 `res://scripts/village.gd`，`Camera3D` 必須掛 `res://scripts/camera_pan.gd`，並設定 `house_view` 與 `tree_view`。這是家／樹鏡頭切換與進入塔羅的必要條件。
- 重新用 Godot MCP 或編輯器保存場景後，要抽查一次關鍵節點的 `script = ExtResource(...)` 是否還在，避免「場景能打開，但互動全失效」。

#### 按鈕與輸入規則

- 塔羅輸入階段 `WRITING`：`SendButton` 送出問題；問題空白時不進入抽牌，提示使用者先寫下一件想問的事。
- `BackButton` 是明確出口，至少在 `WRITING`、`CARD_SEA`、`RESULT` 顯示；`TRAVELING` 與 `REVEALING` 動畫中暫時隱藏，避免重複觸發轉場。
- 返回主場景要有 `_returning` 防重入旗標，避免連點回家造成多次 `change_scene_to_file`。
- 手勢和鍵盤可以保留為輔助入口；塔羅場景不常駐「回家」按鈕，避免跟上滑返回重複、破壞抽牌夜空的沉浸感。塔羅場景以向上滑動回家為主，與主場景的滑動操作保持一致；第一次進入場景時短暫顯示一次「向上滑動可回家」，提示使用底部安全區的全局固定位置，淡出後不常駐，避免放在結果文字區內被牌義內容覆蓋。

#### Autoload 與跨場景狀態

- 腳本內不要直接依賴裸全域名 `SceneTransition` 或 `GameState`；優先使用 `get_node("/root/SceneTransition")`、`get_node("/root/GameState")`。這樣在 MCP 保存、獨立載入場景或編譯順序不同時，比較不會出現找不到 Autoload 的問題。
- 塔羅抽牌結果寫入 `GameState`，目前保留這些欄位：
  - `last_tarot_card`
  - `last_tarot_keyword`
  - `last_tarot_question`
  - `last_tarot_action`
  - `last_tarot_village_effect`
- 主場景讀取 `last_tarot_village_effect` 顯示「星空回來了：...」這類村莊回應。這是 V0 的非美術版視覺連通；未來 3D 美術完成後，可改由同一份狀態驅動局部光、粒子、遠景島光或環境節奏。

#### Godot 物理與動畫注意事項

- 塔羅牌可點擊載體使用 `Area3D`。動畫中不要把 `Area3D.scale` 縮到 `Vector3.ZERO`，Jolt Physics 會出現 singular transform / invalid transform 警告。若要讓未選中的牌視覺消失，縮到 `Vector3.ONE * 0.01` 即可。
- 牌面美術未完成前，可先用 BoxMesh 與材質光效驗證流程；正式美術接入後，仍應保留「牌背朝上、點選一張、翻牌、結果回到村莊狀態」的流程骨架。
- `TarotSky.tscn` 的保存驗證標準不是只有「Godot 沒報錯」，還要確認根節點腳本仍在、按鈕能觸發、主場景讀得到 `GameState`。

### 安全與危機處理

- **產品定位：** 所有塔羅頁面、牌名、回應與商店文案都必須明確寫成「自我反思提示」，不可暗示真實占卜、命運預測、心理治療或醫療效果。
- **私密文字：** V0 問題只存本機；Store MVP 的雲端保存必須遵守第 09 節的資料權限和刪除規則。私密不等於沒有隱私責任，不得把原文寫入一般分析事件、錯誤日誌或客服截圖。
- **高風險主題：** 牌面回應不得對自傷、自殺、健康、用藥、法律、投資或人身安全給出判斷。遇到這些主題時，先顯示中性的求助／專業資源入口，不把塔羅結果當成處理方式。
- **危機偵測：** 若啟用本機關鍵字偵測，只用來顯示求助資源，不上傳、不留存、不改變抽牌結果。需要在首次使用和隱私說明中告知，並允許使用者關閉非必要的提示。
- **資源管理：** 求助資源要依使用者主動選擇的地區顯示，包含緊急服務、危機專線與一般支持資源；上線前由專人確認，並設定定期檢查日期。App 不承諾即時監控，也不暗示有人會主動介入。
- **抽牌流程：** 任何危機提示都不能被安排在塔羅結果之後，讓使用者誤以為牌面是危機建議。必要時先中止或跳過抽牌，再顯示資源與離開入口。

## 05 內容與安全設計（樹：許願／告解＋漂流瓶）

沿用原許願池手冊的原則：私密書寫完全自由，公開才需要安全機制。這條原則對樹的許願／告解、以及塔羅的問題輸入都適用。

### 基本規則

- **V0 的許願與告解：** 不做每日額度、不接廣告、不花星光。使用者可以在合理字數上限內自由記錄；V0 只存在本機，刪除後立即從本機畫面移除。
- **Store MVP 的許願與告解：** 仍不以付費或廣告限制核心書寫。可設定防止誤操作的合理字數上限：許願最多 20 字客製內容，告解最多 200 字。兩者都只對本人可見，不公開、不分享、不進漂流瓶。
- **許願：** 分類模板（感情／事業／健康／財富／人際／其他）＋最多 20 字客製內容。Phase 2 起才評估「讓願望飄出去」，並在正式開放前完成內容治理規格。
- **消災告解：** 私密自由書寫，但不能把它描述成治療、消除問題或保證改善。Phase 3 才評估是否允許外流；在此之前只做私密書寫。
- **常態求助資源入口：** App 內設定頁要有常態顯示的求助資源；它不能只靠關鍵字觸發，也不能放在付費牆後。
- **危機內容處理：** 若啟用本機提示，偵測只用來顯示資源，不上傳、不留存、不影響一般內容保存。提示不能把塔羅結果當成危機建議；若判定需要立即協助，先顯示資源和離開入口，再由使用者自行決定是否繼續書寫。

### 願望牌的去留（固定天數後被風吹走）

每塊願望牌掛上樹枝滿一段時間（初版建議 **5～7 天**）後，會被風吹走——不是消失，是「心願被送出去」的正面收尾，配一句類似「這個心願已經飄了七天，風要帶它去遠方了」的提示。

- **樹的成長不受影響：** tree_level 靠累積總願望數（永久紀錄，只會往上），不是「牌還掛著幾塊」；牌被吹走不會讓樹變小或降級。
- **想回顧舊願望：** 靠回顧卡（見 02.5 節），不是靠樹上還掛著那塊牌。
- **天然解決掛牌過多：** 願望牌掛滿 5～7 天後會被吹走，樹上同時存在的牌數量自然受到控制；不需要額外做每日額度、疊放或群組邏輯。
- **Phase 2 加分項（先預留欄位）：** 若願望被送進漂流瓶、收到別人的祝福，可以讓它提早被吹走，通知裡把兩件事一起講，例如「這個心願已經被 3 個人聽見了，風要把它帶走了」。

### 漂流瓶願望交換（Phase 2，取代傳統公開心願牆）

不做一整面攤開來滑的「公開心願牆」，改成**一對一、雙向的善意交換**——像收到一封漂流瓶：

- **收：** 每天最多收到少數幾個（例如 1～3 個）陌生人飄來的願望，一次只看一個，讀完可以送出一份祝福。
- **送：** 使用者自己選擇要不要讓某個願望飄出去；飄出去的願望會隨機、延遲地分發給其他人，自己也會收到別人回的祝福數。
- **為什麼更安全：** 沒有一整面牆可以滑，就沒有比較、沒有排行榜、沒有炎上。一次只給你看一個願望，只能給善意、給不了惡意——避開 Secret、Whisper、Yik Yak 死於「匿名＋自由留言＋排名」的教訓。

**祝福的形式，分階段開放：**

| 階段 | 祝福的形式 |
|---|---|
| Phase 2（A 版） | 只能送預設祝福（為你加油／給你力量／抱抱）。沒有自由文字，但仍要有內容過濾、略過、檢舉、封鎖和人工處理流程 |
| Phase 3（B 版） | 預設祝福＋一句自由回話，需配套關鍵字過濾＋檢舉機制＋封鎖 |

### 漂流瓶安全層（Phase 2 起）

願望「飄出去」時要跑一次關鍵字過濾；不開放留言／回覆串、不做排行榜；願望分發延遲＋打散，不即時、不可回溯到特定人；每人每日「飄出／收到」都設上限；提供檢舉／不想再收到這類的入口。

## 06 法律風險備忘

以台灣為主的初步整理，**不是正式法律意見**，正式上線前建議找律師看過條款與文案。用白話說明每條「怕的是什麼、我們怎麼避開」。

### 一直都要守的（V0／Store MVP 就適用）

| 怕什麼 | 白話說明 | 我們怎麼做 |
|---|---|---|
| 說塔羅／消災「真的有效」 | 若講得像真能算命、真能消災，會被當成不實廣告 | 文案定位成「情緒抒發與反思工具」，不做效果宣稱；不出現「準」「會／不會」這種斷言 |
| 付費抽卡 | 花錢隨機抽東西＝賭博性質，是刑事紅線 | 絕對不做付費抽卡，塔羅也不例外 |
| 使用者刪不掉自己的資料 | 法律規定人有權要求刪除自己的個資 | 提供單筆刪除和刪除帳號入口；確認後立即停止產品查詢與本機顯示，後台備份與第三方服務的清除期限依隱私政策和適用法律執行 |
| 定位權限 | 為了抓天氣要用定位，若沒講清楚會被質疑亂拿位置 | 講明「定位只用來顯示天氣」，並提供「手動選城市」取代定位 |
| 未成年人課金 | 未成年亂刷錢，交易效力有爭議 | 條款寫明，並用 App Store／Google Play 既有的家長／年齡機制 |
| 危機內容沒好好處理 | 有人寫下想不開的話，平台放著不管會有道德與究責風險 | 設定頁常態放求助資源；偵測到危機字眼時，先顯示地區化求助資源和離開入口，再由使用者自行決定是否繼續，不把塔羅結果當成建議 |

### Phase 2 開漂流瓶後，額外要守的（社交才有的風險）

漂流瓶＝把 A 寫的東西送到 B 眼前，等於平台在「散布使用者產生的內容」，多了幾條原本單機時沒有的風險：

| 怕什麼 | 白話說明 | 我們怎麼做 |
|---|---|---|
| 你收到別人的不當內容 | 飄來的願望可能有色情、辱罵、廣告、仇恨言論，平台推給你就有責任 | 願望「飄出去」前先跑關鍵字過濾；每則都能一鍵略過並檢舉；累積被檢舉的內容自動下架 |
| 別人的內容洩漏第三人個資 | 有人在願望裡寫別人的真名、電話、住址 | 條款明訂不得張貼他人個資；過濾＋檢舉一起擋 |
| 未成年接觸到陌生人內容 | 有陌生人互動的 App，各國對保護未成年要求特別高 | 明確標示年齡分級；漂流瓶內容經過過濾；提供檢舉與封鎖 |
| App 商店審查卡關 | 「使用者產生內容＋陌生人互動」是商店審查的重點，沒做防護會被退件 | 上線前備好三件套：內容過濾、檢舉、封鎖／略過；審查表單據實說明 |
| Phase 3 自由回話的騷擾風險 | 一旦能寫字給特定的人，就等於陌生人私訊，騷擾／性騷擾風險大增 | 這是 Phase 3 才開；開之前必須先有成熟的過濾＋檢舉＋封鎖機制 |

**法律與安全結論：** V0／Store MVP 不開放公開內容或陌生人互動，但仍要把私密文字視為敏感資料，完成資料最小化、權限、刪除和危機資源規格。Phase 2 開漂流瓶後，才增加內容過濾、略過、檢舉、封鎖、人工處理和未成年人保護等社交治理要求。本文不是正式法律意見；上線前仍需按目標地區請專業人士檢查隱私、塔羅、危機內容、廣告和商店文案。

## 07 商業模式（Phase 3 再評估）

**V0 和 Store MVP 不做廣告、訂閱、星光、商店或付費額度。** 先用固定解鎖或測試開關驗證核心體驗，避免把抽牌、告解和成長綁上付款，也避免在核心價值還沒有驗證前引入交易、退款和多裝置同步風險。

### 未來商業化原則

- **核心體驗不因付費變成更準、更有效或更能解決問題。** 付費只能購買外觀、音效或去廣告，不能購買塔羅答案、危機資源、睡眠判定或成長速度。
- **不做付費抽卡、隨機付費獎勵或用星光換抽牌結果。** 塔羅牌是固定內容，不因付款增加「命中率」或改變結果。
- **若重新加入額度限制，必須先定義免費基礎額度、離線行為、重複廣告回調、退款、撤銷和多設備同步。** 訂閱狀態以 Apple／Google 的購買驗證結果為準，不能相信客戶端自行上傳的 `is_subscribed`。
- **告解和危機相關功能不放在付費牆後，也不以無限額度鼓勵大量提交敏感文字。**
- **廣告若日後加入，只能是可跳過的自願獎勵廣告，不得在抽牌或危機提示中插入，不得把看廣告描述成獲得更好的結果。**

### V0／Store MVP 的替代方案

- 裝飾先用固定測試解鎖，不建立 `currency_balance`、`Transaction`、`ShopItem` 的正式交易流程。
- 不請求廣告 SDK 權限，不做簽到獎勵，不做訂閱權限判斷。
- Phase 3 若確認有長期使用價值，再另立商業化規格與法律／商店審查清單。

## 09 資料模型與資料安全

**資料分層原則：** V0 以本機資料為主；Store MVP 才加入帳號與雲端同步。所有私密正文（許願、告解、塔羅問題）都屬敏感資料，不寫入普通分析事件、錯誤日誌、推播內容或客服追蹤。客戶端只負責提出操作，成長等級、額度、刪除狀態與訂閱權益由服務端或本機權威狀態計算，不能接受客戶端直接上傳結果。

**User**
- id / target_bedtime / location_or_city / timezone / created_at / deleted_at
- `currency_balance`、`is_subscribed`、`subscription_expires_at` 僅 Phase 3 商業化後加入；Store MVP 不建立交易或訂閱權益。

**Wish**（樹）
- id / user_id / category / template_id / custom_text
- status：許願中／已飄走；plaque_blown_at / created_at / deleted_at
- `is_drifting`、`moderation_status`、`drifted_at` 僅 Phase 2 啟用
- `fulfilled_at` 僅作未來預留，不代表牌被吹走或願望已實現

**Confession**（樹）
- id / user_id / private_content / created_at / deleted_at
- `is_drifting`、`drifted_content`、`moderation_status`、`drifted_at` / `undrifted_at` 僅 Phase 3 啟用

**SleepEntry**（家）
- id / user_id / sleep_day / bedtime_at_utc / local_timezone / target_bedtime_at_event / source / is_on_time
- client_event_id / created_at / updated_at / deleted_at
- `sleep_day` 是依按下當下的本地時間、05:00 切換規則和當時設定計算出的固定歸屬日；之後修改時區或目標時間，不重算舊資料。

**WeatherSnapshot（Store MVP）**
- user_id / city_or_location / timezone / weather_code / fetched_at / expires_at / created_at
- 只影響天空、粒子和語錄，不影響成長、睡眠或抽牌結果。

**DailyOpeningState（Store MVP，可選）**
- id / user_id / local_date / quote_id / shown_at / completed_at
- 同一使用者同一本地日最多一次完整開場；重播只在本機播放，不重複建立資料。

**TarotDraw（Store MVP 可選）**
- id / user_id / local_date / question / card / response_text / keyword / weather_context / created_at / deleted_at
- 只保存使用者選擇保存的內容；永遠不可分享或進漂流瓶。V0 的問題不進雲端。

**TarotResponsePool / QuoteLibrary / Festival**
- 保留原有內容欄位，但由服務端或隨 App 發布的唯讀內容提供；不得讓一般客戶端修改牌義、回應或節日規則。

**Phase 2 之後資料**
- `BlessingReceived`、`DriftInbox`、`Transaction`、`ShopItem` 僅在各自階段另立安全與商業規格後加入，不列入 V0／Store MVP 核心資料模型。

### 補充規則：日期、同步與權限

- **SleepEntry 的日期與去重：** 使用者按下「睡了」時，依當下事件時間、使用者當時的 `timezone` 和 05:00 切換點計算固定的 `sleep_day`；同一 `user_id + sleep_day` 只能有一筆有效手動紀錄。伺服器重新計算 `is_on_time`，不接受客戶端直接指定結果。目標時間修改只影響修改後建立的新紀錄；不追溯改寫歷史資料。
- **跨時區與城市變更：** Store MVP 不做旅行後的歷史時區重算，但每筆 SleepEntry 必須保存事件當時的 `local_timezone` 和 `target_bedtime_at_event`。城市變更只影響新的天氣快照與新睡眠事件，不改寫舊資料；這個限制要在設定頁說明。
- **離線操作：** V0 只保存本機資料。Store MVP 的離線行為必須為每個寫入或刪除操作產生 `client_event_id`，同步時由服務端以冪等方式處理；重送同一事件不能新增第二筆資料。睡眠使用 `user_id + sleep_day` 唯一約束，其他內容使用不可重複的本機 ID。
- **同步衝突：** 伺服器是最終權威。離線刪除必須以同步事件送出，不能被舊裝置的建立事件覆蓋；同一筆內容的修改以較新的有效 `updated_at` 為準，衝突結果要回傳客戶端。WorldState、`house_level`、`tree_level`、額度和權益都由服務端重算，客戶端只能顯示暫時狀態。
- **WorldState 重算：** 每次有效 SleepEntry 新增、修改、刪除或同步後，服務端依 `is_on_time = true` 的有效紀錄重算 `house_level`；有效 Wish 數量重算 `tree_level`。重複操作、離線重送、跨裝置同步都不能重複升級。漏做一天不降級。
- **刪除：** 單筆刪除和刪除帳號要分開。使用者確認刪除後，內容立即從產品查詢和本機畫面移除；同步層要阻止舊裝置把已刪除內容重新建立。原文不進普通日誌、分析事件、推播或客服工具。後台備份是否短期保留，必須依適用地區法律和隱私政策定義期限；不能預設宣稱「保留 30 天一定合規」。
- **服務端權限（Store MVP 必做）：** 啟用 Supabase RLS。使用者只能讀取、修改和刪除自己的 User、Wish、Confession、SleepEntry、TarotDraw；一般客戶端不得直接修改 `user_id`、`is_on_time`、`house_level`、`tree_level`、內容審核狀態、交易金額或訂閱狀態。權威欄位只能由受控的服務端函式更新。
- **V0 本機資料：** 本機資料至少要有清除全部資料入口；若日後升級成雲端帳號，必須先定義匿名本機資料與帳號合併規則，避免把資料錯綁到別的帳號。

**關鍵安全設計：**

## 10 美術與場景設計

延續許願池原本的視覺語言（許願樹＋溫暖夜景，避開真實廟宇聯想），家、樹、願望牌也統一進同一套調性。

> 🎨 **配色與造型定案（美術方向重新調整）：** 原本規劃「靛夜為主、其餘顏色只當小面積點綴」，實測後發現這樣氛圍不夠、造型也容易顯得普通。改成參考 Minecraft 奇幻建築配合高階路徑追蹤算圖（如 Chunky）的視覺語言：**大膽的創意造型（蘑菇傘、花瓣、圓塔）＋飽和濃郁的色彩＋豐富的細節堆疊（藤蔓、花串、彩繪玻璃、懸掛燈籠）**，靠光影後製（體積霧、光柱、景深模糊、泛光）撐出氛圍，而不是靠限制配色。原本的五色仍然是很好用的基礎色票，但不再是「只能用這五色」的硬性限制，可以視造型主題（櫻花粉、紫藤紫、楓葉金等）自由擴展色彩。

> 🧊 **視覺總則：整個世界都是 voxel 方塊風構成，無例外。** 家、樹、願望牌、燈籠、鄰居島、**塔羅牌**等所有物件都是 voxel 立體模型，用 MagicaVoxel 建模。塔羅牌做成有厚度、能翻面發光的 voxel 牌，牌面用 voxel 拼出符號，抽牌在專屬的夜空場景進行（見第 04 節）。全部方塊構成、統一算圖氛圍，畫面才像出自同一個世界——「voxel」指的是建模方式，不是畫面感覺要簡陋，成品要跟參考的 Minecraft 高階算圖同一個等級。
>
> 原許願池的「天燈」意象已移除。許願的累積物是 **voxel 願望牌**——一塊小木牌，掛在樹枝上，像日本繪馬那種，也無宗教包袱。

### 場景

- **家：** 建在浮空島上（見第 02 節），沿用「越住越溫馨」邏輯——達標天數越多，窗戶燈光越暖、屋子裝飾越多。同一畫面上顯示 V0 的中性天氣備援或 Store MVP 的真實天氣效果與塔羅反思入口。**已解鎖的模型與裝飾全天保留，但燈火亮度由當下時段控制：夜晚最亮，清晨逐步變淡，白天基本關閉，黃昏再逐步亮起**（見第 02.5、03 節）。屋頂造型鼓勵大膽（蘑菇傘、圓塔尖頂等），不要求標準三角頂。
- **樹：** 許願樹跟家在同一座浮空島上，樹冠要做得**飽滿蓬鬆、比例誇張**（不要稀疏分散的小球狀葉叢），樹枝上掛願望牌（voxel 小木牌），花季可做成櫻花／紫藤等花瓣狀樹冠。跟家不是獨立場景，點樹鏡頭平移過去（見第 02 節）。
- **瀑布：** 浮空島邊緣垂落，voxel 半透明藍色方塊柱＋Godot 的 UV 捲動 shader 做出流動感＋粒子做水花水霧，細節見下方氛圍加強方向。
- **鄰居島：** 遠景漂浮的小島，簡化建模＋景深模糊處理，隨 house_level 解鎖陸續點亮，細節見第 02、15 節。
- **塔羅牌：** voxel 立體牌（有厚度、能翻面發光），牌面用 voxel 拼出符號（太陽、星星、月亮）。抽牌在專屬夜空場景進行：望向星空→寫問題→射上天空→牌海（滿天漂浮的牌**一律牌背朝上、發著微光**，看不到牌面圖案，維持懸念；只有被選中的那張才飛近、翻面亮出正面圖案）→抽牌翻正解讀。
- **家↔樹鏡頭平移、家↔抽牌夜空轉場：** 家跟樹是同一座島的鏡頭平移，不用做場景轉場動畫；抬頭望向星空才是真正離開島面的轉場，這段轉場動畫才需要儀式感。

### 氛圍加強方向（靠光與粒子，不是靠建模精細度）

參考了幾張原神截圖後確認方向：想要的是那種戲劇性暖光、巨樹存在感的**情緒**，不是要追那個等級的建模精細度，而且仍然全部用 voxel 製作。

- **樹冠比例誇張化：** 樹幹細、樹冠大、層數多做到 3～4 層，巨樹感靠比例堆出來，不用雕細節葉片。
- **光柱效果：** 用 Godot 的方向光＋體積霧，做出樹冠縫隙透光的丁達爾光柱，voxel 模型本身不用變複雜。
- **螢火／光點粒子取代花瓣特效：** 飄在樹冠周圍跟地面附近的發光小光點，量少但夠亮，是原神花瓣氛圍的 voxel 版替代方案。
- **地面發光小花點綴：** 樹根周圍點幾顆會發光的小 voxel 花草，呼應地面光效，不用做整片草地建模。
- **暖色不用全天開：** 可以只在特定天氣（黃昏／晴天）或節日時加強樹的暖光效果，夜晚維持靛夜基調；白天則是藍天配樹冠本身的花色（櫻花粉、紫藤紫等），日夜兩版各有各的主色調，不強求整天都是同一個顏色。
- **瀑布的做法（新增）：** 不做真的流體模擬。MagicaVoxel 裡把瀑布建成一整條半透明藍色的 voxel 方塊柱，從島緣垂直往下疊；Godot 端掛一個簡單的 UV 捲動 shader（貼圖隨時間往下位移），模型完全沒動、但視覺上有水流動的錯覺；瀑布頂端與底部各加一小撮粒子做水花水霧。整套做法效能負擔很低，跟做一面牆的工作量差不多。
- **鄰居島的做法（新增）：** 因為永遠只在遠景看、不會靠近，鄰居島可以做得比主島簡化很多，搭配 Godot 的景深後製模糊掉細節——「越遠越朦朧」本身就是氛圍的一部分，不用花力氣雕細節。

> 🚫 **紅線提醒：** 避免神社／鳥居／石獅狐狸像這類明確的宗教／廟宇符號，跟本節開頭「避開真實廟宇聯想」的原則一致——只抓光影與粒子的情緒，不抓建築符號。

**標題／場景標題：** Noto Serif TC（600/700）；**內文／介面文字：** Noto Sans TC；**數字（星光、字數）：** tabular-nums 對齊。

## 12 塔羅設計參考資料（外部研究整理，Phase 3 構想）

整理自四篇塔羅教學文章，主要回應「牌卡要做多少張」與「回應文案怎麼寫」這兩個待決問題。這節是**參考資料**，不是已拍板的設計決定。

### 12.1 一副牌的完整結構（78 張）

- **大阿爾克那 22 張：** 代表大方向、關鍵性事件或人生課題。
- **小阿爾克那 56 張，4 花色×14 張：** 權杖（火）熱情行動、聖杯（水）情感直覺、寶劍（風）邏輯衝突、星幣（土）金錢穩定。
- 每張牌都有一組正位關鍵字＋一組逆位關鍵字。

**對照現行方案：** 先做的 6 張正向牌全部屬於大阿爾克那裡評價偏正面的牌。**擴充順序建議：** 先擴到大阿爾克那全 22 張，再考慮小阿爾克那。

### 12.2 牌義寫法參考

每張牌用「正位」「逆位」兩組關鍵字表達。現行機制只做正向牌，只用正位語意、不判斷逆位——之後擴充到 22 張時再決定要不要引入逆位。

> ✏️ **文案原則：盡可能還原塔羅牌本來的感覺，不刻意避諱字眼。** 唯一的硬邊界是第 06 節的法律紅線——不能宣稱真的能預測、占卜，跟牌名、牌義道不道地無關。除此之外：**牌名照傳統用**（死神、惡魔、高塔不用改名或迴避，這些原型意象本來就是塔羅的吸引力所在）；**牌義先誠實講傳統解釋**（死神直接講「某個階段要結束、需要放手」，逆位直接講「抗拒改變」，不用先包裝成別的說法）；「只給溫暖」管的是讀完整段話之後的感受，不是每個字都要正面——公式是「先誠實講牌義→收尾補一句往前走的方向」，重點放在後段給方向，不是迴避前段本義。這套原則對現行 6 張牌與未來的大阿爾克那、逆位都適用。

### 12.3 若未來做多張牌陣：可直接參考的結構與整合邏輯

| 牌陣 | 第1張 | 第2張 | 第3張 | 適合問題 |
|---|---|---|---|---|
| 時間軸型 | 過去影響 | 現在狀態 | 未來傾向 | 事情怎麼發展 |
| 行動型 | 目前情境 | 主要阻礙 | 可行建議 | 我該怎麼做 |
| 選擇型 | 選項A | 選項B | 評估重點 | 比較兩條路 |
| 內外型 | 表層想法 | 內在驅動 | 外在表現 | 理解情緒/關係 |

> 📌 **牌陣結構定案：用「行動型」，不用「時間軸型」。** 「未來傾向」這個位置名稱本身有風險——等於在畫面上明講「這張牌在講你的未來」，太接近占卜預測的定位，跟第 04、06 節「不出現會/不會/準、不代表真實預測」的紅線衝突。行動型（目前情境／主要阻礙／可行建議）三個位置都是反思＋行動導向，沒有一格在講「未來會怎樣」，法律風險低很多。牌陣結構固定、內容客製化：三個位置模板不變，配出來的反思文字才依問題＋牌＋天氣變化。

**多張牌之間的四種關係：** 支持／延續、拉扯／對立、因果／回應、轉折／修正。

## 13 製作流程：從 V0 到上架

給第一次要動手的人的路線圖。先完成 V0 並用封閉測試驗證核心體驗，再補 Store MVP 的帳號、雲端、隱私和上架必要能力。每個階段結束都應該是「能給人用、能測、能根據回饋調整」的狀態；只有通過上架檢查的版本才送 App Store／Google Play。

### 👤 分工定位（重要）

**你（專案主）負責美術與決策，程式的部分交給 AI 協作完成。** 下面每一步都標上負責人：**🎨 你** 用 MagicaVoxel 做 voxel 資產、定調視覺、拍板決定、測手感；**🤖 AI** 寫程式、接後台與 API、除錯、解釋每段程式在做什麼；**🤝 一起** 需要你決定方向、AI 執行的事。你不用學會自己寫程式，你要學會的是「看得懂 AI 做出來的結果、能測、能給回饋」（詳見第 16 節）。

### 階段 0：開工前先拍板（不寫程式，1～2 天）

1. 🤝 拍板 V0 的本機資料格式、清除入口、目標就寢時間和塔羅文案邊界。帳號與雲端同步留到 Store MVP 再決定。
2. 🤝 決定 V0 使用中性天氣備援；真實天氣 API 和定位權限留到 Store MVP，並先選定可能使用的服務。
3. 🎨 若目標是日後上架，再提前了解 Apple／Google 開發者帳號申請條件；V0 網頁版或封閉測試不以商店帳號為前置條件。

### 階段 1：V0 體驗驗證（本機優先）

1. 🤖 **搭骨架先跑起來** —— Godot 空場景放灰盒佔位的家和樹，先確認鏡頭、點擊和返回流程。
2. 🤖 **做睡前打卡** —— 依本機固定規則保存睡眠事件，重複點擊不重複升級，漏做不扣等級。
3. 🤖 **做許願／告解** —— 本機保存、可查看和刪除；不公開、不分享、不做每日付費額度。
4. 🤖 **做塔羅反思** —— 6 張牌、固定星空、簡單弧形牌海、翻牌和返回；問題可選填，只在本機暫存，不解析內容。
5. 🤝 **換上第一版美術與聲音** —— 先用最小資產完成一個可反覆操作的閉環；天氣先使用中性備援，不阻擋主流程。
6. 🤝 **封閉測試** —— 觀察使用者是否能找到入口、是否願意回來，以及核心流程是否造成壓力；未達到驗證目標前不開工商業化。

### 階段 2：Store MVP（上架準備）

1. 🤖 **接帳號和雲端同步** —— Supabase Auth、RLS、唯一約束、`client_event_id` 冪等同步、離線刪除和衝突回傳先完成，再接 UI。
2. 🤖 **補天氣增強效果** —— 手動城市優先，授權定位為選配；加入快照、API 失敗備援和金鑰保護。
3. 🤖 **補隱私與安全功能** —— 本機／雲端刪除、資料清除、敏感正文不進日誌、危機資源頁和塔羅免責文案。
4. 🤝 **補可發現性與可用性** —— 核心入口不能只靠隱藏手勢；支援跳過動畫、不同螢幕尺寸和低階裝置。
5. 🤝 **完整測試後再送審** —— 先做封閉測試和商店資料檢查，不因功能完成就直接宣稱可以上架。

### 階段 3：Phase 2／3

- 漂流瓶先另立資料、安全和人工處理規格，完成過濾、略過、檢舉、封鎖和下架流程後再開放。
- 22 張牌、多張牌陣、自由回話和商業化各自拆成獨立規格，不與 V0／Store MVP 共用未驗證的額度和權益邏輯。

## 14 美術與場景製作建議（MagicaVoxel 導向）

voxel（方塊積木風）跟整個 App「安靜、溫暖、不擬真」的調性很搭：做得快、好統一，溫暖不擬真、剛好避開恐怖谷，檔案小、手機跑得動。

### 統一規範（動手前先定）

- **色票基準（不再鎖死）：** 五色（靛夜／燈金／翠玉／火硃／紙白）當基礎色票、存成 palette 檔方便套用，但不強制「全部資產只用這五色」——可依主題（櫻花粉、紫藤紫、楓葉金等）自由擴展，重點是每個場景要有清楚的主色調，不是雜亂無章。
- **統一體素密度：** 先定「1 公尺＝幾個方塊」，家、樹、鄰居島都照同一密度做（鄰居島遠景可適度簡化）。
- **光靠氛圍，不靠寫實：** 燈火、黃昏、星空這種「光的溫度」靠 Godot 的燈光、發光材質、粒子營造，比把模型做很精細更有效。

### 各場景的美術重點

- **家：** 一個基礎屋子＋多層可疊加的裝飾件，升級是逐件點亮／加裝飾，不是換新房子。屋頂造型鼓勵大膽（蘑菇傘、圓塔尖頂等）。
- **樹：** 情感核心，值得多花力氣。4～5 個生長階段（幼苗→小樹→成樹→茂盛→開花），階段切換要有過渡動畫或粒子，樹冠要做得飽滿誇張。願望牌做成 voxel 小木牌／石牌，一塊塊掛到樹枝上。
- **瀑布：** 半透明藍色 voxel 方塊柱從浮空島邊緣垂落，搭配 Godot 的 UV 捲動 shader 做出流動錯覺，不做真的流體模擬，頂端底部加粒子做水花水霧。
- **鄰居島：** 遠景漂浮小島，簡化建模＋景深模糊處理，同一棟房子改色重複擺即可，隨 house_level 解鎖陸續點亮。
- **天空／天氣：** 不做 voxel 模型，用 Godot 背景漸層＋光照＋粒子（雨、雪、星點、飄雲）。做一套天氣狀態，每種都要「就算是陰雨也很美」。
- **塔羅牌（V0／Store MVP）：** voxel 立體牌，有厚度、能翻面、能發光，牌面用 voxel 拼出符號。牌背朝上時發微光，V0／Store MVP 先排成一段弧、點一張抽出即可，環形星盤那種滑動聚合效果留到 Phase 3。搭配「射上天空→牌海浮現→翻牌」的動畫與音效。**抽牌夜空**是獨立場景（靛夜打底＋燈金星點），不是家/樹那兩個場景，也不受真實天氣影響。
- **牌面美術定案：固定舞台＋角色本身翻轉。** 牌面走完整立體小場景（例如太陽牌拼「人物剪影＋太陽＋地面」的縮小舞台），不是抽象符號。舞台（地板、背景、光源）永遠固定方向、正常打光，只有場景裡的角色模型本身在逆位時旋轉 180 度（頭朝下），不是整張卡一起翻轉——這樣光影永遠正確，一張牌只需做一份角色模型，正逆位共用（MVP 只有正位、不觸發翻轉，這個設計是為 Phase 3 引入逆位時預留）。

### 給一個人做美術的務實建議

先做灰盒佔位、程式先跑通，最後才換正式模型；資產分「基礎件＋裝飾件」，不要做「完成品」；氣氛的錢花在燈光和粒子上，不是花在模型精度上。

## 15 成長門檻與美術資產清單（初版方案，待實測調整）

> 📎 **開工前實作三節連讀：** 第 15 節（要做哪些美術資產、成長門檻數字）→ 第 16 節（你和 AI 怎麼分工協作）→ 第 17 節（每個功能做不做得出來、難度與雷）。這三節是把設計轉成實作的依據。

升級節奏要「一開始很快就有回饋，越到後面越慢」。**漏做一天絕不倒退、不扣等級**——這是全 App 的紅線，成長只會前進或停住，永遠不退。

### 家的溫暖度（house_level）— 靠累積準時就寢天數推進

| 等級 | 累積準時天數 | 畫面變化 |
|---|---|---|
| Lv.0 | 0 | 家有微光，冷清但不荒涼（冷啟動起點） |
| Lv.1 | 1 天 | 窗戶亮起暖光（第一次打卡就升級） |
| Lv.2 | 3 天 | 門口點一盞小燈、加一件掛飾 |
| Lv.3 | 7 天 | 煙囪冒煙、屋內更暖、多一件裝飾 |
| Lv.4 | 14 天 | 遠景出現第一座鄰居島的燈火 |
| Lv.5 | 30 天 | 鄰居島變多，村落夜景成形 |
| Lv.6+ | 之後每 30 天 | 持續增加鄰居島燈火／季節性小裝飾，無上限、越來越慢 |

### 「準時就寢」怎麼判定（Store MVP 初版）

規則先固定，實作時由服務端計算，客戶端不能自行提交 `is_on_time`：

- **打卡時間：** 目標時間前後 60 分鐘內算準時；太早超過 60 分鐘不算準時。
- **睡眠歸屬日：** 先把按下時間轉成事件當時的本地時間；本地時間 00:00～04:59 歸給前一天，05:00 之後歸給當天。
- **目標時間跨午夜：** 目標時間若落在 00:00～04:59，該時間的準時視窗仍依完整日期時間計算，不用單純以「當天日期」判斷。例：目標 01:00，00:00～02:00 的打卡歸到前一個 `sleep_day`，由伺服器保存固定結果。
- **超過 05:00：** 歸入新的 `sleep_day`；若不在該日目標時間的容差內，保存為 `is_on_time = false`，不增加等級，也不扣除既有等級。
- **一天一筆：** 同一 `user_id + sleep_day` 最多一筆有效手動紀錄。重複點擊不能重複升級；衝突由伺服器依事件時間和既定修改規則處理。

> V0 可以先用本機同一套規則；Store MVP 必須以服務端結果為準。±60 分鐘和 05:00 是初版參數，修改時要更新規格和測試，不可只改前端。

#### 目標就寢時間可以改嗎？（初版規則）

- 可以改。冷啟動設一次，之後在設定頁隨時能調。
- **改了只影響改動之後的新紀錄，不追溯重算過去的 `is_on_time`。** 例如本來目標 23:00、已累積 10 天準時，改成 01:00 後，那 10 天不會因為新目標而重新判定——避免有人用「改目標時間」回頭刷等級或洗掉紀錄。
- house_level 一樣是依「有效 SleepEntry 的 is_on_time」重算（見第 09 節），改目標時間只改變「往後新打卡怎麼判定準時」，不動歷史紀錄。

### 樹的生長階段（tree_level）— 靠累積許願數推進

| 階段 | 累積願望數 | 樹的樣子 |
|---|---|---|
| 幼苗 | 0～1 | 剛冒出的小芽（冷啟動時「種下第一棵樹」） |
| 小樹 | 2 | 有主幹和幾片葉（快速回饋） |
| 成樹 | 5 | 樹冠成形，開始能掛願望牌 |
| 茂盛 | 12 | 枝葉繁密，掛滿多塊願望牌 |
| 開花 | 25 | 開花＋掛滿願望牌，最華麗的完成態 |
| 開花+ | 之後每 15 個願 | 花況／光點持續豐富，無上限、越來越慢 |

願望牌（voxel 小木牌）是每許一個願就掛一塊，掛滿 5～7 天後被風吹走（見第 05 節），跟樹的階段分開算，不會無限堆積；「我許過很多願」看得見的是樹的成長等級本身，不是掛著的牌數。告解不推進樹的等級（是「放下」不是「許願」），但可以有自己的小視覺回饋。

- **燈火顯示和成長等級分開：** house_level 決定哪些房屋、窗戶、門燈和鄰居島已解鎖；當下是清晨、白天、黃昏或夜晚，則由第 02.5、03 節的時段規則決定這些燈的亮度。早上燈光變淡不代表家降級，白天熄滅也不代表已解鎖的裝飾消失。
- **完成「睡了」只觸發當次熄燈流程：** 窗戶、門口燈和鄰居島燈逐步變暗，隔天清晨再由晨光接手；漏睡一天不讓任何已解鎖的燈火或裝飾倒退、消失或被扣除。
- **house_level 以有效 SleepEntry 重新統計並依門檻重算，不用前端重複累加的方式** ——資料修正或跨裝置同步後，畫面和等級仍能回到同一個結果（見第 09 節）。

### V0／Store MVP 資產分層

**V0 最小資產：** 浮空島基座、基礎家、樹至少 3 個階段、1 種願望牌、簡化瀑布、6 張塔羅牌與牌背、基本燈光粒子和音效。鄰居島、日期字體和複雜開場先用佔位版本。

**Store MVP 再補：** 樹完整 5 階段、家裝飾、鄰居島、正式日期字體、天氣粒子和可跳過的每日開場。

**資產清單：**
- 家：基礎屋子×1、暖光窗戶件×1、門口小燈×1；掛飾和煙囪煙效屬 Store MVP 或後續美術迭代。
- 樹：V0 先做 3 個階段；Store MVP 補齊幼苗／小樹／成樹／茂盛／開花 5 階段、1～2 種願望牌和階段切換粒子。
- 浮空島：島體基座×1（含邊緣造型）。
- 瀑布：半透明藍色 voxel 方塊柱×1，搭配 UV 捲動 shader、水花和水霧粒子。
- 鄰居島：Store MVP 才加入簡化版小島和改色房子，搭配景深模糊。
- 天氣：Store MVP 才加入晴／多雲／雨等天氣效果；任何版本都保留中性備援畫面。
- 每日開場：Store MVP 才加入正式日期字體、流星和語錄飄散；節日裝飾不影響核心流程。
- 塔羅：6 張正向牌、1 張牌背、固定抽牌夜空和簡單弧形牌海。
- 共用氛圍件：燈籠／螢火光點，以及許願、熄燈、抽牌所需的基本音效和輕微觸覺。

**暫不製作：** 漂流瓶 UI、回顧卡、塔羅牌主題套組、環形星盤、多張牌陣、22 張以上牌組、付費商店素材。

### MVP／Store MVP 驗收標準

以下條件全部通過，才可以把 Store MVP 視為具備送審前提；V0 只需完成標示為 V0 的項目。

- 沒有網路時，V0 仍可完成家、樹、睡前打卡和塔羅反思流程。
- 拒絕定位或天氣 API 失敗時，村落不空白，且核心操作不被阻擋。
- 重複點擊「睡了」不會重複增加準時天數或升級。
- 00:00～04:59、05:00 後、目標時間跨午夜等案例的 `sleep_day` 和 `is_on_time` 都符合規格。
- V0 的許願、告解和塔羅問題可以查看與刪除；刪除後本機畫面不再顯示。
- Store MVP 中，同一個 `client_event_id` 重送不會建立第二筆資料；同一 `user_id + sleep_day` 不會有兩筆有效睡眠紀錄。
- 離線刪除同步後，舊裝置重新上線不能把已刪除內容恢復。
- 使用者只能讀取自己的私密內容；客戶端不能直接修改成長等級、`is_on_time`、審核狀態或權益。
- 塔羅和語錄不包含預測、保證、診斷、治療，或健康、法律、投資建議。
- 危機資源可從設定頁直接找到；高風險文字不會被塔羅結果包裝成答案。
- 核心入口不只依賴隱藏手勢，動畫可以跳過，文字在小螢幕不會被遮擋。
- 完成隱私政策、資料刪除說明、第三方服務清單、定位說明和目標地區的商店審查資料後，才進入送審流程。

## 16 這份做得到嗎？AI 寫程式、你做美術的協作分工

> 📎 開工前實作三節：第 15 節（資產與門檻）→ **第 16 節（分工協作）** → 第 17 節（逐功能可行性）。

**做得到，但要按階段做。** V0 的目標是完成並驗證本機核心閉環；Store MVP 的目標是補齊雲端、隱私、可用性與上架必要能力。不能把「AI 能寫出原型」等同於「產品已具備安全、穩定和可上架條件」。

### 分工總表：誰做什麼

| 你（🎨 專案主） | AI（🤖 協作） |
|---|---|
| 用 MagicaVoxel 做 voxel 資產（家、樹、燈籠…） | 寫全部程式（Godot 腳本、接後台、接 API） |
| 定調視覺風格、色票、體素密度 | 除錯，解釋每段程式在做什麼 |
| 拍板設計決定（成長門檻、動線手感） | 把你的美術素材接進 Godot |
| 測試「玩起來的感覺」，給回饋 | 打包、寫上架送審資料 |
| 申請帳號、付款、按送審鈕（要本人） | 教你每一步該點哪裡、貼什麼 |

**一句話：你像導演＋美術，AI 是工程師。你說要什麼、看成果、給回饋；AI 把它變成能跑的程式。**

### 各部分難度（對 AI 來說）

| 部分 | 對 AI 難度 | 你要做的 |
|---|---|---|
| 睡前打卡 | ★ 很簡單 | 測手感、確認熄燈動畫好看 |
| 許願／告解（存自己看） | ★ 很簡單 | 測、給回饋 |
| 接入 Supabase 存資料（Store MVP） | ★★ 不難 | Store MVP 才建置帳號、RLS 和同步；V0 使用本機資料 |
| 接入真實天氣 API（Store MVP，可選） | ★★ 不難 | 手動城市優先，定位為選配；V0 使用中性備援 |
| Godot 場景與動畫 | ★★ 不難 | 提供 voxel 素材、定手感 |
| 塔羅：望向星空反思牌（V0） | ★★ 需要調整手感 | 做 6 張 voxel 牌和牌背；文案一起想 |
| 上架準備（Store MVP） | ★★★ 繁瑣 | 帳號、隱私、測試和送審資料需本人確認 |
| 漂流瓶（Phase 2） | ★★★★ 最難 | 這是 Phase 2，V0／Store MVP 都不用碰 |

**重點：** V0 的核心功能（包括塔羅）主要是 ★～★★，AI 可以先做出可測版本；Store MVP 的帳號、同步、刪除、RLS 和上架準備需要額外驗證。最難的漂流瓶排到 Phase 2，V0／Store MVP 都不做。

### 你只需要記住三件事

1. **不用學寫程式，但要學會「看成果、給回饋」。** AI 做出一版，你打開來玩，告訴我「熄燈太快了」「樹長大的動畫要更明顯」——這種回饋比你會不會寫程式重要得多。
2. **可以先做網頁版驗證，不用一開始就碰上架。** Godot 能直接輸出成網頁，先做一個瀏覽器打開就能玩的村落，自己玩、給朋友玩，確認點子有人喜歡，之後再處理上架的繁瑣事。
3. **一步一步來，不要看「整份」。** 照第 13 節階段 1 的順序，一步一步做，不會一次面對整個專案。

### 協作節奏（對應第 13 節階段 1）

## 17 可行性總表：每個功能你要做多少、AI 做不做得出來

> 📎 開工前實作三節：第 15 節（資產與門檻）→ 第 16 節（分工協作）→ **第 17 節（逐功能可行性）**。

分工是「你做美術、AI 寫程式」，所以每個功能都用同一把尺量：**你的美術負擔（在 MagicaVoxel 做幾個 voxel）／AI 程式難度／要注意的雷**。難度標記：🟢 好做、🟡 要花時間調手感、🔴 難點或效能雷。

| 功能 | 階段 | 🎨 你的美術負擔 | 🤖 AI 程式難度 | 要注意的雷 |
|---|---|---|---|---|
| 家：基礎屋＋裝飾件 | Store MVP | 基礎屋×1＋裝飾件約5～6件 | 🟢 疊裝飾＝依等級開關顯示，簡單 | 無 |
| 家：鄰居島 | Store MVP | 0（基礎屋改色重複用＋簡化島體） | 🟢 複製擺放＋景深模糊 | 別擺太多，遠處點燈即可 |
| 瀑布：UV 捲動 shader | V0 | 半透明方塊柱×1 | 🟢 貼圖 UV 隨時間位移，模型不用動 | 效能負擔低，跟做一面牆差不多；水花水霧粒子另外加 |
| 家↔樹：同島鏡頭平移 | V0 | 0（用現有模型） | 🟢 攝影機在同一場景內移動，不是切場景讀取 | 比做圓形星球（地形彎曲、鏡頭繞轉）簡單很多，是刻意選的低風險做法；浮空島頂仍是平面，跟平面地面版邏輯相容 |
| 樹：5 個生長階段 | Store MVP | 樹體×5 | 🟢 依等級換模型 | 「長大過渡」動畫是🟡，可先硬切再優化 |
| 樹：願望牌掛載＋定時吹走 | V0 | 願望牌×1～2種 | 🟢 每許一願掛一塊，排程檢查掛滿天數就吹走 | 牌掛滿 5～7 天後自然吹走，不需要每日額度或疊放／群組邏輯 |
| 睡前打卡＋熄燈動畫 | V0 | 0（用燈光，非模型） | 🟢 記時間＋比對＋燈光變化 | 無，全 App 最單純的功能 |
| 天氣：背景＋光影 | Store MVP，可選 | 0（Godot 光照＋粒子） | 🟢 抓天氣代碼→切換光影 | V0 使用中性備援，不依賴網路 |
| 天氣：語錄 | Store MVP，可選 | 0（純文字） | 🟢 依天氣代碼配一句 | V0 先用通用語錄，不依賴天氣 API |
| 天氣：備援畫面 | V0 | 0 | 🟢 API 失敗→切中性畫面 | 一定要做，否則天氣掛了主畫面壞掉 |
| 每日開場：日期＋流星語錄 | Store MVP，可選 | voxel 數字0～9＋月份字（一次做好） | 🟢 選句＋短期不重複＋浮現/飄散動畫 | V0 不要求；Store MVP 同一本地日只播一次 |
| 節日語錄＋裝飾 | Store MVP，可選 | 節日小裝飾（想做才做） | 🟢 對照節日表換語錄/裝飾 | V0 不依賴節日內容；農曆節日的日期換算要留意 |
| 冷啟動開場儀式 | V0／Store MVP | 0（用現有素材） | 🟢 第一次打開的引導流程 | 無 |
| 純觀賞模式 | V0／Store MVP | 0 | 🟢 就是不做事、讓場景動 | 無 |
| 聲音＋觸覺 | V0／Store MVP | 音效素材（你找或做） | 🟢 觸發播放＋震動 | 無 |
| 塔羅：voxel 牌 | V0 | 6 張牌＋1 牌背 | 🟢 隨機抽 1 張 | 量小，比做房子簡單；V0 核心體驗，優先做 |
| 塔羅：回應配對 | V0 | 0（文案內容量） | 🟢 依固定牌義回應池提供反思提示 | V0 不解析使用者問題內容；一張牌配一組回應句撐耐看度，見第 04 節 |
| 塔羅：望向星空→寫字→射上天空→翻牌 | V0 | 0（Godot 動畫） | 🟢 轉場＋輸入框＋動畫 | 無 |
| 塔羅：牌海（先做簡單弧形排列） | V0 | 0 | 🟢 排成一段弧、點一張抽出 | 環形星盤那種滑動聚合效果留到 Phase 3 再做，不擋 V0 |
| 回顧卡 | Phase 2 | 卡片版型（簡單） | 🟢 撈舊資料生成一張卡 | 需累積夠久資料才有東西可回顧 |
| 漂流瓶：願望飄出/收到/回祝福 | Phase 2 | 0（用現有 UI） | 🟡 隨機延遲分發＋祝福統計＋過濾檢舉 | 社交要一整套防濫用機制，比單機功能重 |
| 塔羅：牌海升級成環形星盤滑動 | Phase 3 | 0 | 🟡 飄浮＋滑動轉動＋點選，要調手感 | V0／Store MVP 已有簡單弧形版可用，這是體驗優化，不急 |
| 塔羅：78 張多選牌陣 | Phase 3 | 牌擴到 22～78 張 | 🔴 效能（多張 3D 同時浮動）＋多牌解讀邏輯 | 排到 Phase 3，V0／Store MVP 不做 |
| 漂流瓶 B 版自由回話 | Phase 3 | 0 | 🔴 自由文字＝騷擾風險，要審核/檢舉/封鎖全套 | 排到 Phase 3，社群穩了再開 |

**白話總結：** V0 要做的美術量不大——浮空島基座、基礎家、樹的 3 個階段、1～2 種願望牌、瀑布、6 張塔羅牌與 1 張牌背，再加一些音效，大概十來個 voxel 資產，天氣和動畫多數用程式完成。Store MVP 再補樹的完整 5 階段、家裝飾、鄰居島、正式天氣效果和每日開場。V0 的程式主要是 🟢，塔羅也不例外；Store MVP 的帳號、同步、刪除和 RLS 需要額外驗證。真正的難點集中在 Phase 2、Phase 3（漂流瓶社交、環形星盤互動、78 張牌陣、自由回話）。
