# 待辦誌 設計手冊

這份手冊整理自 Claude 產出的「待辦誌」Artifact（一個可獨立運作的待辦事項網頁 App），把裡面實際寫出來的功能、介面結構、視覺系統、資料模型都拆解記錄下來，方便之後參考或延伸開發。

來源：[待辦誌 Artifact](https://claude.ai/artifact/LwUpNt95RyKX1ztSqrkGFi)

---

## 01 概念

- **核心體驗：** 一個單頁的待辦清單工具，可以幫每筆待辦加上「重要性（低／中／高）」、「類別」、「事件」、「預計完成日」，並依這些條件篩選、分組顯示。
- **一句話定位：** **「一本能依事件分堆、依重要性排序的待辦清單。」**
- **語言／風格：** 全繁體中文介面，視覺走溫暖紙感（米杏底色＋赭橘強調色），字體混搭襯線標題＋等寬數字，質感偏「手帳」而非制式待辦 App。

---

## 02 核心功能

**1. 新增待辦（composer）**
- 一行文字輸入＋送出。
- 重要性用三顆藥丸按鈕切換（低／中／高），預設「中」。
- 類別、事件都是下拉選單，選單旁各有一顆「＋」圓鈕，點下去會展開一列輸入框讓使用者當場新增新的類別／事件（不用跳頁、不用先到設定頁建立）。
- 預計完成日是原生日期輸入。

**2. 統計列**
- 頂部四格：總計、進行中、已完成、逾期（逾期數字用警示色標紅）。
- 統計會即時反映目前的篩選條件（選了某類別／事件時，統計只算篩選後的範圍）。

**3. 篩選**
- 狀態分頁：全部／進行中／已完成。
- 額外兩個下拉：依類別篩選、依事件篩選，各自預設「全部」。

**4. 依「事件」分組顯示**
- 這是這個 App 比較特別的設計：只要目前清單裡出現超過一種事件，畫面就會自動用事件分組（例如「小明的婚禮」自成一區），每組標題顯示事件名稱＋項目數。
- 分組排序依該事件裡最早的預計完成日排；沒有指定事件的項目一律排最後（「未指定事件」）。
- 只有一種事件（或都沒設事件）時，不顯示分組標題，維持單一清單，避免畫面雜訊。

**5. 任務卡片**
- 左邊一顆圓形勾選框，勾選＝完成（會記錄完成時間），再點一次可取消。
- 任務文字可直接點擊進入行內編輯（inline edit），Enter 確認、Esc 取消。
- 下面兩排標籤／中繼資訊：
  - 第一排：類別標籤（依類別自動配色，六色輪替）、事件標籤、重要性標籤——三個都可以直接點擊，原地變成下拉選單重新指派，不用開編輯視窗。
  - 第二排：新增日期、預計完成日（逾期會標紅並附「已逾期」字樣，當天會標黃附「今天」）、完成日期（未完成則顯示「未設定」的淡化樣式）——一樣可點擊直接改日期。
- 右邊刪除鈕：滑鼠移到卡片上才顯示（避免誤觸），刪除後跳 Toast 並提供「復原」5 秒內可救回。
- 排序邏輯（進行中）：逾期優先 → 重要性（高→中→低）→ 預計完成日早到晚 → 建立時間早到晚。已完成項目則依完成時間新到舊排。

**6. 空狀態與離線提示**
- 清單為空時顯示引導文字，鼓勵新增第一筆。
- 如果目前是「瀏覽器暫存模式」（沒有連上資料庫），畫面底部會提示「重新整理頁面後資料可能會遺失」。

## 03 資料存取策略

- App 會偵測執行環境是否提供 `window.claude.use("db")` 這個資料庫能力：
  - **有：** 走 Firestore 風格的 collection（`tasks`／`categories`／`events`），用 `onSnapshot` 即時同步，並在資料庫是空的時候自動灌入種子資料（3 筆範例待辦＋2 個範例類別：醫療、日常）。
  - **沒有：** 退回純前端記憶體陣列運作，同樣灌種子資料，但重新整理頁面就會全部消失，並顯示離線提示。
- 這個雙軌設計讓同一份 Artifact code 可以「有後端就是真的待辦工具，沒後端也能單機示範」，不會因為缺資料庫就整個壞掉。
- 刪除採「軟性 Undo」：先真的刪除／從陣列移除，同時保留快照，Toast 的復原按鈕會把快照整筆寫回去。

## 04 視覺設計系統

**色彩（CSS 變數，區分亮／暗模式）**

| 用途 | 亮色 | 暗色 | 說明 |
|---|---|---|---|
| 背景 `--bg` | `#eeece4` | `#171410` | 米杏／深咖啡底 |
| 卡片 `--surface` | `#ffffff` | `#211d17` | |
| 次卡片 `--surface-2` | `#f7f5ef` | `#29241c` | composer 內欄位底色 |
| 主文字 `--text` | `#221f1a` | `#f0ebe0` | |
| 次文字 `--text-muted` | `#75705f` | `#a89e8a` | |
| 邊框 `--border` | `#e2ddd0` | `#3a3327` | |
| 強調色 `--accent` | `#a8571f`（赭橘） | `#e0954f` | 新增按鈕、標題點綴 |
| 成功 `--success` | `#3f7a52` | `#6fae82` | 完成狀態 |
| 警示 `--warn` | `#b8791f` | `#e0ad5c` | 今天到期 |
| 危險 `--danger` | `#b23a3a` | `#e07a7a` | 逾期 |

- 類別標籤另外準備 6 組低飽和配色（`cat0`～`cat5`：青綠、靛紫、粉紫、灰藍、橄欖、赭棕），新增類別時依序輪替指派顏色，讓多類別並存時能一眼區分又不刺眼。
- 支援系統亮暗模式自動切換（`prefers-color-scheme`），也保留 `data-theme="light/dark"` 手動覆寫的掛勾。

**字體**
- 標題／事件分組名稱：`Noto Serif TC`（襯線，帶手帳質感）。
- 內文與標籤：`Noto Sans TC` / 系統無襯線字體。
- 日期、統計數字、等寬資訊：`JetBrains Mono`，數字用 `tabular-nums` 對齊。

**元件風格**
- 全面圓角（按鈕近全圓角膠囊、卡片 10–14px 圓角），陰影很淺（`0 1px 2px` 等級），走輕量紙感而非強對比的 Material 陰影。
- 重要性用左邊框顏色條（高＝紅、中＝黃、低＝灰、完成＝綠）快速辨識，不用整卡染色，維持乾淨。
- 大量互動採「原地行內編輯」而非跳出對話框（點文字變輸入框、點標籤變下拉選單、點日期變日期選擇器），減少操作層級。

## 05 資料模型

**Task（待辦）**
- `id`
- `text`：內容
- `done`：是否完成
- `priority`：`high` / `mid` / `low`
- `category`：類別名稱（字串，可為 `null`）
- `event`：事件名稱（字串，可為 `null`）
- `dueDate`：預計完成日（`YYYY-MM-DD` 或 `null`）
- `createdAt` / `completedAt`：ISO 時間字串
- `seed`：是否為示例資料（畫面上會標「示例」小標籤）

**Category（類別）**
- `id` / `name` / `colorIndex`（決定標籤配色，對 6 取餘數）/ `createdAt`

**Event（事件）**
- `id` / `name` / `createdAt`

三者關聯用「名稱字串」對應，而非外鍵 id 對應（`task.category` 存的是類別名稱本身）——好處是就算資料庫層還沒建好類別／事件也能先打字上去，壞處是類別改名不會自動連動已存在的任務，算是刻意換取實作簡單的取捨。

## 06 待改進 / 觀察重點

- **類別、事件改名不連動：** 因為關聯用名稱字串比對，若之後要支援「重新命名類別」，需要額外處理把所有引用該名稱的 task 一併更新，否則會出現孤兒標籤（顯示成「未分類／未指定事件」樣式的舊名稱）。
- **事件分組排序目前用「最早到期日」：** 沒有到期日的事件會被排到最後，長期使用若事件很多、多數沒填日期，分組順序可能不夠直覺，可考慮改成「建立時間」或讓使用者手動排序。
- **離線模式沒有落地儲存：** 目前退回本機模式時是存在記憶體陣列，沒有寫 localStorage，重新整理必掉資料，如果要當真正的離線可用工具，這塊值得補上。
- **目前沒有「批次操作」：** 例如批次刪除已完成、批次搬移類別，資料量大時可能需要。

## 07 若要獨立成產品：帳號、資料庫、推播規劃

現在這份是 Claude Artifact，資料庫用的是 Artifact 平台自帶的 `db` 能力——**所有打開連結、且能連上資料庫的人共用同一份清單**（一起編輯，不是各自獨立），而且一旦用了這個能力，**就不能再公開分享連結，只能分享給同一個組織裡登入的人**。如果目標是「每個人登入後各自擁有一份待辦、還能收到到期提醒」，這已經超出 Artifact 平台能做的範圍，得做成獨立網站/App。以下是要補的四塊：

**1. 帳號系統（現在完全沒有）**
- 需要登入/註冊，系統才知道「這是誰的清單」。
- 選項：Supabase Auth、Firebase Auth、Clerk，免費額度內可處理 email／Google 登入。

**2. 真正的資料庫（換掉 Artifact 的 `db` 模擬）**
- `window.claude.use("db")` 只在 Claude Artifact 環境裡有效，脫離平台就沒有了，要換成 Supabase（Postgres）或 Firebase（Firestore）。
- 手冊第 05 節的 Task／Category／Event 資料結構可以直接沿用，每筆多加一個 `user_id` 欄位，查詢時只抓自己的資料即可做到「人手一份」。

**3. 推播通知（全新的一塊）**
- 用瀏覽器原生 **Web Push**（Push API + Service Worker），免費——Google／Mozilla／Apple 提供的推播中繼服務不收費。
- 使用者只要按過一次「允許通知」，之後手機不用開著網頁也會收到系統通知，跟一般 App 的通知體感一樣。
- 但要「到期前主動提醒」，不能只靠使用者開著頁面，需要**後端排程**（Supabase Edge Functions／Firebase Cloud Functions 設排程，例如每小時掃一次快到期的任務並觸發推播），這是額外的工程量。
- iOS 例外：Safari 要 16.4 以上，且使用者必須先把網頁「加入主畫面」變成 PWA 才能拿到推播權限，單純用 Safari 開網頁申請不到；Android 直接在瀏覽器允許通知即可，沒有這個限制。
- 如果之後想包成原生手機 App（而非網頁），才需要換成 Apple／Google 的原生推播（APNs／FCM），並多一筆上架費：Apple 一年 US$99、Google 一次性 US$25。

**4. 前端要重寫的部分**
- 現有的 UI／互動邏輯（新增、篩選、事件分組、行內編輯）可以直接沿用。
- 但資料存取層（現在直接呼叫 `col.add()`／`onSnapshot()`）要整個換成呼叫 Supabase/Firebase 的 SDK，並加上「只顯示自己帳號資料」的判斷。

**成本概估：**

| 項目 | 免費？ | 備註 |
|---|---|---|
| Supabase（帳號＋資料庫） | 免費額度內可用 | 個人/小規模用量幾乎用不完 |
| Web Push 通知 | 免費 | iOS 需先加到主畫面才拿得到權限 |
| 前端 Hosting（Vercel/Netlify） | 免費 | 部署現有這份網頁 |
| 後端排程檢查到期日 | 免費額度內 | Supabase/Firebase 都有排程功能 |
| 上架 App Store／Google Play | 否 | 只有想做「真的 App」才需要，網頁＋PWA 可完全跳過這筆 |

**兩種規模的取捨：**
- 只要「各自登入、各自一份清單、頁面上看到到期提醒的視覺標示」——不需要推播那一層，Supabase 免費額度＋前端小改，工作量不大。
- 要「手機主動跳通知提醒」——才需要 Web Push＋後端排程，工程量明顯拉高，且要事先告知 iPhone 使用者多做「加入主畫面」這個步驟。
